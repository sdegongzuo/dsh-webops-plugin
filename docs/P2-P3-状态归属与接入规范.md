# P2 / P3 新工具接入的 CDP 状态归属规范

> 全部结论来自本机实测（Electron **44.0.0** / Chromium 152.0.7977.54 / Windows）。运行器在 `deepseek-harness` 的 pnpm store 里：
> `deepseek-harness/node_modules/.pnpm/electron@44.0.0_*/node_modules/electron/dist/electron.exe`——**根 `node_modules/electron/dist` 不存在**（pnpm 不 hoist），按老路径找会误判成"本机没有 44"。
> U8/U9 的三个探针（`u8.jsonl` / `u9.jsonl` / `u9b.jsonl`）跑在 44.0.0 上；另在 **Electron 43.2.0** 上复跑一遍（`u8-e43.jsonl` / `u9-e43.jsonl` / `u9b-e43.jsonl`），**两版结果逐项一致**。
> 其余原始时序日志同样在 `.workbuddy/tmp/`（`gl.jsonl` / `gl2.jsonl` / `cl.jsonl` / `rp2.jsonl` / `rp3.jsonl` / `u6.jsonl` / `u6b2.jsonl` / `u7.jsonl`）。
> 事实条目里 **F1–F8、F10–F14 为实测**，F9 是**推论**（已标注）；开发方案第 7 节列出补测结果 U1–U9。

## 0. 一句话

**CDP 的状态作用域是逐 domain 不同的，不能一概而论。**
"target 级共享、后写赢"在 `Emulation` 全类和 `Network` 的**部分**命令上成立——实测 `emulateNetworkConditions`、`setExtraHTTPHeaders` 跨 client 覆盖，而同域的 `setBlockedURLs` 却 session 私有。因此**每接入一个会写状态的命令都要先实测它的作用域，连同一个 domain 内都不能类推**。

补测（F8）进一步说明：**共享的域也不止 `Emulation` 和 `Network`**——`Page.addScriptToEvaluateOnNewDocument` 同样是 target 级共享，且副作用要到"下一次导航"才显形。所以判据不是"哪个 domain"，而是"**这条命令写的是不是 target 级行为状态**"。

## 1. 本轮实测事实（F1–F7 首轮；F8/F9 方案检视后补测；F10 定位句柄；F11–F14 事件重放与投递）

| # | 事实 | 证据 |
|---|---|---|
| F1 | `Emulation.setDeviceMetricsOverride` 的覆盖**跨 client 可见，后写赢** | A 设 400 → A 读 400；B 设 600 → A 读 **600** |
| F2 | `Emulation.clearDeviceMetricsOverride` **只还原 devicePixelRatio，视口尺寸永久残留** | 基线 900 → 设 400 → clear 后读 **400**；再设 800 → clear 后又读 **400** |
| F3 | `Network.setBlockedURLs` 是 **session 私有**，互不影响；空数组是**有效**清除 | A 设 `['*']` → A 被阻断；B 设不匹配 pattern → A **仍阻断**；A 自己设 `[]` → A **恢复** |
| F4 | `Runtime.enable` 会把该 target 的 console 历史缓存**全量重放**，每次 enable 都重放一遍 | 3 次 attach/enable，收到 `M1M2` → `M1M2M3` → `M1M2M3M4`（干净版，已排除监听器累积） |
| F5 | 重放**包含 debugger detach 期间**产生的消息 | detach 期间用 `webContents.executeJavaScript` 打 `MID-DETACHED`，re-attach 后收到 ✓ |
| F6 | `Overlay.enable` 必须先 `DOM.enable` | `Overlay.enable` 直接报 `DOM should be enabled first` |
| F7 | 上一轮"事件是广播的"已更正为：**只有 enable 过该 domain 的 session 才收** | B 未 enable 任何 domain 时收到 0 个事件 |
| F8 | `Page.addScriptToEvaluateOnNewDocument` **跨 client 共享**：注册者不导航时，**别人触发的导航照样被注入**；但注册项随注册者的 session detach 而清除（旧 identifier 报 `Script not found`） | A 注册 → B 触发导航 → B 与 A 都读到 `window.__U6 === "A"`；A detach 后再导航则不再注入 |
| F9 | CDP **不广播其它 client 的命令**，所以"人工设了 UA override"agent 侧一无所知——`owner: 'human'` 必须有明确的判定来源，见第 3 节 | 推论（F7 的直接后果） |
| F10 | `backendNodeId` 是**稳定定位句柄**：跨 `DOM.getDocument` 恒定、**无需 `DOM.enable`**、可直接配 `Runtime.callFunctionOn` 取 rect；元素被 `replaceWith` 换掉后 `resolveNode` 仍成功，但 `isConnected` 变 `false`（**可检出**） | nodeId 6→15→24 而 backendNodeId 恒为 6；换掉元素后 `isConnected=false` |
| F11 | `Log.entryAdded` **也会重放**（含 detach 窗口），但字段口径与 `Runtime.consoleAPICalled` 不同：`timestamp` 是 **number**、**无 `executionContextId`**、有 `source`（`javascript` / `network` / `other`） | detach 期间产生的条目在 `Log.enable` 后重新抵达；重放条 `ts=1789289442861.96(number)`、`ctx=false` |
| F12 | **`Log` 的重放上限也是 1000 条**，且超限时**显式发一条截断提示条目**（`source='other'`、`timestamp=0`） | 实时 3000 条 → 重放回 1000 条 + 1 条 `'2010 log entries are not shown.'`（3010−1000=2010） |
| F13 | **`Network` 事件不做历史重放**：detach 窗口内**已完成**的请求**永久丢失** | 同一窗口内发起的两个请求，re-enable 后 `Network.*` 事件**一条都没有** |
| F14 | **跨 detach 的"进行中"请求**：attach 期发起、re-attach 后完成 → 收尾链完整；**detach 期间发起** → 只收到响应侧事件，**`requestWillBeSent` 缺失** | A：`responseReceivedExtraInfo`→`responseReceived`→`dataReceived`→`loadingFinished` 四条齐；B：三条，`requestWillBeSent` 缺席 |

**修订上一轮说法**：
- ❌ 旧：「`clear` 会把人工设的值一起压掉」→ ✅ 实际是 **per-session 覆盖槽，clear 弹自己那层**；且**连自己都还不了原**（F2）。
- ⚠️ 旧：「target 级状态共享、后写赢、无归属（普适）」→ 只对**部分**域成立（见 F3：`Network.setBlockedURLs` 就是私有的），而且**并非无归属**——跨 client 共享的命令必须记账（见第 3 节）。

## 3. 硬规则（按顺序，能用前一条就别用后一条）

1. **不产生**：新工具的默认形态应当是"只 enable 读事件"或"纯计算"。`Runtime`/`Log`/`Network` 的只读采集属于这一类，是安全的——**但 `Network` 的 enable 有个已知缺口**：跨 detach 的请求会产出"无请求头的半截记录"（F14），采集器必须显式处理，见 §2 与开发方案 3.2.1。
2. **session 私有优先**：需要设置行为时，优先选 session 私有的命令（如 `Network.setBlockedURLs`，F3）。它们是天然的隔离。
3. **必须写 target 级状态时，记账 + 冲突报错**：**跨 client 覆盖的域不止 `Emulation`**（`Network.emulateNetworkConditions` / `setExtraHTTPHeaders`、`Page.addScriptToEvaluateOnNewDocument`、`Page.bringToFront` 同样是 target 级共享，实测见 `[V25][V26][V35][V21]`）。用 `BrowserRuntime` 内的 `targetState: Map<targetId, Map<StateKey, {owner, at, applied, previous}>>`，已被另一方持有则抛可恢复错误 `BROWSER_STATE_CONTENDED`，而不是静默覆盖。
   - **`owner: 'human'` 的来源必须定义清楚**（CDP 不广播其它 client 的命令，F9），否则这个错误码永远触发不了：① P3 接管激活期间，该 target 的 target 级状态**整体视为 `human`**（粗粒度让渡，**主力手段**）；② 写入后延迟 ≥170ms 回读（`[V7]`）值不符 → 判 `human`——**只对有读取面的 key 成立**（`Emulation` 两条可读；`Network.emulateNetworkConditions` / `setExtraHTTPHeaders` 没有 get 命令，`[V25][V26]` 的"读到"是页面行为侧回显，CDP 读不到）；③ 未观察过的 key 在**语义与展示**上按"来源未知、可能来自人工"，但**不得据此阻断写入**。
   - **冲突判定条件**（避免"第一次设置就被判争用"的死锁）：`owner === 'agent'` 且探测到值被外部改写 → 抛；处于接管窗口 → 抛；**从没被 agent 写过 → 允许写**，回执标注来源未知并把旧值留在 `previous`。
   - **`BROWSER_STATE_CONTENDED` 要有恢复路径**：payload 带 `stateKey`/`holder`/`at`；错误**不可重试**（原样重发必然再失败，这句要写进错误消息）；允许的唯一"抢"的姿势是显式 `force: true`，并把被覆盖的 `previous` 写进回执。
4. **永远不要用 `clear*` 做还原**：F2 已证明 `Emulation.clearDeviceMetricsOverride` 还不了原。要还原就**显式 set 回真实尺寸**。
5. **观察层消解**：`refs.resolve()` 前用 `{href, performance.timeOrigin}` 轻量指纹比对，不一致就推进 ref 纪元并报 `BROWSER_STALE_REF`。这把 `stale_ref` 从被动检查升级为主动失效。
   - **这是启发式，不是完备判定**：`href` 与 `timeOrigin` 都不变的 SPA 内部重渲染抓不住。兜底必须留在 `browser_locate` **每次现算 `getBoundingClientRect()`**，而且**三个判据都要查**（F10）：`resolveNode` 抛错 → `BROWSER_STALE_REF`；`isConnected === false` → `BROWSER_STALE_REF`（**只查 resolveNode 会漏**）；rect 宽高为 0 → 报"不可点击"。绝不能缓存 snapshot 时的几何值。
   - **已知漏报**：节点没被换、只是被复用来显示另一条数据（列表重排 / 虚拟滚动）。廉价手段检不出，locate 只报坐标，点得对不对由调用方按业务语义判断。

## 4. `browser_execute` 的边界（唯一的高危入口）

它是逃生舱，能碰的不只是"target 级状态"，而是**跨 target 与整个浏览器**。

**用允许列表（默认拒），不用拒绝列表**：
- 拒绝列表在本节早先的版本里写成"优于允许列表，因为新命令会不断加入"——**这个理由是反的**。命令不断加入意味着黑名单永远追不上，任何未列出的新命令默认**放行**；而本规范第 3 节与开发方案 7.2 的立场是"新命令默认按共享处理"。默认放行的黑名单与处处保守的哲学自相矛盾。本节与第 2 节表格原先也互相打脸（一处写"白名单"、一处写"拒绝列表"），现统一为允许列表。
- 未在允许列表里的 `domain.method` 一律拒，错误消息带上 method 全文。

**允许列表**（只读 / session 私有 / 只导航）：
`Runtime.evaluate`、`Runtime.getProperties`、`DOM.getDocument`、`DOM.querySelector`、`Page.navigate`、`Page.reload`、`Page.captureScreenshot`、`Accessibility.getFullAXTree`、`Network.enable`、`Network.getResponseBody`、`Log.enable`。

**必须拒绝的**：
- `Target.*` —— `Target.attachToTarget` 可拿到**其它标签页**的 session，越出本会话边界
- `Browser.*` —— `Browser.close` 直接关掉整个浏览器
- `Emulation.*` / `Fetch.*` / `Overlay.*` —— 跨 client 污染（见第 2 节）
- `Input.*` —— 绕过 P1 的能力分级（`BROWSER_TOOL_CAPABILITIES` 的 `read`/`mutate` 判定的意义会被架空）
- `Network.emulateNetworkConditions` / `Network.setExtraHTTPHeaders` —— **实测跨 client 共享、后写赢**（`[V25][V26]`）。早先版本把整个 `Network` 域列进"允许"，是漏的
- `Network.setCacheDisabled` —— 作用域无法判定，按最坏假设拒
- `Page.addScriptToEvaluateOnNewDocument` / `removeScriptToEvaluateOnNewDocument` —— **实测跨 client 共享**（`[V35]`）：注册者不导航，别人触发的导航照样被注入。副作用要到"下一次导航"才显形，尤其危险

## 5. 补测结果（已全部完成）

| 编号 | 问题 | 结论 |
|---|---|---|
| U1 | `Network.emulateNetworkConditions` / `setExtraHTTPHeaders` / `setCacheDisabled` 的作用域 | 前两者**跨 client 共享、后写赢**；`setCacheDisabled` **无法判定**（本机无观测面）→ 按最坏假设处理 |
| U2 | `Overlay.highlightNode` 与人工 DevTools Elements 面板高亮是否互相取消 | **不取消**——多 client 各自独立、精确覆盖自己的元素 |
| U3 | `Runtime.setAsyncCallStackDepth` 等 Runtime 级设置是否跨 session | **session 私有** |
| U4 | `clearDeviceMetricsOverride` 的残留是 Electron 特有还是 Chromium 通用 | **Electron 特有**；纯 Chrome 153 完全还原 |
| U5 | `devtools-opened` 事件时序 | 回调内**同步** attach 即可，无需延迟 |
| U6 | `Page.addScriptToEvaluateOnNewDocument` 的作用域与生命周期 | **target 级共享**（别人触发的导航也吃它的注入），但**注册项随注册者 session detach 清除**；旧 identifier 跨 session 失效 |
| U7 | `backendNodeId` 能不能当稳定定位句柄 | **能**：跨 `getDocument` 稳定、无需 `DOM.enable`、可配 `callFunctionOn` 取 rect；元素被替换后靠 `isConnected` 可检出（F10） |
| U8 | `Log` / `Network` 两域有没有 `Runtime` 那样的"enable 即全量重放" | **`Log` 有、`Network` 没有**（F11/F13）；且 `Log` 的字段口径与 `Runtime` 不同，去重键必须按域分开 |
| U9 | `Log` 的重放上限；跨 detach 的进行中请求 | `Log` 上限**也是 1000**，超限有显式截断提示条目（F12）；进行中请求的后续事件**会**投递，但 **detach 期间发起**的缺 `requestWillBeSent`（F14） |

> U6 是方案检视后追加的补测，日志 `u6.jsonl`（detach 行为）与 `u6b2.jsonl`（跨 client 共享）。
> 判据细节：**"共享"与"持久"是两件事**——它不跨 session 存活，但只要注册者活着，任何 client 的导航都会被注入。
> U8/U9 的日志：`u8.jsonl`（两域是否重放）、`u9.jsonl`（`Log` 上限 1000 + 截断提示条目）、`u9b.jsonl`（跨 detach 的进行中请求）。

证据与详细判读见 `P2-P3-开发方案.md` 第 7 节。
