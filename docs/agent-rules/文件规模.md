# 文件规模与拆分规则

新增、扩展、重构或 review 人工维护的源码、测试、脚本、配置及规则文档时读取本文件。

## 1. 默认上限

- 单文件默认不超过 **2000 行**；超过时先按职责拆分，或提供符合 §3 的特殊说明。
- 按实际文本行数统计，包含注释、空行和夹具；CRLF 与 LF 使用同一口径，末尾换行不额外算一行。
- 第三方代码、依赖、构建产物、机器生成文件和自动生成的验收证据不适用此上限；不能把人工代码标为生成文件来规避。
- 修改既有超限文件时，先核对职责与例外依据，再决定本轮拆分范围；未修改的历史文件不要求顺带重构。

## 2. 拆分要求

1. 按可以独立修改和验证的职责拆分，专用类型、schema、渲染与实现尽量同组维护。
2. 保留对外入口、调用顺序、状态归属、错误语义和行为契约；共享状态由明确的单一位置持有。
3. 新模块只接收需要的依赖，不把原对象的所有私有方法和字段包装成大上下文对象传递。
4. 完成后核对行数、依赖方向和循环引用，运行对应类型检查、测试与必要的运行态验证。

### 测试文件

测试优先按被测公共契约及行为组织，不要求随着实现文件拆分，也不为压缩行数隐藏测试步骤或抽出大量断言 helper。

超限测试文件需要特殊说明，但行数本身不足以证明应拆分。评估这些实际收益：

- 是否覆盖互不相关的公共契约，可形成独立测试组。
- 是否需要不同的运行环境、初始化或隔离方式。
- 是否存在明确的定位困难、频繁冲突或运行性能问题，拆分能够改善。
- 拆分是否会产生更复杂的共享夹具，或让读者跨文件才能理解一次测试。

## 3. 特殊说明

例外可以写在文件头，或登记在本节。必须明确具体路径、保留完整文件的理由，以及何时重新评估。仅写“测试文件”“以后再拆”或“历史原因”不足以构成例外。

review 时核对例外理由是否仍成立；职责、运行环境或夹具组织发生变化时重新评估。

### 当前例外

| 文件 | 保留理由 | 重新评估条件 |
|---|---|---|
| `src/browser-cdp/provider.test.ts` | 从 `CdpBrowserProvider` 公共入口验证完整行为，各组使用同一套 `FakeChrome`/`FakeSocket` 协议夹具；本轮重构保留原测试作为行为回归基线，避免同时改变实现与测试组织。 | 出现独立运行环境、共享夹具妨碍局部理解，或有明确冲突、定位及性能问题时；继续扩展前核对行为分组。 |

## 4. 完成标准

- 本轮新增与修改的适用文件均不超过 2000 行，或已有可核对的具体例外说明。
- 拆分后的专用实现仍集中、依赖无环、共享状态无新增副本。
- 验证结果说明实际运行范围及跳过项，不用源码行数或绿测试替代真实交互验收。

测试组织的参考依据：[Vitest 测试组织](https://vitest.dev/guide/learn/testing-in-practice#organizing-test-files)、[Google 单元测试可读性](https://abseil.io/resources/swe-book/html/ch12.html)。这里的 2000 行是本仓库维护规则，不是这些指南规定的统一阈值。
