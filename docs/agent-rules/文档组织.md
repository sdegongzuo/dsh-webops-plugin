# 长期文档组织标准

适用于已落地、需要长期使用和维护的文档。目标是：人能快速理解并操作，agent 能找到入口、准确执行和核验结果。两者共用一套正文，不分别维护流程。

## 1. 适用范围

| 适用 | 不适用 |
|---|---|
| 已实现功能的使用、安装、运维和发布指南 | 初始方案、需求草稿、未实施的设计 |
| 当前生效的规则、架构和机制参考 | 开发计划、任务拆解、进度记录、调试笔记 |
| 持续维护的验证方法、验收索引和故障处理指南 | 单次开发报告、临时实验记录、原始日志 |

按内容用途判断，不按文件名判断。混合文档中，已落地部分适用本标准；未实施部分单独标明状态和范围。功能落地后，从方案和开发记录中提炼当前操作、约束与依据，再接入长期文档入口。

被长期文档或任务入口引用的方案，应在头部标明状态、核对日期和当前指南位置。实现、验收、安装与发布状态分别说明。已落地方案注明“仅历史依据”，不再作为操作入口；仍在推进的设计可保留明确的设计入口。混合方案按章节标明适用范围，不将整份文档当作已落地或未实施。

过程记录另按 [过程记录管理](过程记录.md) 维护，统一从 [记录入口](../records/README.md) 查找。长期文档引用必要结论和证据，不复制持续追加的开发过程。

本标准不要求重写历史过程记录，也不以整理文档为由删除文件。文件操作遵守 [项目规则](../../AGENTS.md#文件删除)，文件规模遵守 [文件规模与拆分规则](文件规模.md)。

## 2. 按任务组织，按需展开

入口回答“我要做这件事，该读哪里”。日常路径直接可见，升级、排障和特殊情况按条件展开。

| 文档职责 | 应包含 | 如何到达 |
|---|---|---|
| 入口 | 任务触发条件、目标文档和适用章节 | AGENTS.md、README 或功能入口 |
| 操作指南 | 前置条件、输入、步骤、通过条件和失败处理 | AGENTS.md 或对应任务入口 |
| 规则 | 必须满足的要求及适用范围 | 受约束的操作指南或 AGENTS.md |
| 机制参考 | 当前架构、配置含义、实现约束和必要原因 | 相关操作指南或架构入口 |
| 验收索引 | 交付结论、证据入口及适用范围；详细过程另存记录 | 验证方法或交付状态入口 |

这些是内容职责，不是必须新建的文件清单。先复用现有文档；只有读者任务、适用条件或维护职责不同，且拆分能减少查找成本时，才另建文件。

规则类文档默认放 docs/agent-rules/；指南和机制参考放 docs/ 的现有职责位置；过程记录按独立管理规则存放。新增文档接入对应任务入口，只有需要 agent 独立识别的新任务分支才登记 AGENTS.md，细分材料由上级文档链接。

## 3. 操作指南的基本结构

日常流程放在前面，例外分支放在对应步骤附近或链接到专项文档。每一步写清执行者、动作和完成条件；本机操作与 CI 自动步骤分别标明。

| 项目 | 写清什么 |
|---|---|
| 适用条件 | 何时走本流程，何时转其他入口 |
| 前置条件 | 必需配置、依赖、权限和已有验收 |
| 输入 | 版本、提交、路径、目标实例等值从哪里取得，哪些需要本轮指定 |
| 执行步骤 | 顺序、命令、执行位置；自动完成的部分说明触发方式 |
| 通过条件 | 用什么输出或实际效果判断成功 |
| 失败处理 | 在哪里停止，保留什么证据，下一步查哪里 |

按任务复杂度合并以上内容，不必机械设置六个标题。纯规则、机制参考和验收记录按自身职责组织，不套操作模板。

例如，“推新 tag”可以写成：

> 前置：本机验收通过，记录对应待发布提交。版本取 package.json.version，tag 为 v<版本>。确认远端同名 tag 和 Release 不存在后推送，触发 release.yml；若同名版本已存在，停止并保留旧 tag 和附件。

具体执行仍遵守该任务的现行规则；例子不额外授予操作权限。

## 4. 事实和证据各有归属

- 每条规则、每段操作命令各有一个权威位置，其他文档链接引用。入口可概括任务，不复制整段流程。
- 配置值、版本和命令参数以配置、源码及脚本帮助为准。正文写清取值位置与约束关系；必须列出具体值时，写明适用版本或日期。
- 当前行为按源码和有效验证描述。未实现、未验证、历史通过分开标明，避免把计划写成现状。
- 验证方法说明如何复验；验收记录说明某次验证了什么。记录日期、提交或版本、实际产物或实例、证据位置和未验项，避免用历史结果证明本次产物。
- 长期指南只保留解决当前任务需要的历史原因。详细过程链接到对应记录。

## 5. 简洁、可读、可执行

- 先写用途和操作，再解释原因。使用短句、常用词和明确动词，减少长括号与口号式标题。
- 顺序操作用编号；目录、参数、版本和通过条件用表格；解释原因用短段落。选择方便阅读的形式，不为结构而增加层级。
- 同一对象使用一致名称。缩写、内部术语首次出现时按读者需要解释。
- 命令注明系统、终端和执行目录。占位符说明来源；路径安全引用，本机路径遵守 [开发规则](开发.md#2-本机路径)。
- 用可检查的条件替代“确认正常”“验证通过”等模糊说法。检查结果对应实际执行层次，如源码、构建产物、安装实例或真实页面效果。
- 常规步骤直接给出后续动作；需要判断时列出条件和分支，避免让读者或 agent 猜测目标、顺序或失败后的处理。

## 6. 修改与验收

重构前列出旧内容的去向：留在主文档、放入参考、链接到既有记录，或标为过时。正常内容编辑可以合并重复表述，仍须保留有效要求和关键例外。

修改后检查：

1. **入口可达**：新增或拆分的文档已接入 AGENTS.md 或对应任务入口，触发条件明确。
2. **步骤完整**：人和 agent 均能找到输入、执行顺序、通过条件与失败出口，无需猜测关键值。
3. **要求保留**：搬迁前后的有效规则、验收条件和异常分支均有去处。
4. **引用有效**：入站链接、文件路径、标题锚点与章节引用均已同步。
5. **事实准确**：命令和参数已对照现行脚本，当前行为与历史证据已区分；按改动运行适当检查。

已有文档在相关维护时逐步采用本标准，不要求一次改写全部文档。

本标准修订按本节五条检查项评审，合入后适用于后续相关变更。本轮回核受影响的直接引用与规则，其余存量文档在维护时逐步调整。
