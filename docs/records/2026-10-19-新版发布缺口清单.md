## 2. 双窗口问题已排除什么

已经保留原始失败，没有给失败页面补点。每轮用新页面和独立 profile，测试宿主正常 dispose。

| 变化 | 实测结果与含义 |
|---|---|
| 结果后再等三秒；去掉前置单窗口案例 | 仍失败；不能归为观察过早或必须有前置窗口残留 |
| 按下后只延迟 50ms；只关闭 backgroundThrottling | 仍失败；不能用固定按压延迟或该设置宣称修复 |
| 不更新按下/松开视觉效果 | 仍失败；不能据此认定原生效果层就是根因 |
| 额外监听页面事件；松开后同步一次 Runtime | 可通过，但改变了处理路径，不能替代原始页面验收 |
| 先移动鼠标；提前等双帧；两窗口串行或反向启动 | 可通过，说明准备/输入路由时序相关；还不足以证明当前产品已稳定 |

**根因仍未完全确认。** 双帧同步只是正在验证的候选，不将诊断脚本的通过率当产品成功率，也不把“回包成功”当“页面收到点击”。

## 3. 尚未覆盖的边界

这些条目继续公开保留。已有实现和单测不等于现场已验；条件触发的功能也不为清空清单而提前实施。

| 边界 | 仍缺什么 | 处理原则 |
|---|---|---|
| 故障竞争 | 真正断连重连、持续 wheel 无回包、弹窗登记期间 opener 关闭/租约换代、按下后接管等现场证据不完整 | 用户已要求不再追加负向验证，本轮不构造故障；明确标“未验”，不能标通过。将来触发真实故障时按矩阵保存输入终态、blocked 恢复依据和页面副作用 |
| 人工接管与输入方式 | 真实验证码、多因素登录、完整输入法 composition、触摸现场未覆盖 | 不声称全覆盖；按真实需求和现场条件补验。已派发 Chromium 输入不能承诺撤销 |
| 登录态 | 早期本地夹具证明的 localStorage/Cookie 生命周期，不能替代真实网站账号及最终安装升级 | 最终安装的数据保留归 G5；真实账号、验证码和多因素场景单列，不能用本地 Cookie 探针代替 |
| 多连接与多实例 | 单窗口两逻辑 CDP 通道已通过；宿主目前只接一条活动 TCP 桥接。不同概念不能混同；直接共享 app 目录未验收 | 维持实例独立数据与端点；不把第二条 TCP 连接、多实例输入并行或共享 app 宣称为已支持/已验收 |
| 外部 Chrome | 缺少 Electron 宿主的窗口输入权和人工前台隔离能力 | 保持既有回退及能力边界；扩展前先定义窗口权威和实际投递边界 |
| 交互诊断 | 空点、探测失败、运行中面板追加等仍按具体问题补实测 | 固定真实失败后再修；不是已确认全部存在的缺陷 |
| 模型与成本 | 模型只输出 reasoning、长文停在半途、审批无效 JSON/429 的失败已保留；新候选的大页面成本尚无普遍收益证据 | 分开统计工具错误、模型偏差、环境失败。既有 S15 同壳证据只适用于相应冻结场景；混用 U2 与官方模型的完成样本不做同模型成本 A/B |
| 后续优化 | 增量快照、spill/compaction 调整、进一步精简 schema/回执未统一启动 | 达到重复大区域、实际预算故障或明确前缀成本等原定条件再启动；保留启动条件，不记为本轮已实现 |

上表边界是否进入某次发布的必验范围，按实际改动、对外功能承诺及 [发版门禁](../agent-rules/验证与发版.md#4-发版门禁) 判断；未验证状态本身不被新版本号自动消除。
