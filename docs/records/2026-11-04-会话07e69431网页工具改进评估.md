## 1. 结论先行

这个会话是目前最接近 [观察优化方案 §5](../网页观察优化方案.md#5-第三阶段局部增量的启动条件) 所述「完整长回复 + 更长历史 + 必要大区域重复」启动条件的**自然任务样本**：同页十轮、每轮要求长回复、页面内容持续累积。但它同时证明，**主要弯路不是「必要区域太大」，而是「等待一律返回全页」加「完成条件用错」**，因此改进优先级不是直接做增量快照，而是先修等待/区域路径与完成语义。按收益从高到低：

## 3. 逐项分析

### 3.1 P0/P2：等待为什么一直全页

`webpage_wait` 的描述与 [快照与上下文 §2.3](../快照与上下文.md#23-连续对话等待与区域读取) 都写了「默认沿用本标签最近成功的 ref/区块观察」，源码 `src/browser-cdp/page-observation.ts` 也在 `previous === undefined` 时给出 `no_previous_region`。本会话 12 次全命中这个回退，原因是**前置条件在 fill→press→wait 循环里从未成立**：

- 唯一带 `observe:true` 的两次 click 在会话开头，分别因 `global_overlay` 和导航回退到全页，没有留下可继承的 ref/区块。
- 10 次 press 都不带附观察参数，不产生任何区域观察。
- 3 次 `region_viewport` 是 `scope=viewport`，不是可继承的 ref/区块；即便如此，随后的 wait（seq273、319）仍报 `no_previous_region`。

也就是说，[遗留问题](../遗留问题.md#2-需要补齐的运行证据) 里 2026-10-19 关闭的「wait 一律全页」只在**本地夹具的 click→wait 路径**上验过；这个自然任务没有点击产生的区域，机制整个空转。十轮累积的页面让每次全页回执线性变大，最后三次（seq 247/273/319）在 800 行处截断，分别有 100 / 202 / 335 条元素未返回，把**最新一轮回复挤到大纲之外**，模型不得不额外做 viewport 快照、加载 `webpage_scroll`、滚到底再拍一次（step 51–54）。

改进方向（按依赖顺序）：

- 让「本轮新回复」成为一等观察对象：wait 命中后默认返回**自上次观察以来新增/变化的内容区域**，而不是全页；或让 press 可选附观察并把结果区作为可继承区域。区域应锚在回复容器，不是输入框。
- 让 `region_viewport`、以及「动作后默认区块观察」的区块成为 wait 的合法继承源，并在 `scope_reason` 里区分「无前次区域」与「前次区域是 viewport/全页，不可继承」，避免把空转伪装成正常。
- 全页大纲截断时优先保留**尾部新内容**（或提供尾部预览，见 [快照与上下文 §2.3.1](../快照与上下文.md#231-find缓存与原文续读已实现未发布) 的首尾预览思路），否则「读当前回复」这个最常见的诉求反而被裁掉。
- 以上都先于增量：按 [方案 §5](../网页观察优化方案.md#5-第三阶段局部增量的启动条件) 与 §7.2 第四步，「若主要重复来自默认 wait 的全页观察，先评估等待成功后的区域观察，避免直接用全页 diff 解决范围错误」。本会话正是这种情形。

### 3.2 P1：完成条件不可靠

工具描述已写明 `until="stable"`「不证明回复完成」，[快照与上下文 §2.3](../快照与上下文.md#23-连续对话等待与区域读取) 要求「优先等待当前回复独有的完成标记」。本会话模型一次都没用 `wait_text`，全部用 stable，且把带 800 行截断标记的全页快照直接解读成「第 N 轮完成 ✅」。第 8/9/10 轮的模型文字甚至显式写「因内容较长快照被截断，但已生成完整回答」——这是从截断证据推断未观察到的内容，属于工具链没有提供可信完成信号时模型自行补洞。

改进方向：当本轮独有完成文本**事先未知**时（真实网页 AI 通常如此），提供「出现新的回复节点/新回复文本」这类结构化等待条件，或让 wait 回执明确区分「页面安静」「检测到新增回复」「无法确认回复完成」；回执不得让模型把「大纲截断」误读为「内容完整」。这与 [用户故事 S01](../用户故事与实测场景.md#s01--网页-ai-连续对话) 的「不能把上一轮已有文本当成新回答」是同一类要求，需要更长会话来验。

### 3.3 P3：回执样板字

一条成功 `webpage_fill` 回执首块 830 字符里，约 570 字符是带全部查询参数的 Google URL；其余是「Refs from the latest snapshot...」与不可信内容声明，宿主另附 150 字符的 `duration_ms` 块。fill/press 本身**不返回任何页面内容**，却重复携带面向快照的不可信内容声明。21 条首块合计 24,565 字符、全部 text 块合计 27,584 字符（两种口径见 §2）。这对应 [遗留问题 §3「继续精简 schema / 回执」](../遗留问题.md#3-后续功能)。

改进方向：非观察类回执只报「动作 + 目标 ref + 是否导航/纪元变化 + duration」；URL 缩为主域或省略；不可信内容声明只放在真正含页面内容的回执。先做字符守卫与单测，再做真实对话对照，不与 P0 的语义改动混在一批归因。

### 3.4 P4：参数与可见性摩擦（复发型）

**全会话共 4 次失败回执，逐次如下（按回执首句精确分类；正文里出现的 `BROWSER_STALE_REF` 提示语与 "before the timeout" 不是失败）：**

| # | seq | 工具 | 调用参数 | 错误 | 后续处置 / 结果 |
|---|---|---|---|---|---|
| 1 | 48 | `webpage_click` | `{ref:"e16", observe:true}` | `[BROWSER_TAB_NOT_VISIBLE]` 标签 `visibilityState=hidden`，`No input event was dispatched` | seq52 `webpage_tabs(activate)` → 仍失败（#2） |
| 2 | 58 | `webpage_click` | 同上（activate 后重试） | 同一 `[BROWSER_TAB_NOT_VISIBLE]` | seq62 用完全相同参数第三次 click → 成功，勾选框变 `checked=false` |
| 3 | 78 | `webpage_fill` | `{ref:"e67", value:"…", observe:"true"}` | `[BROWSER_INVALID_PARAMS]` 「未知字段 "observe"；允许字段：session_id, ref, value」，未派发任何浏览器操作 | seq82 去掉 `observe` 重新 fill → 成功 |
| 4 | 98 | `todo_write` | 每个 todo 多带 `status_detail:""` | `invalid arguments: "todos[N].status_detail" is not a declared property (additionalProperties: false)`，宿主参数校验，非网页工具 | seq103 去掉 `status_detail` → `Updated todo list` |

12 次 `webpage_wait` 的回执首句均为 `wait done` 且 `The awaited condition became true before the timeout`，**无超时失败**；整个会话只有 3 个 `turn/end`（turn 1、2、3），均为 `completed`。turn 2（「取消使用统计然后进行十轮AI对话测试」）模型判断指令模糊，只输出澄清问题、未调用任何工具，turn/end 仍为 `completed`，不算工具失败；turn 3 一个 turn 内完成十轮网页对话，模型逐轮自述「第 N 轮完成 ✅」，**这些自述与 3 个 `turn/end` 都不是十轮网页回答完整的证据**。即四次失败全部发生在「参数形状」和「窗口可见性」，没有页面侧错误、没有重复提交、没有被 `satisfied=false` 卡住的等待。

- `webpage_fill` 被传 `observe:"true"`（字符串且该工具无此字段）→ `BROWSER_INVALID_PARAMS`。这与 [方案 §7.1/§7.3](../网页观察优化方案.md#71-下一轮的明确顺序) 记录的布尔字符串、参数外推同类：模型会把「动作工具」的参数外推到「输入工具」。可考虑对明显错位的字段给出更具体的纠正（例如「`webpage_fill` 无 observe；要观察请在其后的 press/wait 上设置」），而不是只列允许字段。
- 首次点击连撞 2 次 `BROWSER_TAB_NOT_VISIBLE`，`webpage_tabs(activate)` 之后仍失败，第三次同样参数的 click 才成功。打包态 GUI 下窗口显示状态与 `visibilityState` 的恢复不可靠；[遗留问题 §2「故障竞争/人工接管」](../遗留问题.md#2-需要补齐的运行证据) 已有相关边界。改进方向是让 activate 真正保证窗口可见，或让回执给出可执行的恢复动作并避免模型用同一参数盲重试。
- `webpage_tools` 被传 `session_id`（已被容忍）这类外推未造成失败，说明容忍有效，可作为同类字段的处理样板。`todo_write` 的 `status_detail` 外推属于宿主侧同类问题，不在本插件网页工具范围内，但记录失败事实以保证「零错误门禁」口径完整。

### 3.5 P5：场景与增量门禁

本会话实际上就是 [S01](../用户故事与实测场景.md#s01--网页-ai-连续对话) 的加长版（3 轮 → 10 轮、短答 → 长回复）。建议在 S01 增加「十轮长回复」压力变体，固定提示、页面与模型，记录每轮 wait 回执体积、区域采用数、完成标记来源、截断与补拍次数、峰值/累计输入，以及宿主压缩时点。

对 [增量快照](../网页观察优化方案.md#5-第三阶段局部增量的启动条件)：这是首个「完整长回复 + 长历史」的自然样本，方向上支持重新评估 C，但**当前重复来自错误范围（全页）而非必要大区域**，不满足「B 稳定采用且任务全部正确后仍出现必要大区域重复」的门槛。先按 §7.2 第四步取得至少三次同模型、同任务、同范围的长会话样本，确认修完 P0/P2 后重复仍来自必要观察，再决定是否进入 C；不凭这一会话启动实现，也不因这一会话永久否定增量。

## 4. 限制

- 单会话、单模型（`workbuddy/hy3`）、单站点（Google AI Mode）、无冻结构建身份、无受控 A/B、无同条件重复样本。只能说明「发生过什么」，不能归因、不能宣称成本下降或稳定成功率改善。
- 统计口径：回执体积按 `tool/result` 每条**首个 text 块**计（本文主口径），宿主另附的 `duration_ms` 块会使全块合计更大，两种口径分别列、不混用；压缩 stub 不计入原始回执体积。**字符不是精确 token、字节或费用**，53,660 token 来自 `compaction/prune` 的 `shadowedTokenCount` 实测字段，不由字符换算。
- 整个会话只有 3 个 `turn/end`，十轮网页对话都在 turn 3 内；`turn/end=completed` 只证明对话结束，不证明十轮网页回答完整或逐轮等待条件成立。
- 不推翻 2026-10-18 收口的 S15 结论（累计 −8.62% / 峰值 −17.18%）：那是本地夹具、含点击、能拿到被操作元素所在区块的场景；本会话是流式 AI、无点击产生区域、用 stable 等待。两者场景不同，恰好说明关闭条件覆盖不到的路径。
- 不判定为回归：`wait` 复用区域的源码与作用域报告都在，属于**自然任务覆盖缺口 / 前置条件未满足**，不是功能缺失。
- 模型侧的「从截断大纲推断完整回答」是模型行为，与工具错误分开记；按 [测量口径](../上下文膨胀-测量口径.md) 的既有约定，不记成工具失败。
- 会话数据来自固定测试实例的 home，未核对当前工作区插件构建哈希；不据此判断当前源码或安装态。
