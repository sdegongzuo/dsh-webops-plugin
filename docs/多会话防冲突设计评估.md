## 2. 硬问题（按严重度）

### P0-1 · 「一个会话 = 一个标签页」—— 三层语义，初版结论过强（**已更正**）

「会话」在本仓库有三层含义，混用会得出相反结论：

| 层 | 指什么 | 与标签页的关系 | 依据 |
|---|---|---|---|
| ① 插件内部 | `sessionId`（= `targetId`） | **1:1** — 一个 sessionId 就是一个受控标签页 | `provider.ts:14`；`sessions: Map<targetId, SessionState>`；处处 `sessionId: session.targetId` |
| ② 上层调用方 | dsh 的 agent / 对话 | **1:N** — 可以 `webpage_open` 多次，同时持有多个 sessionId | `webpage_tabs list` 返回**全部**受控标签页，不按调用方分组 |
| ③ CDP client | 调试器连接 | agent 一条 + 人工 DevTools 一条 | `[V8][V30][V21]`；`state.ts:52` 的 `StateOwner = 'agent' \| 'human'` |

**初版错在哪**：只看了 ①（这部分是事实），就推出「多会话共享同一标签页无法发生」。
但设计文档说的「会话」是 ② —— `BrowserRuntime extends Service`（`browser/index.ts:93`）是**共享服务**，
`sessions` Map 是 provider 实例级的、**全局可见**，任何调用方拿到 sessionId 都能操作那个标签页。
→ **两个上层调用方共用同一个 sessionId 操作同一标签页，是可能的。**

**也要如实标出边界**：项目已建模的冲突方是 `StateOwner = 'agent' | 'human'`（`state.ts:52`），
即**「另一方」= 人工 DevTools，不是另一个 agent**。所以「多个 agent 会话争用同一标签页」
要么尚未发生、要么尚未建模 —— **这是需要向 dsh 侧确认的前提**：不能默认它存在，也不能默认它不存在。

### P0-2 · 锁键退化为 `X:X` —— 冗余，但**没有失效**（**已更正**）

初版写「两键永不相等 → 互斥永不触发」，**该推论错误**。
冲突不是「两个 sessionId 撞在一起」，而是「**两个调用方 + 同一个 sessionId**」；
此时两者算出的锁键都是 `T1:T1`，**相同** → 互斥**正常生效**。

所以正确的结论只有一条：

- 键里 `${sessionId}` 与 `${tabId}` **恒等**，写一半就够 → **冗余**，建议简化为二者之一；
- 功能**没有失效**，**不能据此砍掉 L1**（初版砍错了）。

设计 2.1 末尾那句「跨会话共享时锁键退化为纯 tabId」与背景并不矛盾 —— 是初版读错了它的语气。

**仍然成立的两条批评**（不因更正而失效）：

1. **Web Locks 用不上**：它是页面内同源 API，锁在浏览器里；本插件要跨的是**调用方**，
   锁必须落在 host 进程的 provider 上。
2. **TTL / 续约 / 崩溃检测的价值取决于调用方边界**：若多个调用方是**同进程内**的并发任务，
   `try/finally` + `AbortSignal` 足够，TTL 纯属过度设计；若调用方**可能跨进程**
   （外部 client 崩溃 ⇒ 僵尸锁真实存在），那 TTL 就有价值。
   **这一点设计没说明，实施前必须先确认调用方是否跨进程** —— 别凭猜测定 TTL。

### P0-3 · diff 不是「精度太低做不了」，是设计的匹配键选弱了（2026-09-18 实测）

#### 实测方法

无头 Chrome 153 + CDP，页面为 10 条搜索结果（30 个可操作元素 + 3 个控件）。
匹配键用**仓库真实实现**（`buildOutline` 出 `ancestorPath` + `computeSemanticKey`），
不是自造近似。脚本：`.probe-semkey.ts` / `.probe-diff.mjs` / `.probe-diff-page.html`（项目根，已 gitignore）。

| 场景 | backendNodeId | semanticKey | 两级并集 |
|---|---|---|---|
| S0 完全没变 | **100%** | 39% | 100% |
| S1 追加 1 条结果 | **100%** | 39% | 100% |
| S2 改一个按钮文本 | **100%** | 39% | 100% |
| S3 列表整体重建（`innerHTML` 重赋值） | **8%** | 42% | 42% |
| S5 整页 reload（跨文档） | **0%** | 36% | 36% |

`semanticKey` 一栏实测 39%，与 `docs/待办.md:382` 记的 ≈0.4 **互相印证** —— 探针口径可信。

#### 三条结论

1. **0.4 卡的是 semanticKey 这条路径，不是 diff。** 设计的 L3 写「按 semanticKey 查找命中 → 复用旧 ref」，
   于是 diff 被绑死在 39% 的天花板上。**换键就解决**：`backendNodeId` 在同文档内稳定且唯一
   （`revalidate` 的四道门 `provider.ts:1244-1299` 早已证明这一点，是真机验证过的原语），
   增量场景实测 **100%**，diff 能省 90%+。
   正确定位：`backendNodeId` 做主键，`semanticKey` 只做**重建时的兜底**（S3 从 8% 补到 42%）。

2. **真正让 diff 归零的是变化模式，不是精度。** S3（DOM 整体重建）下并集也只有 42% ——
   省不到 60%，还要全额付 diff 的认知成本，此时不如全量。
   真实 SPA 里 `innerHTML` 级重建很常见：无 key 的列表重渲染、虚拟滚动、分页整块替换、SSE 流式整块替换。
   **要不要做 diff，取决于你的目标页面是「增量更新」还是「重建式更新」**——这必须实测，不能靠设计文档里那句「省 97%」。

3. **新盲区（S4）：值变化检测不到。** 改输入框 `value` 后，`backendNodeId` 存活、`name` 也不变
   （input 的 AX name 来自 `aria-label`），diff 会报 `unchanged`；但 `snapshot.ts:339` 会把 `value="…"` /
   `checked` / `expanded` 印进**行文本**，模型看到的行明明变了。
   → `changed` 判定必须把 **value + reported properties** 算进去，只比 `name` 会漏。

#### 附：「semanticKey 精度」到底指什么

**不是哈希碰撞率**（djb2 32 位在这个规模下碰撞可忽略），而是
**「页面里有多少比例的元素，其 key 在全页唯一」**（单例元素数 / 总元素数）。实测现场：

```
可操作元素 33 个，唯一 key 13 个 → unique/total = 39.4%
撞车的 key：2 组，共 20 个元素
  ×10  role=button  name="翻译此页"      ancestorPath = "list>listitem"
  ×10  role=button  name="查看详细信息"   ancestorPath = "list>listitem"
```

根因：`listitem` **没有可访问名称**，祖先路径里只剩 `list>listitem`；
真正能区分的「结果标题 N」是它的**兄弟子树**，不在祖先链上（`待办.md:310` 已指出这一点）。

「提精度」就是往哈希输入里补区分信息，三条路各有代价：

| 做法 | 效果 | 代价 |
|---|---|---|
| 路径带 listitem 序号（`listitem[3]`） | 区分度拉满 | **列表中间插入一条 → 后面全部错位**，没变的元素被判成变了 |
| 路径带兄弟标题（`listitem[结果标题 3]`） | 区分度高 | 路径变长；标题一改 key 跟着变（但标题改了本就该算变） |
| 组内序号（`{role, name, nth}`，Camofox 方案） | 区分度拉满 | 同上，**插入即错位** |

⚠️ **序号类方案有反作用**：提高区分度的同时降低稳定性。实测 S1（追加一条结果）里
`backendNodeId` 是 100% 存活，而序号方案会让后半列表的 key 全体变化 —— 追求「精度」反而把
diff 的 unchanged 打下去。

⚠️ **更要紧的一点：低唯一率在本设计里是安全特性，不是缺陷。**
约束「唯一命中才复用、多命中发新号」正是靠它防止错配。若强行把唯一率提到 0.8+，
跨文档场景（reload 后）会有大量元素「看起来唯一命中」→ **错误复活旧 ref**（同名不同元素），
而 `revalidate` 的 `loaderId` 门（`provider.ts:1263`）恰恰是用来挡这个的。
所以「unique/total ≥ 0.8」当验收目标是危险的。

#### 对上一版的修正

初版写「diff 收益被 0.4 腰斩」——这句话**在设计的方案内成立**（它确实规定用 semanticKey 匹配），
但**不是 diff 的固有上限**。换 `backendNodeId` 做主键后，增量场景是 100%。
所以「先修 semanticKey 精度再谈 diff」这个排序**作废**，换成下面的 C。

### P1-1 · Web Locks API 用不上；TTL + 续约 + 崩溃检测是过度设计

- Web Locks 是**页面内同源** API，锁存在浏览器里，需要页面 JS 主动 `navigator.locks.request()`。
  本插件的锁要跨的是 **MCP 会话**，锁必须落在 host 进程（Node/Electron）—— 页面里的锁帮不上忙。
- 锁的持有者是**同进程内的异步调用**，不是可能崩溃的远端进程。进程崩了，标签页和 provider 一起没了，僵尸锁无从谈起。
- 于是「TTL 15s / 导航 60s / 每 TTL·⅓ 续约 / holderPid 存活检测 / stale-lease reaping」全部无的放矢。
  同进程内一个 `try/finally` + `AbortSignal`（`mutate` 已经带 signal）就够了。
- 附带成本：每把锁每 5s 一个定时器，长会话多标签就是定时器风暴。

### P1-2 · 整页版本号粒度错，且 hash 基准没定义

三个具体问题：

1. **hash 基准没说清**：本仓库的 outline 是**折叠后、按 maxLines/maxOutlineChars 截断**的（`snapshot.ts:616-660`）。
   若 hash 基于 `lines`，`max_lines` 一变版本号就变，`truncated` 状态也不稳定 —— 版本号会随调用参数抖动。
   必须明确为「基于 `rows`（全量可操作元素）」，而 `rows` 本身也受 `maxDepth` 影响。
2. **粒度太粗**：页面任一处变化（时钟 tick、轮播、SSE 流式输出、骨架屏替换）都让**整页**版本号 +1，
   于是「页面上别处动了一下」会让所有操作都撞 PAGE_CHANGED。
   本仓库的 `until:'stable'` 等待逻辑（`types.ts:271`）恰恰说明这类抖动是常态。
3. **有现成的更优解**：元素级校验 —— `(loaderId, backendNodeId, role, name)` 四元组。
   - 便宜：不用整树 hash，只读被操作的那个节点；
   - 精准：SPA 局部更新时，没被碰到的元素照旧可操作；
   - **语义已存在**：`revalidate` 的 `identity_mismatch` / `node_gone`（`types.ts:490-494`）就是这套判定，
     `locate` 也已经做「现算 + isConnected 守卫」。**复用它，不要新造一套版本号。**

### P1-3 · 增量 diff 与「折叠 / 截断」的口径会打架

本仓库已经踩过一次同类坑（2026-09-18 真机实测）：折叠标记行进了 `webpage_find` 的底稿，
变成「模型看不到、find 却报出来」的**幻影命中**，最终逼出 `unfoldedLines` 与 `FOLD_MARKER_PREFIX`。

diff 会再踩一次，而且是同源的：

- 模型看到的 `outline` 是**折叠后**的；diff 若基于 `rows`（全量），
  模型会看到「我视图里没有的 ref 被列为 unchanged」—— 同样是幻影。
- diff 的 `unchanged: ["r1","r2"]` **只给 ref 不给 role/name**。模型必须自己保留上一份全量视图才看得懂。
  但 MCP 工具从模型视角是 stateless 的，**上下文压缩 / 截断之后 diff 直接不可解**，
  而设计里唯一的逃生舱是「变化 >50% 自动全量」—— 模型自己发现看不懂时没有主动请求全量的路。

要做得有：① diff 口径与模型所见视图严格一致；② `full: true` 逃生舱；③ 导航 / 首次 / 距上次超 N 步强制全量。

### P2 · 重启恢复是伪问题（LRU 一条**已撤回**，见补记）

- **LRU**：初版判为伪问题（理由：`RefTarget` 只有数字与短串，没有元素引用可删），
  **该判断已失效** —— 实现在评估期间（21:22）由并行改动落地。见下方补记。
- **重启恢复**：`hydrate` 虽已实现，但 `SessionState` 是**内存态**（`sessions: Map`），
  provider 重启 = 标签页一起没了（或至少 session 全部重建）。「重启后旧 ref 复用 >80%」这条验收
  需要一个现在不存在的前提：**标签页活着而插件进程重启**。设计没说明这个场景从哪来。
  → 该判断**仍然成立**。

#### 补记：LRU 软淘汰已落地（2026-09-18 21:22，评估期间并行合入）

`refs.ts` 新增 `LIVE_BINDING_CAP = 2000`、`evicted: Map<ref, semanticKey>`、`lastSeen` 时钟：

- `trimLive()`（`refs.ts:378-397`）：live 超 2000 时按 `lastSeen` 淘汰最旧，把 `ref → semanticKey` 存进 `evicted`。
- `bindRow()`（`refs.ts:348-365`）：live 无命中、且 `evicted` 里该 key 唯一 → **同号复活**。
- **不变量守住了**：复用只在 semanticKey 唯一命中时发生；`mint()` 仍 `sequence += 1`，新号不复用旧号。
- **跨文档误复活风险已挡住**：`evicted.clear()` 在 `publish()`（`refs.ts:139`，换纪元）与
  `invalidate()`（`refs.ts:247`，导航 / 人工接管）都调用 —— 等价于「换文档即清空」，
  与 `revalidate` 的 `loaderId` 门达到同样效果。

**残留两个小问题（不阻塞，建议 follow-up）**

1. `evicted` **在单个纪元内无界**：区域快照反复 `adopt` 会让它持续增长，
   且 `exportBindings()`（`refs.ts:288`）把它一并持久化 → 长期会话下持久化体积无界。建议给 `evicted` 也设上限。
2. `trimLive()` 每淘汰一条就全表扫一次 `lastSeen`，淘汰 k 条是 O(k·n)。一次 `adopt` 大量新增时会抖动，
   建议换成最小堆或按时钟排序的队列。

## 3. 真正该做的（重排后）

### A. 【新，最该先做】同会话串行队列

**这是设计里唯一遗漏、但真实存在的并发源**：模型在一轮里可以并行发多个工具调用
（主流模型都支持 parallel tool calls），两个 `webpage_click` 打同一个 sessionId 会**真正交错**。

现状只有一句声明（`refs.ts:84`：「provider 内部对同一会话的操作是串行的」），
**代码里没有任何串行化机制** —— 没有队列、没有锁。声明不等于保护。

最坏情形：click A 触发导航 → epoch 推进 → click B 的 ref 已失效但 B 已经过了 resolve，
于是 B 打在旧 backendNodeId 上（导航后该 id 要么失效、要么指向新文档的同位置节点 —— 后者是静默错误）。

做法（便宜且可回退）：per-target 的 promise chain，`mutate`/`observe` 入口排队，
`AbortSignal` 照旧生效，异常不阻断队列。**不需要 TTL、不需要续约、不需要崩溃检测。**

### B. 【替代 L2】元素级 expected 校验

把 `expected_version` 换成 `expected: { loaderId?, backendNodeId?, role?, name? }`，
校验逻辑直接复用 `revalidate` 现成的身份比对；不匹配时错误码沿用既有失败原因
（`document_changed` / `node_gone` / `identity_mismatch`），不新造语义。

### C. 【推迟 L3】先测目标页面的变化模式，再谈 diff

> 取代初版的「先修 semanticKey 精度」——那条已作废，理由见本节末尾。

用 `.probe-diff-page.html` + `.probe-semkey.ts`（项目根，已 gitignore）对**真实目标页面**
连拍两次，测 `backendNodeId` 存活率。**≥ 80% 才做 diff**，否则不做（重建式页面做 diff 是负收益）。

**为什么取消「先提精度到 0.8」**：① 与 diff 无关 —— diff 用 `backendNodeId` 做主键就是 100%；
② 序号 / nth 类补法会让「列表中间插入一条」导致后面全体错位，**反而降低** unchanged；
③ 低唯一率是防错配的安全特性，强行提到 0.8 会让跨文档场景错误复活旧 ref（详见 P0-3 附）。

### D. 【若做 diff】先定口径

diff 与模型所见视图一致 + `full: true` + 强制全量的三种时机；
`changed` 计数要与 `droppedElements` / `foldedRepeats` / `truncatedByBudget` **分开报**
（本仓库已为「口径混报」付出过两次代价，见 `types.ts:383-386`）。

## 4. 建议顺序与验收

| 序 | 动作 | 验收（可量化） |
|---|---|---|
| 0 | 对齐 `待办.md` §7 与源码状态（Step 2/3 已落地） | 文档与 `refs.ts` 一致 |
| A | per-target 串行队列 | 并发 2×`webpage_click` 同一 session：不交错，第二个在第一个完成后执行 |
| B | 元素级 expected 校验 | 导航后拿旧 ref 操作 → 明确报错，绝不静默命中新文档节点 |
| C | **先测目标页面的变化模式**（增量 vs 重建） | 拿典型页面连拍两次，存活率 ≥80% 才值得做 diff |
| D | diff 实现：backendNodeId 主键 + semanticKey 兜底 + 值/属性纳入 changed + 重建检测 | 增量场景省 ≥90%；重建场景自动退化全量 |

「先提 semanticKey 精度到 0.8 再做 diff」（已证明与 diff 无关，见 P0-3）。

## 5. 更正：号空间不是问题，缺的是「调用方归属标记」

初版写「各 session 各自 `new RefRegistry()` ⇒ A 的 `e3` ≠ B 的 `e3`，号空间冲突没人管」。
**该担忧不成立**：两个调用方若是共享**同一个 sessionId**，它们操作的是**同一个 `SessionState`**
（`sessions: Map<targetId, SessionState>`），也就是**同一个 `RefRegistry`** —— 号空间天然共享。
各调用方各自 open 不同 sessionId 的情况则本就互不干扰（`provider.ts:362, 428` 的
`new RefRegistry()` 是**每个标签页一个**，不是每个调用方一个）。

**真正没被设计覆盖的是另一件事：provider 不知道请求来自哪个调用方。**

- 冲突发生时，无法回给模型「**谁**占着这个标签页」（设计 2.4 承诺要返回持有者标识 —— 现在没东西可填）；
- 也就无法做「只有持有者能续约 / 释放」「检测到持有者消失则回收租约」这类语义；
- 现在唯一带归属概念的是 `TargetStateRegistry`（`state.ts`），而它的 owner 只有
  `'agent' | 'human'`（`state.ts:52`）—— **没有「哪个 agent 调用方」这一维**。

→ 所以 L1 落地时，**第一件事是给请求加调用方标识**（类似 `state.ts` 的 owner，
  但取值是调用方 id 而非 agent/human），锁的持有者、冲突回执、续约/回收都靠它。
  这比锁本身的算法更重要，设计里完全没提。
