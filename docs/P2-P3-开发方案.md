# P2 / P3 开发方案（全部基于本机实测）

> 环境：Electron 44.0.0 / Chromium 152.0.7977.54 / Windows（U4 的对照在纯 Chrome 153.0.8010.36 上做）。
> 探针与原始日志在 `.workbuddy/tmp/`。**方案里每条设计决策后面标 `[V#]`，指向本文第 6 节的实测事实编号。**
> 第 7 节列出 U1–U5 的补测结果——**已全部完成**，其中两项推翻了初版方案的结论。

---

## 1. 结论摘要（四句话）

1. **不需要互斥锁**：人工开 DevTools 与 agent 的 debugger **可以共存**，agent 在 DevTools 打开后仍能把调试器接回去 `[V5]`，且 `devtools-opened` 回调里**同步** attach 就行、连延迟都不需要 `[V34]`；人工打断点也卡不住 agent 的命令 `[V2]`。
2. **要进簿记的是：`Emulation` 全类 + `Network` 的两个共享设置 + `Page.addScriptToEvaluateOnNewDocument` + `Page.bringToFront`**：`setDeviceMetricsOverride` / `setUserAgentOverride` `[V6][V9]`、`emulateNetworkConditions` `[V25]`、`setExtraHTTPHeaders` `[V26]`、`addScriptToEvaluateOnNewDocument` `[V35]`、`bringToFront` `[V21]`，实测全部跨 client 共享 / 后写赢。而 `Network.setBlockedURLs` `[V12]`、`Runtime.setAsyncCallStackDepth` `[V30]` 实测 session 私有，**不进簿记**；`Network.setCacheDisabled` `[V27]` 无法判定 → **`browser_execute` 直接拒掉**（见 3.3），也就不需要簿记。**作用域逐 domain 不同，绝不能类推——连"同一个域只有一种作用域"都不成立。**
3. **`clear*` 不能当还原手段** `[V10]`——但这是 **Electron 特有**：纯 Chrome 153 上 clear 会完全还原到真实视口 `[V29]`。约束照旧（Electron 才是实际运行环境），只是要清楚它的适用边界。
4. **`browser_execute` 是唯一需要能力边界的入口**（它能越出本会话边界），边界用**白名单**而不是拒绝列表——新命令默认拒，见 3.3。

## 2. 通用层（所有 P2/P3 工具共享）

### 2.1 新增可恢复错误码

| 错误码 | 触发条件 | 依据 |
|---|---|---|
| `BROWSER_DEBUGGER_DETACHED` | CDP 命令抛出 `Error: No target available` | `[V16]` |
| `BROWSER_STATE_CONTENDED` | 要向一个冲突的 target 级状态写入（判定条件与处置见 2.3.1，恢复路径见 2.1.1） | `[V6][V9]` |
| `BROWSER_EXECUTE_RESULT_UNSERIALIZABLE` | `browser_execute` 返回值无法序列化 | `[V22]` |

`[V16]` 实测：detach 期间 `dbg.sendCommand('Runtime.evaluate')` **同步抛 `Error: No target available`**，2.5s 超时保护未触发（说明是立即失败，**不会挂起**），且 3 秒后再发仍是同样错误。re-attach 后自动恢复 `[V16]`。
→ 所以映射成可恢复错误码是安全的，不需要"探测式重试"。

#### 2.1.1 `BROWSER_STATE_CONTENDED` 的恢复路径（**补，原方案缺失**）

原方案只写了"什么时候抛"，没写"抛了以后模型能干什么"——那等于一个死错误。补上：

| 模型可以做的事 | 语义 | 适用 |
|---|---|---|
| 重新 `browser_snapshot` / `browser_screenshot` | **首选**。接管期间页面已变，手上的 ref 本来就作废 | 恒可用 |
| 等接管结束再试 | 只在「确有人在操作」时成立；**无接管时的争用不会自己消失**，不能当默认重试策略 | 接管窗口内 |
| 显式覆盖（`force: true`） | 唯一被允许的"抢"的姿势——必须显式，绝不静默覆盖 | 恒可用 |

实现要求：
- 错误 payload 必须带 `stateKey` / `holder`（`'human'` / `'agent'`）/ `at`（毫秒时间戳），模型才知道**是谁、什么时候**占的；
- 错误码**不可重试**：同一命令原样重发必然再失败（状态没变），这一点要写进错误消息正文，否则模型会陷入重试循环；
- `force: true` 时把 `previous` 写进结果回执，让调用方知道覆盖掉了什么。

### 2.2 detach / re-attach 流程（P3 的核心，**替换 `6a0dc8b` 的让位设计**）

> **状态：已落地。** `host.cjs` 的 `toggleDevTools()` 已按本节时序改完，并新增 `devtools`
> op 让这条行为可被脚本触发；验证脚本 `pnpm run smoke:devtools` 跑通（DevTools 打开期间
> `provider.observe(snapshot)` 仍成功，13s 干净退出）。下面保留原始分析作为依据。

`host.cjs` 的 `toggleDevTools()` 原来是"detach 让位 → 等 `devtools-closed` 才接回"，等于人工看 DevTools 的全程 agent 都是瞎的。按实测可以改成：

```js
// 1) DevTools 打开前必须先 detach（否则静默失败）      [V3]
entry.debugger.detach()
wc.openDevTools({ mode: 'undocked' })

// 2) DevTools 打开后，target 不再排斥第二个 client，直接接回  [V5]
//    V5 实测：DevTools 已打开时 attach 成功，且 Runtime.evaluate 正常返回。
//    [V34] 实测：devtools-opened 回调内直接 attach 即可，连延迟都不需要。
//    ⚠ `reenableDomains` **目前在仓库里不存在**（当前落地只有 `attachDebugger`）。
//      它是 P2 采集器接入时才必须补的一步：re-attach 不保证之前 enable 过的
//      domain 还在，采集器必须在接回后重新 enable（见 3.1 的 enable 策略）。
wc.once('devtools-opened', () => { attachDebugger(entry); reenableDomains(entry) })

// 3) 兜底：DevTools 关闭后调一次 —— 实测这是 **no-op**，别当它有活干。
//    devtools-opened 时已经接回，attachDebugger 幂等直接 return；留着只是表达
//    「关掉 DevTools 之后一定还连着」这个不变量。
wc.on('devtools-closed', () => { attachDebugger(entry); reenableDomains(entry) })
```

**⚠ 过渡期的 `Inspector.detached` 语义（补，原方案只提了改注释）**

**前提已经变了**：工作区当前实现里，`entry.lettingGo` 状态位（`host.cjs:193`）会让 `openTab` 里的 detach 监听器**让路不发**，改由 `toggleDevTools` 补发一条 reason 更准的（`host.cjs:352`）。所以一次 toggle **只发一条**，`reason: 'devtools-opened'`；不置位时（页面真的没了）才走监听器那条，`reason: 'target closed'`（`[V23]`）。

但这条事件依然落在**毫秒级过渡**里——紧跟其后就是 `devtools-opened` → `attachDebugger()` 接回。所以约定一句话：**`Inspector.detached` 不等于会话失效**。

- **现状核对（重要，与检视意见的前提不同）**：父进程当前**根本不订阅**这条事件——全仓库只有 `scripts/smoke-devtools.ts` 订阅它做断言；而 `refs.invalidate()` 只在两处被调用：导航之后（`provider.ts:297`）与操作落地后地址变化（`provider.ts:844`），**都与 detach 无关**。所以"detach 会误推 ref 纪元"**目前是个不存在的风险**。真正要防的是 P3：接管语义一旦要接"观察失效"的信号，最容易顺手把这条事件拿来用——所以规矩先立在这里；
- **规矩**：收到 `Inspector.detached` **不得推进 ref 纪元**。判"真的没了"看 reason：`'devtools-opened'` = 我们自己的过渡；`'target closed'` / `'tab closed by the user'` 才是真断（`[V23]`）；
- **`lettingGo` 是宿主进程内的状态位，父进程看不到**——reason 是父进程唯一拿得到的区分信号。**待办**：把它写进 `host.cjs` 顶部的「子 → 父」协议清单。当前那份清单里**没有** `Inspector.detached` 这一项，`[V23]` 的语义只活在代码注释里；
- **P3 需要一个真正的失效信号**：既然这条事件不能当失效用，"人工接管期间的观察失效"眼下**没有任何通知通道**。别以为 2.2 已经把它解决了——这是 P3 要补的设计；
- 更干净的做法：把这条合成事件的 method 改成非 CDP 标准的名字（如 `dsh.devtoolsTransition`），从协议层面杜绝与真实 `Inspector.detached` 撞车；
- 另注：`attachDebugger` 的 doc comment 已记下「**re-attach 不保证 domain enable 状态还在**，P2 采集器接上时必须在 re-attach 后补 `Runtime.enable`」——这和 `[V13][V14]` 是同一件事，别漏。

**两个坑**：
- **必须先 detach 再 openDevTools**：`attach` 期间调 `openDevTools` 会**静默失败**——`isDevToolsOpened()` 返回 false，**不抛任何错** `[V3]`。绝不能靠 `try/catch` 判断成功，必须校验 `isDevToolsOpened()`。
- **`detach` 事件的 reason 恒为 `target closed`** `[V23]`——**主动 detach 也是这个 reason**，不能用它区分"人为让位"和"页面真的没了"。区分要靠自己维护的状态位（谁触发的 detach）。

### 2.3 target 级状态簿记（`Emulation` 全类 + `Network` 两个共享设置 + `Page.addScriptToEvaluateOnNewDocument` + `Page.bringToFront`）

```ts
targetState: Map<targetId, Map<StateKey, { owner: 'agent' | 'human'; at: number; applied: unknown; previous: unknown }>>
```
（`previous` = 我们写入前读到的值或"未知"，用于 `force` 覆盖后回执——字段名与规范文档第 3 节保持一致。）

**为什么要簿记的正是这几个**（全部实测，别类推）：

| 命令 | 实测作用域 | 证据 |
|---|---|---|
| `Emulation.setDeviceMetricsOverride` | **跨 client 覆盖、后写赢** | `[V9]` |
| `Emulation.setUserAgentOverride` | **跨 client 覆盖、后写赢** | `[V6]` |
| `Network.emulateNetworkConditions` | **跨 client 覆盖、后写赢**（A 置离线 → B 置 `offline:false` → A 恢复联网） | `[V25]` |
| `Network.setExtraHTTPHeaders` | **跨 client 覆盖、后写赢**（A 设 `x-probe:A` → B 设 `B` → A 读到 `B`） | `[V26]` |
| `Network.setBlockedURLs` | session 私有 | `[V12]` |
| `Runtime.setAsyncCallStackDepth` | session 私有 | `[V30]` |
| `Network.setCacheDisabled` | **无法判定**（本环境无观测面，见 `[V27]`）→ 不进簿记，**`browser_execute` 直接拒**（3.3） | `[V27][V28]` |
| `Page.addScriptToEvaluateOnNewDocument` | **跨 client 共享**：A 注册后，**由 B 触发的导航照样被注入**；但注册项随 A 的 session detach 而清除（旧 identifier 跨 session 报 `Script not found`） | `[V35]` |
| `Page.bringToFront` | **共享、最后调用者赢**（A、B 都能成功调用，无互斥）——它不是"锁"，是 target 级操作 | `[V21]` |

**⚠ 初版方案在这里是错的**：初版写「真正要治理的只有 `Emulation` 一类」，依据是 `Network.setBlockedURLs` 实测私有 `[V12]`。补测证明 **`Network` 域内三个设置的作用域并不一致**——`setBlockedURLs` 私有，而 `emulateNetworkConditions`、`setExtraHTTPHeaders` 共享。**同域内都不能类推。**

对 `setCacheDisabled`：因为无法判定，**按最坏假设处理**——`browser_execute` 直接拒掉（3.3），于是"不用它"和"免于簿记"同时成立。这也带来一条更保守的实现原则：**凡是写 target 级状态的新命令，落地前必须先按第 7 节的方法实测作用域，默认按"共享"处理。**

**⚠ 三条硬规则**：
1. 校验写入结果时**不能立即回读断言**：写入是异步可见的，设完立刻回读会读到旧值，约 170ms 后才正确 `[V7]`。要么延迟、要么重试。
2. **不要用 `clear*` 做还原** `[V10]`（详见 5.1）。
3. `Emulation.clearDeviceMetricsOverride` 是**弹自己那层**，动不了别人的覆盖 `[V11]`——所以并发写入时不会互相清掉，但也意味着**你不能靠 clear 收回别人的状态**。

#### 2.3.1 `owner: 'human'` 从哪来（**补，原方案的空白**）

原方案定义了 `owner: 'agent' | 'human'` 却没定义 `'human'` 怎么来。而 **CDP 不广播其它 client 的命令**——只有自己 enable 过的 domain 的事件才收得到，命令流完全不可见（`[V8][V30]`）。真人在 DevTools 里设了 UA override，agent 那边一声不响，`owner` 永远停在 `'agent'`，于是 `BROWSER_STATE_CONTENDED` 对 `human` **永不触发**。

**判定来源（按优先级）**：

| 来源 | 规则 | 适用范围 |
|---|---|---|
| ① 粗粒度让渡 | P3 接管语义激活期间（agent 停止操作、进入人工窗口），该 target 的 target 级状态**整体视为 `human` 所有** | 全部 key。**这是主力手段**——观测不到对方命令，只能粗粒度让 |
| ② 延迟回读探测 | 写入后**延迟 ≥170ms**（即硬规则 1 的可见延迟）再回读；读回值 ≠ 本次写入 → 判定被外部改写，`owner` 置 `human`，`applied` 更新为读回值 | **只对"有读取面"的 key 成立**：`Emulation.setDeviceMetricsOverride`（读 `innerWidth`/`dpr`）、`setUserAgentOverride`（读 `navigator.userAgent`）。而 `Network.emulateNetworkConditions` / `setExtraHTTPHeaders` **没有 get 命令**——`[V25][V26]` 里的"读到"是**页面行为侧的回显**（请求失败 / 服务端回显 header），不是 CDP 能读的。这两条只能靠 ① |

**⚠ 别写成「未观察过的 key 默认 `human`，据此阻断写入」**——那样 agent 第一次设置任何状态都会被判成争用，寸步难行。`targetState` 记的是 **agent 自己的写入**，冲突判定条件应当是：

| 情形 | 处置 |
|---|---|
| `owner === 'agent'` 且探测到值被外部改写 | 抛 `BROWSER_STATE_CONTENDED`（有人从背后把我们设的东西改了） |
| 处于接管窗口内 | 抛（整体让渡，见 ①） |
| **从没被 agent 写过** | **允许写**，但回执须标注"此前该状态来源未知，可能来自人工"，并把读到的旧值留在 `previous` 里以便恢复 |

"未知归属按人工所有"这条保守原则只体现在**语义与展示**上（别声称这状态是我们设的），**不体现在阻断写入上**。

## 3. P2 工具

### 3.1 `browser_console`（console 采集）

| 项 | 决定 | 依据 |
|---|---|---|
| 事件源 | `Runtime.consoleAPICalled` + `Log.entryAdded` | — |
| enable 策略 | **每次 attach 后重新 `Runtime.enable` + `Log.enable`**——**两个域都会重放**（原方案标"`Log` 未测"，已实测） | `[V13][V14]` `[V37]` |
| 去重键 | **按域分桶的高水位时间戳**：`Runtime` 用 `(executionContextId, type)`、`Log` **只能**用 `(source)`（它没有 `executionContextId`）——**不能共用一个三元组** | `[V17]` `[V37]` |
| 本地缓冲 | **≥ 1000 条**——这是**窗口一致性**要求，不是去重前提（见 3.1.1）。两域的重放上限实测**都是 1000** | `[V24]` `[V39]` |
| 超限信号 | `Log` 域超限时会**显式发一条截断提示条目**，要当信号用、不能被去重吃掉 | `[V39]` |
| 禁用 | 不做 `Runtime.disable` / `Log.disable`（会影响他人） | 推论 |

`[V14]` 实测：detach 期间由页面自己产生的 console（`webContents.executeJavaScript` 打的一条，完全绕开 CDP），re-attach + `Runtime.enable` 后**照样能收到**。
→ 这是好消息：**人工接管窗口不会漏消息**。

**但必须去重**：`[V13]` 实测三次 attach/enable 收到 `M1M2` → `M1M2M3` → `M1M2M3M4`，每次 enable 都会把历史**全量重放**一遍。`Runtime` 侧的去重键可以用 `executionContextId` + `timestamp`——`[V17]` 实测这两个字段都在，且 timestamp 精度到微秒（`1789282776445.069`、`1789282776445.167`、`1789282776445.198`，三条各异）。**但这套键只对 `Runtime` 成立**，`Log` 域见下。

**⚠ 重放不是无限的**：`[V24]` 实测产生 1500 条后 detach → re-enable，**实时收到 1500/1500，重放只回 1000 条**。所以：
- 不能只依赖重放兜底——实时采集必须自己落缓冲；
- 人工接管期间若产生超过 1000 条 console，早期那些会**永久丢失**，错误提示里要说清。

**`Log.entryAdded` 也会重放，但字段口径与 `Runtime` 不同**（`[V37]` 实测，原方案标"未测"）：

| 维度 | `Runtime.consoleAPICalled` | `Log.entryAdded` |
|---|---|---|
| 会不会重放 | 会（`[V13][V14]`） | **会**，且**覆盖 detach 窗口**——detach 期间产生的条目，re-enable 后照样补到 |
| `timestamp` 类型 | 微秒精度（`[V17]`） | **number**（毫秒带亚毫秒小数，实测 `1789289442861.96`） |
| `executionContextId` | **有** | **没有**——字段根本不存在（实测 `false`） |
| 可分桶的维度 | `executionContextId` + `type` | 只剩 `source`（实测取值 `javascript` / `network` / `other`） |

→ **去重键必须按域设计**。`(executionContextId, source, timestamp)` 这个三元组对 `Log` 域**根本不成立**（`executionContextId` 缺席）；两域的时间戳类型也不同，跨域比大小是错的。

**`Log` 的重放上限也是 1000 条，但它比 `Runtime` 多一个可用信号**（`[V39]` 实测）：

产生 3000 条 Log 后 detach → re-enable，**只回 1000 条**（与 `[V24]` 的 Runtime 同口径）；同时**多发一条截断提示条目**，形如 `{ source: 'other', text: '2010 log entries are not shown.', timestamp: 0 }`——待重放 3010 条 − 上限 1000 条 = 2010，提示里的数字**精确对上**。

→ **这条提示必须特判放行、不能被高水位时间戳吃掉**：它的 `timestamp` 恒为 **0**，任何高水位都会把它当"旧消息"丢掉，而它是"这里有内容缺失"的**唯一信号**。`Runtime` 没有等价提示——它的截断是**无声**的。

#### 3.1.1 去重与环形缓冲：两条不同的推理链，别混着推（**补**）

原方案只写了"至少 1000 条环形缓冲"，没说清 1000 这个数从哪来、它到底约束的是什么。**这里其实有两条独立推理链，混起来会得出错结论**：

| 路径 | 去重靠什么 | `RING_CAPACITY` 的角色 |
|---|---|---|
| （甲）seen-set / 扫缓冲查重 | 缓冲里有没有这条 | **硬约束**：容量必须 ≥ 重放窗口（1000，`[V24][V39]` 两域同口径），否则重放回来的旧消息在缓冲里查不到、被当新消息重复入账 |
| （乙）**按域分桶**的高水位时间戳 | 每个桶一个标量（该流已处理到的最大 timestamp） | **与去重无关**——高水位独立于缓冲存活，重放回来的消息时间戳必然旧于高水位，一律被丢。**例外：截断提示条目 `timestamp=0`**（`[V39]`） |

**本方案选（乙）**。所以 `RING_CAPACITY >= 1000` **不是去重的正确性前提**，而是**窗口一致性**要求：实时采集能留存的历史，不应短于 re-attach 能补齐的量（1000 条，`[V24][V39]` 两域同口径），否则补齐时反而要丢掉大部分重放消息、兜底白做。两条路径给出同一个下界，但**理由不同**——注释里要写清是哪一条，别留下"因为要去重所以要 1000"这种似是而非的话。

**（乙）的实现要点**：
- 重放是**按序**的（`[V13]`：`M1M2` → `M1M2M3` → `M1M2M3M4`），所以只需记住"该流已处理到的最新 timestamp"，比它旧的一律丢；
- 内存 O(上下文数) 而非 O(消息数)，长时间运行不涨；
- **分桶维度两域不同，不能共用一套 key**（`[V37]` 实测）：`Runtime.consoleAPICalled` 有 `executionContextId` → 桶键用 `('rt', contextId, type)`；`Log.entryAdded` **没有** `executionContextId` → 只能用 `('log', source)`（`source` 实测取 `javascript` / `network` / `other`）。原方案写的单个三元组 `(executionContextId, source, timestamp)` 对 `Log` 域**不成立**；
- **`timestamp <= 0` 的条目绕过高水位**：`Log` 域的截断提示条目 `timestamp` 恒为 **0**（`[V39]`），高水位会把它当旧消息丢掉——而它是"内容被截断"的唯一信号，必须特判放行；
- 副作用要认：**同一桶内**、时间戳完全相同（或早于高水位）的消息会被丢掉一条。两域的实测时间戳精度都在亚毫秒级（`[V17]` 的 `Runtime`、`[V37]` 的 `Log`），同桶撞车概率低，可接受——但要在注释里写明，别让人以为是 bug。

### 3.2 `browser_network`（network 采集）

| 项 | 决定 | 依据 |
|---|---|---|
| 采集方式 | 只用 `Network.enable` 读事件 | `[V8][V12]` |
| 重放兜底 | **已实测**：`Network` **不做历史重放**——detach 窗口内**已完成**的请求永久丢失；但**进行中**的请求，re-enable 后仍能收到后续事件，其中 **detach 期间发起**的那些**缺 `requestWillBeSent`** → 会产出"有响应、没请求头"的半截记录，必须显式处理（见 3.2.1） | `[V38][V40]` |
| `requestId` | **不需要任何映射**，直接用 | `[V18]` |
| `getResponseBody` | 直接用收到的 `requestId` 调 | `[V18]` |
| 禁止 | **不得使用 `Fetch.enable`** 做请求拦截 | 推论 |
| 禁止 | 采集期间**不要顺手调** `Network.emulateNetworkConditions` / `setExtraHTTPHeaders` | `[V25][V26]` 实测二者跨 client 覆盖，会污染人工的会话 |

`[V18]` 实测：A（Electron debugger）与 B（外部 client）收到的是**完全相同的 `requestId`**（`37668.2`、`37668.3`），且 A 用这个 id 调 `Network.getResponseBody` **成功拿到响应体**（`bodyLength=4`，"pong"）。
→ 这条省掉了原本以为要做的"per-session requestId 映射表"。

#### 3.2.1 跨 detach 的网络事件：不是"全丢"，是"半截"（**补，原方案只写了"按会丢准备"**）

`[V38][V40]` 实测下来，"会丢"这个说法**既过宽也过窄**——四种情形要分开看：

| 情形 | `requestWillBeSent` | 响应侧事件（`responseReceived` / `dataReceived` / `loadingFinished`） |
|---|---|---|
| 发起与完成**都在 attach 期间** | ✅ | ✅ |
| attach 期发起，**detach 期间完成** | ✅ | ❌ **永久丢失**——`Network` 无重放（`[V38]`） |
| attach 期发起，**re-attach 之后才完成** | ✅ | ✅ **完整补上**（实测四条齐：`responseReceivedExtraInfo` → `responseReceived` → `dataReceived` → `loadingFinished`） |
| **detach 期间发起**，re-attach 后完成 | ❌ **不补发** | ✅ 收到（`responseReceived` / `dataReceived` / `loadingFinished`）——**但缺请求头** |

**最后一行是要害**：`requestWillBeSent` 带着 method / URL / 请求头 / postData，是**建档的唯一来源**；它缺席之后，那几个响应事件就是**无头孤儿**。而"只在 `requestWillBeSent` 时建 entry、后续事件按 `requestId` 更新"恰恰是最自然的写法——那样这批事件会被**静默丢弃**。

→ 实现要求：
1. 收到**找不到对应 entry** 的 `responseReceived` 时**不要直接丢**：建一条降级 entry，标 `partial: true` + `reason: 'request-headers-missing'`；URL 可以从 `response.url` 取（实测有值），但 method / 请求头 / postData **明确标为未知**；
2. 与"detach 期间已完成的请求"区分开：那一档是真丢（`[V38]`），属于**已知且接受**的能力边界，统计里要如实反映，别假装没发生过；
3. 回归用例见 8-3，必须覆盖上表第三、四两档——它们才是"不漏也不重"这个说法真正的边界。

### 3.3 `browser_execute`（唯一高危入口）

**能力边界（设计规则，非 CDP 限制）：改成白名单制**（修订：原方案是黑名单，与自身哲学冲突）

原方案用"拒绝列表"，理由写的是"新命令会不断加入"。这个理由恰恰是反的：命令不断加入意味着**黑名单永远追不上**——任何没被列出的新命令默认都是**放行**的。而 7.2 立的规矩是"新命令默认按共享处理"，3.2 又要求"采集期间不得调 `Network.emulateNetworkConditions`"。一个默认放行的黑名单，和一个处处保守的哲学，放在一起自相矛盾。改成默认拒：

| 层 | 规则 |
|---|---|
| 默认 | **拒绝**。不在允许列表里的 `domain.method` 一律 `BROWSER_EXECUTE_NOT_ALLOWED`，错误消息里带上被拒的 method 全文 |
| 允许列表（只读 / session 私有 / 只导航） | `Runtime.evaluate`、`Runtime.getProperties`、`DOM.getDocument`、`DOM.querySelector`、`Page.navigate`、`Page.reload`、`Page.captureScreenshot`、`Accessibility.getFullAXTree`、`Network.enable`、`Network.getResponseBody`、`Log.enable` |
| 白名单内**若将来出现写 target 级状态的命令** | 必须走 `targetState`（见 2.3 的表）。**当前允许列表里没有这类命令**——写状态的全在下面的"必须拒绝"里，所以这条目前是前瞻约束，不是有例可依的现行规则 |

**必须拒绝的（无论允许列表怎么长）**：

- `Target.*` —— `Target.attachToTarget` 可拿到**其它标签页**的 session，越出本会话边界
- `Browser.*` —— `Browser.close` 关掉整个浏览器
- `Emulation.*` / `Fetch.*` —— 跨 client 污染 `[V6][V9]`（`Fetch.enable` 还能拦截、改写请求）
- `Overlay.*` —— 注意**理由不是"跨 client"**：`[V31]` 实测高亮多 client 各自独立、互不取消。拒它是因为它是**给眼睛看的副作用**——会污染截图、干扰人工在 DevTools Elements 里的高亮，而 `highlightRect` 的 `color` 还会把整个视口染色 `[V32]`。agent 的高亮走 `browser_locate`（4.3）这条受控通道，不开放任意 `Overlay.*`
- `Input.*` —— 绕过 P1 的 `BROWSER_TOOL_CAPABILITIES` 分级，架空 `read`/`mutate` 判定
- **`Network.emulateNetworkConditions` / `Network.setExtraHTTPHeaders`** —— `[V25][V26]` 实测**跨 client 覆盖、后写赢**，必须进簿记；**原方案漏了**（黑名单只写了 `Emulation.*`，整个 `Network.*` 域没拦，等于开了个绕过簿记直接污染人工会话的后门）
- **`Network.setCacheDisabled`** —— `[V27]` 作用域无法判定，方案自己说"按最坏假设处理"，那就必须拒
- **`Page.addScriptToEvaluateOnNewDocument` / `Page.removeScriptToEvaluateOnNewDocument`** —— `[V35]` 实测**跨 client 共享**：A 注册后**由 B 触发的导航照样被注入**。性质与 `[V25]` 同族（写 target 级行为状态），而且更隐蔽——副作用要到"下一次导航"才显形，事后无法察觉。
  - 对 `browser_execute`：**拒绝**。这条逃生舱不该提供"往所有 client 的页面里塞脚本"的能力。
  - 对 2.3 簿记：**预先登记**，不是"拒了还记账"。被拒即没有调用路径；记账只在将来真有工具（如 `browser_inject_script`）用它时才生效。到那时的 key 要用稳定标识（如 `<worldName>:<按注册顺序>`），因为 identifier 只保证 session 内有效。
- `Page.setBypassCSP`、`Debugger.*`、`Security.*` 等其它写状态 / 改行为的命令 —— 按 7.2 先实测，**默认先拒**

**返回值处理（三种失败形态，全部实测）** `[V22]`：

| 表达式 | 结果 |
|---|---|
| `document.body` + `returnByValue` | **静默返回 `{}`** —— 不报错，最危险 |
| 循环引用对象 | 抛 `Object reference chain is too long` |
| `window` | 抛 `Object reference chain is too long` |
| `Symbol('s')` | 抛 `Object couldn't be returned by value` |
| `new Array(100000).fill(1).length` | 正常返回 `100000` |

→ 实现要点：
1. 强制 `returnByValue: true`；
2. **不能只判断 `result.value === undefined`**——DOM 节点那种情况 `value` 是个 `{}`，看着"有值"其实是垃圾。要**同时检查 `result.type` / `result.subtype`**，`object` 且无有效内容时按不可序列化处理；
3. 把上面两个错误消息映射成 `BROWSER_EXECUTE_RESULT_UNSERIALIZABLE`，并在提示里告诉模型"返回原始值或 JSON 字符串"；
4. 自己实现超时——`[V2]` 证明页面被断点暂停时命令仍能正常返回，但挂起风险不能因此排除。

### 3.4 上下文预算：三道闸门，以及**两类截断不能给同一条建议**（**补，2026-09-17**）

读型工具（`browser_console` / `browser_network`）返回的是**页面产生的、模型无法预期的**文本，条数上限挡不住总量。所以有三道闸门，缺一不可：

| 闸门 | 管什么 | console | network |
|---|---|---|---|
| 条数 `limit` | 条数 | 默认 50，上限 `MAX_P2_LIMIT = 150` | 同左 |
| 单条裁剪 | 单条最长 | `CONSOLE_TEXT_MAX_CHARS = 2000` | list 的 URL **不截**（截了会误导，URL 是要给模型复制出去用的）；body 文本 20000 / **base64 只有 2000** |
| 总量预算 | 一次返回的总字符 | `CONSOLE_RESULT_MAX_CHARS = 40000` | `NETWORK_LIST_MAX_CHARS = 40000` |

**条数上限必须配总量闸门**：单条 2000 字符 × `limit` 500 = 100 万字符 ≈ 28 万 token，一次调用就能把上下文吃光。现实里 `console.log(JSON.stringify(大对象))` 顶到单条上限的条目很常见，`data:` URI 做 URL 也能有几百 KB。

**base64 body 单独压到 2000**：它编码的是图片 / 字体 / wasm，模型既解不出来也读不懂，2 万字符只是 5.7k token 的纯噪声。留一小段只为看出格式，真要看图走 `browser_screenshot`。

**两类截断要分开报**（`truncatedByBudget` / `truncated`），因为「怎么拿到更多」的答案不同：

| 实际原因 | 正确的建议 | 错误的建议 |
|---|---|---|
| 条数到了 | 调大 `limit` | —— |
| 总量到了 | 用 `level` / `text` / `url` **过滤** | ❌「调大 limit」 |

给错建议比不给更糟：模型会照着调大 `limit`、拿到同样的结果、再试一次。所以**工具层的措辞由这两个标志决定**，不是由「结果被截断了」这一个事实决定。

两个实现细节：

- **第一条永远返回**，否则模型连「有什么可过滤的」都不知道；
- 闸门在 push **之前**判 `>=`，所以放行条数 = `ceil(预算 / 单条长度)` —— 测试按这个式子算期望值，别写死常数。

### 4.1 人工接管 / 回收

**语义 = agent 停止操作 + 重新观察，不是断开连接** `[V5]`。
三件事：① 通知（观察失效）② 归属簿记 ③ 前台协商。

**前台协商**：`Page.bringToFront` 实测 **A、B 双方都能成功调用**，没有互斥 `[V21]`。所以它不是"锁"，是"最后调用者赢"的 target 级操作，**已列进 2.3 的表**。注意它是一条**动作**而不是持久状态：簿记在这里只解决"知道谁最后把窗口抢到前台"，别指望它能阻止对方再抢一次。

#### 4.1.1 「观察失效」的通知通道（**补：2.2 排除了 `Inspector.detached`，这里给出替代**）

**问题**：2.2 的结论是 `Inspector.detached` **不能**当失效信号（它只标记"让位那一瞬"，且立刻 re-attach）。但 P3 的第①件事恰恰是"通知观察失效"——于是现状是**一条通道都没有**：人工用菜单或 `Ctrl+Shift+I` 打开 DevTools 时，agent 侧完全不知情。

**为什么也不能靠 `toggleDevTools()` 的返回值**：它只覆盖"agent 自己触发的 toggle"（`host.cjs` 的 `devtools` op）。人工走**菜单 / 快捷键**时不经任何 op，返回值这条路拿不到。

**设计**：宿主新增一条**独立的编排消息**，不进 CDP 事件流：

```js
// 子 → 父（新增）
{ type: 'takeover', tabId, active: true | false }
```

- **触发点**：`host.cjs` 里 `view.webContents.on('devtools-opened')` / `('devtools-closed')`。这两个事件对"agent 触发"和"人工触发"一视同仁，正好补上缺口；
- **为什么不写成 `{ type: 'event', method: 'dsh.takeover' }`**：那条通道的职责是搬运 CDP（`socket.ts` → `CdpConnection`），混进私有 method 会让"这哪来的 CDP 事件"变成下一个人要查的问题，而且它本就不在 CDP 协议里；
- **父进程侧改动**：`TabHostChannel` 加 `onTakeover(listener)`（与现有 `onEvent` / `onClose` 并列），`Bridge.dispatch` 加一个 `type === 'takeover'` 分支；
- **provider 侧**：`session.takeover: boolean` 状态位。

**语义（关键：接管 ≠ 作废）**：

| 用途 | 做法 |
|---|---|
| 通知模型 | `browser_snapshot` 结果里带 `takeover: true` + "人工正在操作，本结果可能随时失效"；`browser_locate` / `browser_screenshot` 照常可用 |
| 2.3.1 的来源①（粗粒度让渡） | 直接读这个标志 |
| **ref 纪元** | **不动**。推了就等于每次人工开关 DevTools 都把模型的 ref 全废掉；而实测 `[V31]` 连高亮都是互不干扰的 |
| 恢复 | 人工关掉 DevTools → `active: false` → 提示消失；模型想确认现状就重新 snapshot |

**重复触发不用去重**：agent 自己调 `toggleDevTools()` 时同样会收到这条事件——`active` 是幂等的状态位，不是计数器。

### 4.2 `browser_find`

**零状态**。在已经拿到的 snapshot 结果上做本地文本检索，不产生任何 CDP 命令。无归属问题。

### 4.3 `browser_locate`

**决定：不要用 `DOM` 的 nodeId 做定位。**

`[V19]` 实测（同一次 attach 内，同一个 `#box` 元素）：

| 调用 | 得到的 nodeId |
|---|---|
| 第 1 次 `DOM.getDocument{depth:2}` + `querySelector('#box')` | **6** |
| 第 2 次 `DOM.getDocument{depth:2}` + `querySelector('#box')` | **13** |

**同一个 session、同一个元素，重复 `getDocument` 后 nodeId 就变了。** 而且 A 和 B 两个 session 各自从 `root=1, box=6` 开始编号 `[V19]`——编号空间是独立的。

→ 结论：nodeId **既不稳定也不跨 session 通用**，绝不能进 ref 缓存。

**实现路线：`backendNodeId` → `DOM.resolveNode` → `Runtime.callFunctionOn` 现算 rect**——不依赖 `DOM.enable`（`[V36]` 实测），也不用 nodeId：

**正确的替代是 `backendNodeId`，不是 selector**（`[V36]` 实测）

`RefTarget` 里**已经有一个稳定句柄**：`backendNodeId`（`refs.ts:24-32`，注释写明它是"跨导航稳定 id"）。实测：

| 事实 | 结果 |
|---|---|
| 连续三次 `DOM.getDocument` 后同一个 `#box` 的 nodeId | **6 → 15 → 24**（每次都变，与 `[V19]` 一致） |
| 同一序列里它的 `backendNodeId` | **恒为 6** |
| `DOM.resolveNode({ backendNodeId })`——**全程没调 `DOM.enable`** | 成功，拿到 `objectId` |
| `Runtime.callFunctionOn(objectId, () => getBoundingClientRect())` | `{x:8, y:8, w:100, h:50}` |

→ 定位链路：`refs.resolve(ref)` → `backendNodeId` → `DOM.resolveNode` → `Runtime.callFunctionOn` 取 rect。**这条路仓库里已经在跑**（截图裁剪 `provider.ts:512-523`、`elementViewportBox` `:582-600`）。**不需要给 `RefTarget` 加字段，也不需要引入 selector。**

**为什么不走 `document.querySelector(selector)`**：
- AX 树里出来的元素未必有唯一 selector（无 id/class 的容器、重名标签）；
- iframe / shadow DOM 里 `document.querySelector` 直接落空；
- 最要命的是**它会静默命中重构后的另一个元素**——而 `backendNodeId` 直接指向节点，没有"匹配错"这种失败模式。

（注：`DOM.querySelector` 仍在 `browser_execute` 的白名单里（3.3），那是给逃生舱用的**只读查询**，与内部定位实现选哪条路无关。）

**但 `resolveNode` 成功 ≠ 元素还在文档里**——这正是下一节要补的守卫。

**若确实要高亮**（两条件必须同时满足，实测报错信息为证）：
- 本 session 必须先 `DOM.enable`，否则 `Overlay.enable` 直接报 `DOM should be enabled first` `[V15]`
- 本 session 必须先 `Overlay.enable`，否则 `Overlay.highlightNode` 报 `-32600 Overlay must be enabled before a tool can use it` `[V20]`

**高亮一律用 `highlightNode`，不要用 `highlightRect`** `[V32]`：

| API | 实测表现 |
|---|---|
| `Overlay.highlightNode` + `highlightConfig` | 精确覆盖目标元素（红像素 719900 ≈ `#box` 的 1200×600 设备像素），**其他区域完全不动** |
| `Overlay.highlightRect` + `color` | 传入 rect 内深色填充，**rect 之外整个视口被染成浅色**（红像素 2073396 ≈ 视口面积的 82%）→ 严重视觉污染 |

**高亮不是单例，多 client 可共存** `[V31]`——这条**推翻**了初版"高亮是单例、会与人工 DevTools Elements 面板互相取消"的假设：

| 阶段 | 红像素（A 高亮 `#box`） | 蓝像素（B 高亮 `#box2`） |
|---|---|---|
| 基线 | 212 | 218 |
| 只有 B 高亮 | 94 | **239971**（≈ `#box2` 全部 240,000 设备像素） |
| A 也高亮 | **719900**（≈ `#box` 全部 720,000） | **239874**（几乎不变） |
| A 执行 `hideHighlight` 后 | 94 | **239971**（完全恢复） |

→ 人工在 DevTools 里选元素与 agent 的 `browser_locate` 高亮**互不干扰，无需协商、无需让位**。

### 4.4 观察失效（`stale_ref` 从被动升级为主动）

`refs.resolve()` 前做一次轻量指纹比对：

```ts
fingerprint = { href: location.href, origin: performance.timeOrigin }
```

不一致 → 推进 ref 纪元 → 报 `BROWSER_STALE_REF`。
（沿用既有的轮询风格——`provider.ts:982` 已论证过纯事件方案的两个坑：事件可能早于 `Page.enable`、SPA 软导航不发 `loadEventFired`。）

**⚠ 这是启发式，不是完备判定（补）**：`href` 不变、`performance.timeOrigin` 不变的 SPA 内部重渲染（列表刷新、路由换了但地址没换、组件整块重挂）**指纹抓不住**，ref 会指向旧元素而不报错。所以要写进注释：

- 指纹的职责是"**尽量早地**发现导航级失效"，不是"保证 ref 一定有效"；
- **真正的兜底在"现算 rect"那一步，且判据是三个不是一个**（`[V36]` 实测支撑）：

| locate 时的观察 | 判定 |
|---|---|
| `DOM.resolveNode({ backendNodeId })` 抛错 | 节点彻底没了 → `BROWSER_STALE_REF` |
| resolve 成功，但 `Runtime.callFunctionOn(..., 'this.isConnected === true')` 得 **`false`** | **元素已被移出文档**（SPA 整块重挂）→ `BROWSER_STALE_REF`。实测：把 `#box` 用 `replaceWith` 换掉后，旧 `backendNodeId` 的 resolveNode **仍然成功**，只有 `isConnected` 变成 `false`——**只查 resolveNode 会漏** |
| rect 宽高为 0 | 元素在文档里但不可见（`display:none` / 未布局）→ 报"不可点击"，**不要**拿 0 坐标去点 |

- **真正剩下的漏报区间**：节点还在文档里、`isConnected === true`，但已被复用来显示**另一条数据**（列表重排、虚拟滚动复用 DOM）。这种"内容变了、节点没换"**没有廉价检测手段**——locate 只报告坐标，点得对不对要由调用方按业务语义判断。注释里别写成"兜底完备"；
- 因此 locate 必须**始终**重新算 rect，绝不能拿 snapshot 时的几何缓存去点，否则连这条兜底都没了。

## 5. 必须写进代码注释的陷阱

### 5.1 永远不要用 `clear*` 做还原 `[V10]`

单 client，Electron，`innerWidth|clientWidth|visualViewport|dpr`：

| 步骤 | 读值 |
|---|---|
| 基线 | `900|900|900|2` |
| `setDeviceMetricsOverride(400)` | `400|400|400|1` |
| `clearDeviceMetricsOverride` | `400|400|400|2` ← **只有 dpr 还原了** |
| `setDeviceMetricsOverride(800)` | `800|800|800|1` |
| `clearDeviceMetricsOverride` | **`400|400|400|2`** ← 停在 400，不是 800，更不是 900 |

**"用完 clear 还原"的写法是错的**——它连自己都还原不干净。要还原就**显式 set 回真实尺寸**。
这条同时推翻了我此前"`clear` 会把人工设的值一起压掉"的推断：实测 `clear` 是**弹自己那层**，B 的 clear 动不了 A 的覆盖 `[V11]`，而它自己的残留又是另一个问题。

**适用范围（`[V29]`，纯 Chrome 复测）**：同一个序列在纯 Chrome 153.0.8010.36 上跑，`clear` **完全还原**到真实视口：

| 步骤 | 纯 Chrome 153 | Electron 44 |
|---|---|---|
| 基线 | 754 | 900 |
| `set(400)` | 400 | 400 |
| **`clear`** | **754** ✓ 还原 | **400** ✗ 残留 |
| `set(800)` | 800 | 800 |
| **`clear`** | **754** ✓ 还原 | **400** ✗ 仍停在 400 |

→ **这是 Electron 的集成行为，不是 CDP 规范行为。** 约束照旧写进通用层（插件跑在 Electron 里），但注释里要标明适用范围，以便将来 Electron 修掉后能安全放宽——那时只需重新跑一次 `probe-chrome.mjs` 就能判定。

### 5.2 `host.cjs` 里「一个 target 只允许一个调试客户端」的错误表述——**已随 2.2 修掉**

这段话原本出现在**两处**，都已改：

| 位置（行号随工作区变动，以 `grep -n "不是互斥" src/browser-electron/host.cjs` 为准） | 原表述 | 现在 |
|---|---|---|
| `attachDebugger` 的 doc comment（约 `host.cjs:271-286`） | 「Chrome 一个 target 只允许一个调试客户端，DevTools 打开期间这里必须让位」 | 改成"**不是互斥**：只在打开那一瞬让位，随后立刻接回"，并补了一条 ⚠「re-attach 不保证 domain enable 还在」 |
| `toggleDevTools` 的 doc comment（约 `host.cjs:318-331`） | 「一个 target 只允许一个调试客户端。所以打开前先 detach 让位……关闭 DevTools 后自动重新 attach」 | 改成两条硬结论：**必须先 detach 再 open**（否则静默失败）+ **打开后可立刻接回** |

（`git diff` 可对照，旧版是 `6a0dc8b`。菜单注册处的"互斥"措辞也一并改掉了，现在写的是「与插件 CDP 调试器**不是互斥**」。）

**但本节只解决了注释，没解决协议**——`Inspector.detached` 的过渡语义见 2.2，那才是真正的实现改动点，别以为改完注释就完事了。

### 5.3 `Overlay.highlightRect` 的 `color` 会把整个视口染色 `[V32]`

`highlightRect({x,y,width,height,color})` 的实测渲染：传入 rect 内是**深色填充**，而 rect 之外的**整个视口**被叠上一层同色浅色遮罩（红像素 2073396 ≈ 视口 82%，见 `.workbuddy/tmp/shot-A-highlight.png`）。

做 `browser_locate` 的"给用户看的高亮"时若用它，会让整页变色。**改用 `Overlay.highlightNode` + `highlightConfig`**（`contentColor` 填色 + `borderColor` 边框），实测只有目标元素被覆盖、其他区域纹丝不动。

### 5.4 `Page.captureScreenshot` 在 `show:false` 的窗口上会永久挂起

本轮探针第一次跑就卡在这里：窗口 `show:false` 时 `Page.captureScreenshot` **不返回也不报错**，因为 6s 超时保护没写、整个进程挂死 5 分钟才被我掐掉。同样写法在 `show:true` 下立刻正常（`1800×1400`，DPR=2）。

→ 凡是走截图的路径（`browser_screenshot`、含像素判定的回归测试）：**窗口必须可见**，并且**所有 CDP 命令都要包超时**——`webContents.debugger.sendCommand` 在异常路径下不会自己 reject。

**超时现在只覆盖了一半（核对结论）**：两条链路是分开的，别以为某处写了 `timeoutMs` 就万事大吉。

| 链路 | 超时在哪 | 状态 |
|---|---|---|
| `browser-cdp` 直连端点 | `CdpConnection.send(..., { timeoutMs })`，默认 30s（`protocol.ts:81` / `:153`），provider 内部还会收紧到 5s（`provider.ts:968` / `:1005`） | ✅ 有 |
| `browser-electron` 窗口宿主 | `WindowCdpSocket.send` → `bridge.request`，有 `commandTimeoutMs` 兜底（`bridge.ts:400`，超时报 `BRIDGE_TIMEOUT`） | ✅ 有（但在**父进程**侧） |
| **`host.cjs` 的 `debugger.sendCommand`** | — | ❌ **裸的**：`case 'cdp'` 里 `await entry.debugger.sendCommand(...)`（约 `host.cjs:405`）没有任何超时 |

后果：父进程超时后 `pending` 条目被删、命令以 `BRIDGE_TIMEOUT` 结束，但**宿主进程里那条 `await` 会永远悬着**，并让 `debugger` 停在一个未知状态（这正是 `[V33]` 那次挂死的形态）。修法：在 `host.cjs` 侧包一层 `Promise.race([sendCommand(...), timeout])`，超时照样回 `{ type: 'cdp', error }`——**别只在新代码里包**。

|---|---|
| 跨源 data URL 页面 `fetch()` 同 URL ×3 | `hit=1,2,3` —— 每次都到服务端 |
| 同源 http 页面 `fetch()` + `Network.responseReceived.fromDiskCache` | `fromDiskCache=false` ×3 |
| **完全不用 CDP** 的对照组（页面自己 fetch ×3） | `srv=1,2,3` —— **所以不是 CDP 的问题** |
| `<img>` 子资源（走 MemoryCache） | 命中缓存 ✓，但**显式设 `cacheDisabled=true` 也照样命中** → 这个缓存不受该设置管辖，**没有分辨力** |

→ 本机的 http 缓存对 `fetch()` 响应不生效，而唯一可命中的 `<img>` 走的是 `cacheDisabled` 管不到的 MemoryCache。**没有观测面，就判不了作用域。**

**处置：按最坏假设处理** —— 要么不使用 `setCacheDisabled`，要么与 `Emulation` 同等对待（纳入簿记）。

### 7.2 一句话方法论

**同一 domain 内的不同命令，作用域也可以不同**：`Network.setBlockedURLs` 是私有的，同域的 `emulateNetworkConditions`、`setExtraHTTPHeaders` 却是共享的。所以**每接入一个写状态的 CDP 命令，都要单独实测**，默认按"共享"处理。可复用 `cdp-behavior-probe` skill 里的模板。

### 7.3 U6 为什么必须单独测

这条命令的副作用**在"下一次导航"才显形**，不在写入那一刻——所以它躲得过所有"写完立刻回读"的检查，也躲得过黑名单（它不在 `Emulation.*` 里，字面看像 `Page` 域的普通导航辅助命令）。测法：注册者 **A 不导航**，让 **B 触发导航**，再看新文档里有没有 A 的脚本。结果（`u6b2.jsonl`）：B 自己读到 `"A"`，A 也读到 `"A"`——跨 client 共享坐实。

这条同时澄清了一个判据细节：**"共享"与"持久"是两件事**。A detach 后脚本不再注入（`u6.jsonl`），说明注册项并不跨 session 存活；但**只要注册者活着，任何 client 的导航都吃它的脚本**——这才是"跨 client 污染"的判据，也是它必须被拦住、必须进簿记的理由。

顺带修正一条推论口径：判据不该问"哪个 domain"，而该问"**这条命令写的是不是 target 级行为状态**"。按 domain 划线会同时犯两个错——`Network` 域里既有共享也有私有；`Page` 域里也有共享的（`addScriptToEvaluateOnNewDocument`）。

### 7.4 U7 顺带纠正了我自己的一个错误判断

复审时我写过"`RefTarget` 没有 selector，所以纯计算定位必须先加字段"——那个判断**把 selector 路线当成了唯一路线**。实测（`[V36]`）表明 `backendNodeId` 本来就是稳定句柄，而且比 selector 更安全：

- selector 是"**匹配**"语义：重构之后可能匹配到另一个元素，**静默点错**；
- `backendNodeId` 是"**指向**"语义：节点没了就只能失败，而失败是**可检出**的（`isConnected`）。

教训与 7.2 同源：**先测再断言**。写下"必须先改造 X"之前，先确认现有句柄是不是已经够用了。

## 8. 实施顺序与回归

1. **通用层**：错误码 + detach/re-attach 流程 + 状态簿记骨架（覆盖范围见 2.3 的表：`Emulation` 全类 + `Network.emulateNetworkConditions` / `setExtraHTTPHeaders` + `Page.addScriptToEvaluateOnNewDocument` + `Page.bringToFront`）。
   回归：① `host.cjs` 的 `toggleDevTools` 改成 2.2 的形态后，人工开/关 DevTools，agent 工具全程可用；② **连开/关 5 次 DevTools，ref 纪元一次都不该被推进**——注意这条**现在必然通过**（`refs.invalidate()` 只由地址变化触发，`provider.ts:297` / `:844`，与 detach 无关），它的价值是**防回归**：P3 接入"观察失效"时最容易顺手拿 `Inspector.detached` 推纪元，这条用例就是拦它的；③ `BROWSER_STATE_CONTENDED` 至少有一条可复现路径——**造争用要用有读取面的 key**（`Emulation.setDeviceMetricsOverride` / `setUserAgentOverride`），`Network.*` 那两条没有 get 命令、没法做回读探测（见 2.3.1）。
2. **`browser_console`**：先做去重（**按域分桶**的高水位：`Runtime` 用 `(contextId, type)`、`Log` 用 `(source)`，`[V17][V37]`），再做环形缓冲（`[V24][V39]`，**≥ 1000 是硬不变式，两域同口径**）。
   回归：① 人工接管窗口内页面产生 console，接管结束后采集器**既不漏也不重**；② "3000 条 Log 后 detach → re-enable"，验 `[V39]` 的上限截断**不会变成重复**，且那条 `timestamp=0` 的**截断提示没有被高水位吃掉**；③ `Runtime` 与 `Log` 各按自己的桶去重、互不串扰（两域时间戳类型不同，串了桶就会比错）。
3. **`browser_network`**：直接用 `requestId`（`[V18]`），不做映射；**但要处理"半截记录"**（无 `requestWillBeSent` 的响应事件，见 3.2.1）。
   回归：① 请求与完成都在 attach 期间 → 事件完整；② attach 期发起、**re-attach 之后**才完成 → 收尾链完整（`[V40]`）；③ **detach 期间发起**、re-attach 后完成 → 收到响应事件，且被**显式标为 `partial`**（**不得静默丢弃**）；④ detach 期间**已完成**的请求 → 确认事件永久丢失（`[V38]`，已知且接受的能力边界）——这条要断言"确实没来"，不是等它出现。
4. **`browser_execute`**：**白名单**（默认拒）+ 返回值三态处理（`[V22]`）。
   回归：① `document.body` 这类必须被识别为不可序列化，而不是返回 `{}`；② `Network.emulateNetworkConditions` / `setExtraHTTPHeaders` / `setCacheDisabled` / `Page.addScriptToEvaluateOnNewDocument` 逐条断言被拒；③ 白名单里任一条命令被拒时，错误消息带上 method 全文。
5. **P3 `browser_find` / `browser_locate` / 接管**：`locate` 走 `backendNodeId` → `DOM.resolveNode` → `Runtime.callFunctionOn`（`[V36]`；**不要**用 nodeId `[V19]`，**也不要**引 selector）；高亮用 `Overlay.highlightNode`（`[V31]`），**不要用 `highlightRect`**（`[V32]`）；接管通知按 4.1.1 新增 `{ type: 'takeover' }` 消息。
   回归：① 窗口保持可见（`[V33]`）；② agent 高亮与人工在 DevTools 里选元素同时进行，互不干扰、互不取消；③ **元素被 `replaceWith` 换掉后 locate 必须报 `BROWSER_STALE_REF`**——专验 `isConnected` 守卫，这是 `[V36]` 里唯一"只查 resolveNode 会漏"的场景；④ 人工开/关 DevTools 时父进程恰好收到 `takeover`（`active=true` / `false` 各一条），且 **ref 纪元不变**。
6. **新增任何写状态的 CDP 命令时**：先按第 7 节的方法实测作用域，默认按"共享"处理，再决定是否进簿记（同域也不能类推）。
7. 全程保持既有风格：`pnpm test` 全绿 + 3 跳过（当前基线 174 passed / 3 skipped，数字会随补测变动）；`tsc --noEmit` 干净；`check:desktop` 的 beacon / dockRegistered / toolViews 硬证据。
