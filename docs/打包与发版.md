# 打包与发版

本文件给出执行路径与完成判据。执行前读 [验证与发版规则](agent-rules/验证与发版.md)；机制、历史依据与故障分析见 [打包机制参考](打包机制参考.md)。

| 任务 | 从哪里开始 |
|---|---|
| 独立插件发布与更新 | §8，使用已有桌面壳 |
| 首次制作完整桌面包或升级上游 | §1–§7 |
| 发布新版本 | §9 |
| 验浏览器登录态与 profile 生命周期 | [浏览器登录态验证](浏览器登录态验证.md) |
| Actions 红色、压缩或启动失败 | §6、§10；先查失败步骤日志 |

## 1. 四个前置（缺一必挂）

1. harness 依赖与所需构建产物齐全；本机配置由 scripts/local-env.mjs 读取。
2. 桌面补丁基线与 workflow 的 HARNESS_REF 同源，核对 docs/harness-desktop-build.patch 能应用。已有工作树补丁先查状态，不重复 apply。
3. electron-builder 的 rename EPERM 防护在位：26.17.0 起上游原生实现 `moveDirAtomic`（重试+copy 兜底），`scripts/patch-electron-builder.mjs` 检测到即放行；旧版 ref 仍打我们自己的重试补丁，两者都没有则明确失败。
4. harness 的 apps/desktop/.env.windows 满足当前桌面政策契约；CI 的 harness 使用短路径（LibreOffice 载荷会撞 MAX_PATH，DOCX/XLSX/PPTX 三种都要过）。

升级前保存本地改动，逐条核对补丁理由、上游新增启动契约和运行时布局；补丁职责表见 [机制参考 §1](打包机制参考.md#1-四个前置缺一必挂)。

## 2. 构建与固定目录

⚠️ 本仓构建一律走 `pnpm exec tsdown --no-clean`：`pnpm build` 展开是 `tsdown && node scripts/copy-assets.mjs`，而 tsdown 第一个 bundle 配了 `clean: true` —— 默认构建等于先整目录删除 `lib/` 再重建，属删除分支。`--no-clean` 下产物与既有文件并存，chunk 名带内容哈希不会互相覆盖。

目录约定：本机目录由 .env.local 配置、环境变量优先，`rtk node scripts/portable-dev.mjs env` 核对来源。产物、缓存与暂存放 D 盘且在工作区外（DSH_DESKTOP_BUILD_ROOT），实测固定目录是 DSH_PORTABLE_TEST_DIR。输出路径必须未存在；包含删除、清空或覆盖旧产物的路径按 AGENTS.md 处理，不关闭保护绕过。

本体缓存按 dsh 版本分槽，`cache.json` 完成标记与文件完整性都通过才可复用；写入顺序 mkdir → 复制 → 校验 → 完成标记，缓存键同时考虑上游与补丁变化 → [机制参考 §3](打包机制参考.md#3-本体缓存)。

### 本地测试的固定目录（别再每轮解压一份）

首次铺底用全新目标目录，之后只更新插件。`portable:refresh`、`set-app`、`clean` 可能删除文件，不能直接当保留模式用；插件保留模式见 §8。

启动用 `rtk node scripts/portable-dev.mjs launch --cdp 9333`，并在下一次工具调用确认进程和 CDP 仍存在。

多个测试实例复用同一轮构建时，按 [本地多实例测试方案](本地多实例测试方案.md) 固定产物身份并隔离实例状态；共享同一 app 目录尚未验收。

### 本机重编桌面端（pnpm harness:build）

网络与镜像从本机配置取得。重编前核对 scripts/harness-build.mjs 及上游子脚本的文件行为和补丁恢复逻辑；改 packages 后先构建相应 host 产物 → [机制参考 §2](打包机制参考.md#2-桌面政策与路径)。

## 3. profile 物化

便携包按根目录隔离实例：`home` 保存会话、配置、凭据、插件与依赖运行时，`data` 保存 Electron 数据、缓存、日志、临时文件及用户工具目录。不同目录允许并行，同目录重复启动聚焦原实例；启动脚本使用 `setlocal`，并转发参数到 exe。升级保留用户的 `home` 和 `data`；只更新插件拿不到新的主程序目录隔离行为，必须更新桌面壳。

旧系统 Electron 偏好与登录态不自动导入；需要保留偏好时，退出实例后把明确属于它的 `keybindings.json` 和 `desktop/settings.json` 复制到 `data/electron` 对应位置，原文件保留。

完整包预置 home/profiles/desktop 下的插件登记与真实文件，核心包由 app/resources/dsh 提供；增量包只写插件目录，保留用户 profile/package.json，插件版本与 bundle 从已安装插件目录读取。

出厂默认追加 5 个实验性 bundle（2026-10-18 定）：agent-team-profile / auto-review / tool-worktree / terminal-bundle / session-search。清单在两个打包脚本的 `FACTORY_EXPERIMENTAL_BUNDLES`，改一处必须同步另一处与 `verify:portable` 断言；只追加进 `dsh.profile.bundles` 末尾、不写 dependencies，包体由随包运行时供给。已装实例不受影响 → [机制参考 §4](打包机制参考.md#4-profile-与增量加载)。

### 随包第三方插件（vendor 通道）

- `vendor/plugins/manifest.json` 是单一真相源：`plugins` 存 npm tarball + sha512（与 registry `dist.integrity` 逐字节一致），`runtimeDependencies` 只列运行时真要嵌套物化的依赖（better-sidebar 的 ws/yaml、dsh-context 的 zod）；`dependencies` 其余包是构建期打进 chunk 的，运行时不解析，不得按它物化。
- 打包脚本派生 profile 的 `dependencies`（精确版本）与 `bundles`（追加在内置两个 bundle 与本插件之后），再调 `scripts/materialize-vendored-plugins.mjs --profile-dir <STAGE>/home/profiles/desktop` 物化，sha512 或身份不符即中止。新增插件只需：tgz 放 `vendor/plugins/`、登记 manifest（连 integrity 一起换）。登记与物化不一致会被 `verify:portable` 的 [2/5]/[3/5] 断言拦下。
- better-sidebar 自带 `dsh.bundle.patch`（单条 insert + `!!js` 防双挂载守卫），随 bundles 由 profile boot 合并，不写进用户 cordis.patch.yml。
- 侧边栏当前 0.26.0，官方模块仍注入已退役的 `webRuntime`，靠 manifest 的 `hostCompatibility` 调 `sidebar-host-compatibility.mjs` 适配（官方 tgz 与 SHA512 不改）；按 `SIDEBAR_COMPATIBLE_VERSIONS` 登记启用，未登记版本物化时直接抛错。机理、判定点与发布门禁见 [机制参考 §9](打包机制参考.md#9-随包侧边栏适配)。

### 便携数据归属

桌面补丁在获取单实例锁前将 DSH_HOME、Electron userData/sessionData 及已知全局写入目录绑定到该包的 home/data，不接受从其他实例继承的目录覆盖。首次自动创建的默认工作区在 data/documents/deepseek-harness/default-workspace；已有工作区、用户主动选择或明确配置的项目目录不搬迁。

浏览器宿主的登录 profile 单独保存在 `<包根>/data/browser`，所有网页标签和对话共用该 profile 的 Cookie 与站点数据。旧版 `data/temp/dsh-browser-electron-host` 不迁移，用户需重新登录，旧数据原样保留；开发态默认用当前 `DSH_HOME/data/browser`，`DSH_BROWSER_USER_DATA_DIR` 非空显式设置优先。用户侧说明见 [安装说明：网页登录态与数据保留](portable-install.md#网页登录态与数据保留)。

## 4. 五道自检

执行前核对脚本是否删除临时文件，确认 19387 无其他实例。下表给出验收职责，不自动授权运行删除路径。

| 自检 | 完成判据 | 目录条件 |
|---|---|---|
| verify-portable | 运行时完整性、插件登记、真实 applyRelease、出货 patch、客户端加载均通过 | 新解压、未启动 |
| verify-ptc | 真 patch 引擎 compose，包内 Node 命中并可求值 | 按脚本核对副本行为 |
| verify-settings | 用户层设置投影与真实模型配置接受 | 按脚本核对副本行为 |
| verify-browser-host | 包内 exe 开窗口，导航、ref、截图及 provider 正反验证 | 可已启动过 |
| verify-plugin-update | 三轮宿主的探针无→有→无，bundle 比较剥除动态 rev | 已有便携目录；保留模式见 §8 |

浏览器登录态生命周期（两 profile 隔离、关标签与重启后的保留）不在此表内，单独执行 [浏览器登录态验证](浏览器登录态验证.md)。

## 5. 真机验证（自检过不了这一关的都不能算过）

1. 正常退出目标实例，更新后重新启动；热刷新不替代重启。
2. 核对用户数据保留、插件版本和实际加载文件。
3. 按 [打包态对话驱动](打包态对话驱动.md) 用渲染页 UI 发真实 prompt；19387 的直接接口不能验证 agent 身份归属。
4. 按 [用户故事](用户故事与实测场景.md) 运行独立场景，分别记录页面效果、原始工具结果、模型偏差与环境阻塞。
5. 核对真实鼠标交互、模型回复和工具调用。启动成功、标题非空、静态检查通过均不能替代此门禁。

## 6. zip 与解压

判据：压缩 exit=0、testzip=None、解压文件前 32 字节无 NUL、结构和实际文件一致、SHA256 对应最终上传附件。CRC 正常不能证明写盘内容正常。用 `scripts/unzip-portable.py` 解到明确目标目录；`scripts/zip-stage.py` 共享读、stdout/stderr 统一 UTF-8（否则 Windows runner 的 cp1252 吞掉中文路径和失败原因），压缩前输出路径必须不存在（脚本仍有旧输出删除分支）。机理见 [机制参考 §7](打包机制参考.md#7-压缩解压与诊断)。

## 7. 出货 patch 的红线

生产 cordis.patch.yml 及生产导出不得包含 fake-llm、llm-replay 或 mock-llm 的 llm/stream 劫持；开发回放只用于开发态，不能证明真实模型验收。

桌面构建补丁与插件配置补丁分别核对。PTC `launch.executable` 覆盖必须用真实 compose 加真 schema 解析双重验证——配置键被上游改名不报错、只写不读，0.1.6 时代的 `nodeExecutable` 已废弃。不以文本存在代替加载生效 → [机制参考 §6](打包机制参考.md#6-包内-node-路径打包态专有坑已修)。

## 8. 独立插件包与更新验证

正式发布与用户安装使用下方“独立插件发布包”。本节开头的 overlay 包仅供现有宿主三轮更新自检使用。

只更新插件时使用已有桌面壳。以下占位路径必须换为本轮 D 盘路径，构建目录和 ZIP 目标均新建，保留暂存证据：

~~~powershell
rtk pnpm exec tsdown --no-clean --out-dir <本轮构建目录>
rtk node scripts/copy-assets.mjs --out-dir <本轮构建目录>
rtk node scripts/package-plugin-update.mjs --lib-dir <本轮构建目录> --stage-root <D盘暂存父目录> --keep-stage --out <未存在的ZIP路径>
rtk node scripts/verify-plugin-update.mjs --dir <便携目录> --lib-dir <本轮构建目录> --scratch-root <D盘暂存父目录> --keep
~~~

保留自检只正常退出自建宿主，拒绝 --in-place。默认打包暂存位置为系统临时目录、默认自检会删除暂存文件，本机必须显式传上述目录与保留参数。

包内仅含 home/profiles/desktop/node_modules/dsh-webops-plugin 的 lib、package.json、cordis.patch.yml，以及根目录更新说明.txt。打包会核对五个 Electron 资产，排除 fake-llm 文件及导出。

安装前正常退出，覆盖本轮明确文件，保留用户 home、profile 登记与旧 chunk；然后重启核对版本、数据哨兵与 GUI。生产插件只加载新入口，旧 chunk 无需清理。三轮生效自检和真实最终 ZIP 安装分别记录。

### 独立插件发布包（package-portable 的保留安全模式）

每次插件 Release 必须同时发布 `dsh-webops-plugin-v<版本>.zip` 与 `dsh-webops-desktop-v<插件版本>-win-x64-portable.zip`。插件 ZIP 根目录即插件内容，完全退出 DSH 后覆盖到实际插件目录再重启；便携版默认目标 `home/profiles/desktop/node_modules/dsh-webops-plugin/`，不能解压到包根。首装用完整便携包，已有用户可只下插件包（步骤见 [安装说明](portable-install.md)）。旧 overlay 脚本仅供三轮自检，不再作 Release 附件。

完整包由 `scripts/package-release-portable.mjs` 组装：从固定 SHA256 的已验收基包只取 app，重建出厂 home，装入本次插件 ZIP 与 vendor 两个插件，不复制用户数据；`release-manifest.json` 分记 pluginVersion 与 dshVersion。基包固定 `desktop-v0.2.1-rc.2`，直接用 SHA256 验证后解出的 app，不再运行只支持 alpha.2 五处锚点的 `prepare-release-app.mjs`。基包 tag / 附件名 / SHA256 与插件三个 DSH peer 精确版本必须一致（实际值以 release.yml 为准），peer 不匹配直接失败，不静默用旧本体。

组装先只读核对中英文语言包与两份 pnpm 的逐文件一致性，再在复制时排除其他语言包与已证明重复的旧 pnpm，不先复制后删除；输入与暂存证据全保留。旧 `slimApp`/CLI 会实际删除，不得在本机运行，也不能把这条保留路径外推到桌面本体旧打包入口。

独立插件包内含完整生产 lib（含 browser-electron 资产，排除 fake-llm）、cordis.patch.yml、发布版 package.json（剔除 devDependencies/scripts 与 fake-llm 导出）、README、LICENSE、INSTALL.md；缺任一即报错。两个打包脚本必须显式传 `--lib-dir`，遗漏在写入前拒绝，防止仓库旧 `lib` 贴新版本号；`package-portable.mjs` 因此为**保留安全模式**：暂存是 stage-root 下 mkdtemp 唯一新目录（`--keep-stage` 仅参数对齐）、输出 zip 必须不存在（存在即报错）、零 rmSync，裸调用因缺 `--lib-dir` 被拒。

~~~powershell
rtk node scripts/package-portable.mjs <版本> --lib-dir <本轮构建目录> --stage-root <D盘暂存父目录> --keep-stage --out <未存在的ZIP路径>
~~~

保留模式会创建输出父目录，路径作为参数直接交给 Python，不拼接 PowerShell。两个脚本均用 `zip-stage.py --no-overwrite` 独占创建，拒绝既有 ZIP 与检查后出现的目标；未传该参数的历史覆盖分支受删除禁令约束，不得运行。`src/package-portable.test.ts` 覆盖缺失父目录、单引号路径、生产文件剔除与拒绝覆盖后哈希不变。

## 9. 发版

| tag | workflow | 产物 |
|---|---|---|
| v* | release.yml | 独立插件包 dsh-webops-plugin-v<版本>.zip + 完整便携包 dsh-webops-desktop-v<插件版本>-win-x64-portable.zip |
| desktop-v<DSH版本> | release-desktop.yml | dsh-webops-desktop-v<DSH版本>-win-x64-portable.zip |

1. 完成本机类型检查、单测、打包态自检与真实 GUI 门禁，记录版本和提交。
2. 插件 `v*` tag 与本仓 package.json 版本一致；桌面 `desktop-v*` tag 与实际 app 的 desktop-runtime.json 中 release.version 一致。桌面包内的插件版本仍取本仓 package.json，不随本体版本改写。两个 workflow 均显式签出 tag；dispatch 的 tag/version 输入决定源码，不能用 main 的修复冒充旧 tag。
3. 选择新版本，核对远端 tag 与 Release 不存在，再发布；已发布 tag 保持原提交，附件保持原内容。
4. 等待对应 Actions 结束，查看步骤结论和失败原文；同时核对 Release 发布状态、确定文件名、大小和 SHA256，两项分别报告。
   - 完整便携包缺失、内置插件版本与 tag 不一致时，不能报告发布完成。
   - workflow 在创建 Release 前解压最终 ZIP 跑 `verify-release-portable`：校验随包运行时哈希、出厂数据边界、三个插件版本和真实宿主首页加载图，不依赖 CI 未编译的 harness lib。
   - 先上传为草稿，核对两个附件均已上传且 GitHub digest 匹配本机 SHA256，再公开发布；失败保留草稿，验证目录不清理。
   - 本机另跑 `verify-portable --keep-temp` 验首次启动准备与完整客户端图。
5. 本机已上传验收附件而自动 workflow 随后失败时，报告“附件已发布 / 自动链失败”，按失败步骤定位；不用附件存在推断 CI 全绿。

发布链同样保留式：Release 只在不存在时新建，同名 Release 已存在即明确失败并提示换新版本号（旧 `gh release upload --clobber` 覆盖分支已按文件删除禁令移除）；本机任何输出路径必须未存在。

本机发版前准备（占位路径换成本轮 D 盘唯一新目录；构建目录、stage-root、插件 ZIP 全部新建，保留全部暂存证据）：

~~~powershell
rtk pnpm exec tsdown --no-clean --out-dir <本轮构建目录>
rtk node scripts/copy-assets.mjs --out-dir <本轮构建目录>
rtk node scripts/package-portable.mjs <版本> --lib-dir <本轮构建目录> --stage-root <D盘暂存父目录> --keep-stage --out <未存在的便携包ZIP>
rtk node scripts/package-release-portable.mjs --app <已验收基包app目录> --plugin-zip <本轮独立插件ZIP> --version <版本> --stage-root <D盘暂存父目录> --out <未存在的完整便携包ZIP>
rtk node scripts/verify-plugin-update.mjs --dir <便携目录> --lib-dir <本轮构建目录> --scratch-root <D盘暂存父目录> --keep
~~~

发布链依赖与并发设计由 src/bundle-patch.test.ts 约束：发布 workflow 不承担需要本机构建 harness 的类型检查/单测；同 tag 串行等待；收尾 Summary 无论成败记录产物；保留式打包契约（no-clean、保留参数、无 clobber）也在其中锁定。修改 workflow 后按验证规则重跑单测。

## 10. 按症状排障

| 症状 | 先查什么 |
|---|---|
| UnicodeEncodeError / cp1252 | Python 子进程 stdout、stderr 编码；运行中文路径和错误路径回归 |
| host never announced a port | Electron 实际异常、是否误 external 化、运行时依赖；不能只延长超时 |
| GUI 退出 0 且无输出 | ELECTRON_RUN_AS_NODE、NODE_OPTIONS 与打包入口 |
| 界面能见但点不动 | 其他窗口是否遮挡、shell 页面是否正常加载 |
| 压缩或重命名 EBUSY/EPERM | 精确文件和持有者，参考共享读与工作区外构建策略 |
| 发布步骤失败 | tag、附件状态、权限和失败原文；不默认删除重发 |

机制和历史原文见 [打包机制参考](打包机制参考.md)，本机操作边界见 [本机排障规则](agent-rules/本机排障.md)。
