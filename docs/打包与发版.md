# 打包与发版

日常插件发版使用本文，人和 agent 共用。先读 [验证与发版规则](agent-rules/验证与发版.md)。

| 要做什么 | 入口 |
|---|---|
| 发布插件及同源码重编的完整便携包 | 下方三步流程 |
| 本机构建、更新测试实例、验包 | [本机打包与验收](本机打包与验收.md) |
| 升级 DSH 本体、重建桌面基包 | [桌面本体升级](桌面本体升级.md) |
| 修改打包实现或排障 | [打包机制参考](打包机制参考.md) |
| 安装或更新已发布插件 | [安装说明](portable-install.md) |

## 发布前准备

在仓库根目录操作；本机终端为 Windows PowerShell，命令经 rtk 执行。准备好可用的 Git、gh 发布权限及本机构建和测试环境。

| 输入 | 从哪里取得 |
|---|---|
| 插件版本 | 本仓 `package.json.version`，tag 为 `v<版本>` |
| 待发布提交 | 本轮明确的提交；验收记录须与其代码和产物对应 |
| 桌面源码 | release.yml 的 `HARNESS_REF` 加本 tag 的 docs/harness-desktop-build.patch；完整便携包在同一作业重编，不以旧公开基包代替当前补丁 |
| 测试目录和证据路径 | .env.local 与本轮 D 盘目录，见本机打包与验收 |

## 日常发版三步

1. **本机验收**：按 [本机打包与验收](本机打包与验收.md) 完成构建、自检、真实便携版增量验证和 GUI 验收。记录提交、版本、产物及原始证据；有失败或必需项未验时停止。
2. **推新 tag**：核对版本，确认远端同名 tag 和 Release 不存在，将新 tag 指向已验收提交后推送。release.yml 自动构建、打包、验证并发布；[自动检查](打包机制参考.md#8-发布链的职责) 无需人工重复执行。
3. **核对结果**：等待 Actions 结束，检查失败步骤和原文错误；同时核对 Release 已公开、两个确定附件齐全、内置插件版本与 tag 一致。记录文件名、大小与 SHA256，并核对 GitHub digest。

| 必需附件 | 文件名 |
|---|---|
| 独立插件包 | `dsh-webops-plugin-v<版本>.zip` |
| 完整 Windows x64 便携包 | `dsh-webops-desktop-v<版本>-win-x64-portable.zip` |

Actions 结论和 Release 完整性分别报告，证据记入 [验收记录](验收记录.md)。缺包、结构验证失败或版本不符时，不算发布完成。

## 失败处理

| 情况 | 下一步 |
|---|---|
| 本机验收未通过 | 停止推 tag，按本机验收的失败项定位 |
| 同名 tag 或 Release 已存在 | 停止并换新版本号，保留旧提交和附件 |
| Actions 失败 | 保留草稿和证据，按失败步骤查日志；[按症状排障](本机打包与验收.md#失败处理) |
| 附件已发布，自动链失败 | 分别报告“附件已发布 / 自动链失败”，不能用附件存在证明 CI 成功 |

两个 workflow 都签出目标 tag；手动 dispatch 也按输入 tag 取源码，不能用 main 修复冒充旧 tag。已发布 tag 和附件的处置按 [发版门禁](agent-rules/验证与发版.md#4-发版门禁) 执行。
