# 上下文膨胀：三个方案与建议

> 一句话：**「撑爆」不是这两次会话的问题**（占用约 11%，宿主兜底阈值在 80%），真正的浪费是
> **步数 × 公共前缀**（知乎那次 ≈ 55 步 × 70.6K 字符 ≈ 388 万字符，占全部重发量的 70%）；
> **增量快照可行**（同文档内容级不变率实测 96.6–99.5%），但按这两次的数据它只值总成本的 ~2%，
> 不该排第一。

本文是**评估与排序稿**，不复制实现细节。增量 diff 的权威设计仍在
`多会话防冲突-实施方案.md` §8（四条硬要求 + 门禁），本文只补它漏掉的两条约束（§2）；
`webpage交互改进-实施方案.md` §5 把它划给 P4 的口径不变。

## 0. 结论

| 方案 | 省什么 | 按本次实测算 | 实现面 | 主要风险 | 建议 |
|---|---|---|---|---|---|
| **A 减步数** | 每一步的公共前缀 + 无效往返 | 砍掉一半试探性往返 ≈ **13%**（知乎） | 小–中（改回执 / 文档要动工具面） | 改回执可能扰动模型行为 | **先做 A2，A1 其次** |
| **B 减新增**（增量 diff） | 同一文档重复快照的重复行 | 同文档重拍省 ~99%，占总成本 ~**2%** | **大**（§8 四条硬要求 + ref 语义） | 口径/语义定错 → 退化回全量 | 最后做，先订正口径 |
| **C 减前缀** | 每步重发的工具 schema | 16 个 `webpage_*` 描述可压 ~50% → 总量 ~**10–13%** | 小（改文案） | 描述是刚精修的，精简可能降低「照做率」 | 值得做，需行为走查兜住 |

**不是方案、但要先做**：宿主已有三层兜底（spill / 输出修剪 / 会话压缩），当前阈值一个都够不着
（§1.3）。这是「防撑爆」的正解，但它是**配置体检**，不需要写代码。

### 0.1 都要做吗 —— 不要

**先换判据**：「省了多少字符」不是判据。真正的判据是三条 —— **① 有没有错误信号（正确性）；
② 是不是每一步都在付（固定成本）；③ 离阈值还有多远（安全阀）。**

| 档 | 条目 | 为什么归这一档 | 不做会怎样 |
|---|---|---|---|
| **必做**（与膨胀无关也得做） | **A2** 修 `page_changed` 虚报 + 改指令 | 它是 **bug**：工具在主动教模型跑全页快照，且回执自相矛盾（`navigated=false` 却说「外面有人动过」）。§6.4 的砍掉条件早挂账 | 每次真机会话白付约 5 张快照，且行为被错误信号带偏 |
| **值得做**（唯一作用在「每步都发生」那项上） | **C** 减前缀 | 前缀就是 70% 成本的来源（知乎 3.88M / 5.55M），且**每条会话每一步都付** | 每步多付 ~13K 字符，功能无损失 |
| **顺手做**（配置一行） | **B2** spill 阈值 50000 → 16000 | 本来就该开的能力，与做不做膨胀无关 | 单条异常大回执（34K）原样进上下文 |
| **有条件才做** | **A1** 回执补目标描述；压缩阈值按**小窗口模型**覆盖 | 收益取决于 A2 之后还剩多少无效往返 | 少省一点，无风险 |
| **暂时不做** | **B1** 增量 diff | 只值总成本 ~2%，且它真正服务的场景（长会话反复观察同一页）**目前不存在**（两次样本各 1 轮） | 长会话真出现时再补——届时先落 §2 两条订正 |
| **永远不做** | 自造输出预算/落盘、调 pruner 阈值、一刀切调压缩阈值 | 与上游能力重复 / 会把 ref 表剪出空洞 / 512K 窗口下无意义 | —— |

**只做一件：A2。做两件：A2 + C。**

**还必须说清一条**：上面没有一条属于「防撑爆」。按实测占用（最小的 u2 窗口 163,840，
两次会话末尾 ≈ **21% / 35%**〔粗估〕），离 80% 阈值都很远——**什么都不做也不会撑爆**。
所以这些方案的真实收益是**成本与正确性**，不是安全阀。安全阀靠宿主三层兜底（§1.3），
插件侧的活只有一句：**别让它去兜底**（`spill` 按条接住大回执，比 `pruner` 剪快照中段安全得多）。

## 1. 问题重述（读数与口径）

### 1.1 口径（可复现）

会话记录在 `$DSH_PORTABLE_TEST_DIR/home/sessions/--D-dev-cli-dsh-webops-plugin--/*/session.v3.jsonl.zstd`：

1. `/d/app/msys64/usr/bin/zstd -d` 解压；
2. 按 `tool/call.callId` ↔ `tool/result.message.source.callId` 配对，取 `tool-result` 里 `type:"text"`
   的全文，**这就是模型看到的东西**；
3. 「行重复率」= 两份相邻快照的行**多重集合**交集 ÷ 后一份行数；
4. 「剥 ref 后」= 先删掉 `[ref=eNN]` 再算（理由见 §2.1）。

两个会话（均为**单个 turn**，不是跨用户消息的多轮）：`95a282ea` Google AI 模式（12:57）、
`e0288ca7` 知乎登录（13:07）。

### 1.2 三个成本项

| 成本项 | 量 | 说明 |
|---|---|---|
| **公共前缀**（每步重发） | 工具 schema **55,712** 字符（49 个工具，其中 `webpage_*` **16 个 / 24,854**）+ system prompt 13,623 + 用户消息 | 日志只在轮次开始记一次 envelope；**每一步的 API 请求都带这份 schema** 是按 `request/header` 口径的**推断**，可在「请求检查」面板直接核对 |
| **新增回执** | Google **130,459** / 知乎 **50,331** 字符 | 快照占 56.5%（73,728）/ 55.5%（27,936）；Google 另有一条 `network list` **34,214**（单条占该会话 26%） |

| 会话 | 步数 | 新增回执累计 | 各步上下文之和 | 放大 |
|---|---|---|---|---|
| Google | 33 | 130,459 | **≈ 429 万字符** | **32.9×** |

> **这一节是全文最重要的一行**：知乎那次的 **3.88M / 5.55M = 70%** 是「55 步 × 70.6K 前缀」，
> 回执（含 7 张快照）只占 30%。**所以「省快照」永远只能省下三成里的一部分。**

### 1.3 兜底为什么一个都没接住（都是实测，不是猜）

| 兜底 | 出厂配置 | 为什么没触发 |
|---|---|---|
| `dsh-spill-policy` | `maxInlineBytes: 50000` | 最大单条是 `network list` **34,214 字符**，**没到线** → 原样进上下文（全文可取回那条路也就没用上） |
| `dsh-compaction-tool-result-pruner` | `thresholdChars 8192` / head 4096 / tail 1024 | **只在压缩触发之后才跑**（压力不足时一个字符都不碰） |
| `dsh-compaction-basic` | `thresholdRatio: 0.8` | u2-flash 窗口 524,288 → 阈值约 **41.9 万 token ≈ 147 万字符**；两次会话末尾是 ~20 万字符（**~11%**）→ 差 7 倍 |
| `/compact` | 手动 | 人没敲 |

（三者都在 `@deepseek-ai/dsh-base` 里挂载，桌面 profile 引入了该 bundle —— 不是「没装」。）

### 1.4 一个会改变排序的未知量

若路由对**公共前缀**走 prompt cache 折扣，则 1.2 里 70% 的「前缀重发」实际单价远低于新增内容，
**B / C 的相对收益上升、A 下降**。日志的 `request/header` 只有 `config` + `tools`，没有任何
cache 控制字段，无法从会话记录判定。**开工前先确认这一条**（问服务端，或看账单口径）。

## 2. 增量快照可行吗 —— 可行，但要先订正两件事

### 2.1 订正一：门禁口径必须**先剥掉 `[ref=eNN]` 再算**

实测（同文档相邻快照）：

| 会话 | 对 | 原始行文本重复率 | **剥 ref 后** |
|---|---|---|---|
| Google | step7→12 / 12→15 / 15→19 / 19→23 | 73.8% / 74.3% / 74.3% / 74.3% | **98.5% / 99.5% / 99.5% / 99.5%** |
| Google | step23→28 | 53.6% | **72.3%**（AI 回答真的出来了，refs 56→78） |
| 知乎 | step3→6 / 6→8 / 8→10 | 60.2% / 60.2% / 57.3% | **99.0% / 99.0% / 97.8%** |
| 知乎 | step10→33 / 33→42 | 56.2% / 53.6% | **96.6% / 89.9%** |

原因：**每次全页快照都推进 epoch 并整表重编号 ref**（Google：`e1,e2` → `e35,e36` → `e91,e92` →
`e147` → `e203` → `e259` → `e315`，步长 = ref 数 56；知乎同样）。含 `[ref=eNN]` 的行文本
**每行都不同**，于是「行文本不变率」被系统性低估。

两条后果：

- **读数**：§8 的门禁表用的是行文本口径。按本文的样本，原始口径会给 53.6–74.3% 的假象，
  容易被误读成「不达标 → 不做」；剥掉 ref 后才是真实的内容稳定度（96.6–99.5%），
  与 §4.3 的中位 98.3% 一致。
- **实现**：真按行文本比对，diff 会得出「全变了」→ 每次都退全量。**必须**按 §8 硬要求 1
  （主键 = `backendNodeId`）比对，行文本只用于渲染。

### 2.2 订正二：ref 语义必须定死（§8 没写这一条）

若未变行**不发**，模型手里的旧 ref 号来自上一个 epoch，而新快照把同一节点编成了新号。
两条出路，必须选一条并写进 schema：

| 出路 | 做法 | 代价 |
|---|---|---|
| **沿用旧号**（推荐） | diff 回执里未变行保留上一次的 ref 号，只有新增/变更行取新号 | 破坏「ref 号只在同一 epoch 内有效」的既有语义，`webpage_revalidate` 与写前门的 epoch 判定要跟着改 |
| **给映射表** | 回执附 `旧号 → 新号`（`rebound_refs` 的全量版） | 映射表本身就是 O(refs) 体积，省下来的可能又还回去 |

### 2.3 收益上限（按本次数据）

- 收益 = 同文档重复快照的重复部分。Google 4 张同尺寸快照（各 ~10.7K）走 diff 后每张只发 ~5 行
  → 约省 **42K 字符**，是该会话新增回执的 **32%**、**总重发量的 1.0%**；知乎同理约省 18K / 总 0.3%。
- 所以：**增量快照不是「防撑爆」的手段，它是「长会话反复观察同一页」的手段**。
  这两次会话都不属于那个场景（各只 1 轮）。

## 3. 三个方案

### A · 减步数（每砍一步 = 省掉一份 70.6K 前缀）

**A1 消除试探性往返。** 知乎那次 22 次 `webpage_execute`（`Runtime.evaluate`）里，大量是「读状态」：
读 `activeElement`、读 URL、读某元素的文本/几何 —— 这些本该由回执直接给。做法：

- `webpage_locate` 回执补「可见文本 + 几何 + 是否在视口」；
- `webpage_snapshot` 在 `page_changed` 脏时自带一行「自上次快照以来的变化摘要」（复用 §6.2 的累加器，不新开机制）；
- `webpage_click` / `press` / `fill` 回执带目标元素的 role/name/文本（**现在 `fill`/`press` 连目标都不描述**，这直接逼出下一次 `execute`）。

**A2 抑制重复全页快照（治触发，最便宜）。** 现在工具在**主动教模型做贵的事**：
`PAGE CHANGED OUTSIDE THIS SESSION` 的收尾指令原文是 `run webpage_snapshot (full, not regional)`，
而 Google 那次它在 4 条回执里出现（12 处命中），触发者只是页面自己换了遥测令牌（URL 的 `mstk=` 变值，
正文 74%→剥 ref 后 99.5% 相同）。做法：

- 脏判据排除「仅遥测令牌/query 抖动」（`mstk` / `csuir` / `ved` 一类），或把它单列成 `addressDrift` 且**不给重拍指令**；
- 指令从「跑全页快照」改成「先 `webpage_revalidate` 旧 ref；确需重观察再拍」；
- 可选再加：同一文档、自上次全页快照后**没有任何本会话动作**时，第二次全页快照返回引用式回执
  （`unchanged since your snapshot at step k: N refs / M lines`）+ `force: true` 逃逸。

**A3 批量动作**（`webpage_act([...])`）——**有争议，先不做**：`webpage交互改进` §5 明写「不新增工具」，
且新工具本身加前缀。先量「同一 ref 上的连续动作」频次再议。

**利弊分支**

| 分支 | 做什么 | 判据 |
|---|---|---|
| A2 先做 | 改脏判据文案（半天） | Google 场景里 `mstk` 不再触发脏；模型重拍次数下降 |
| A1 后做 | 回执补目标描述 + 变化摘要 | `webpage_execute` 调用数下降（知乎基线 22 次/55 步） |
| A2 无效 | 模型仍每次全页重拍 | 才做「引用式回执」那一档 |

**风险**：A1 改回执文本 = 改模型输入，可能扰动行为 → 每档都要跑 `webpage交互改进` §6 的场景 A/D/E。
**代价**：A2 判据放宽 = 可能漏报真实外部变化 → 由 P1 写前门兜底（§6.3 的既定分工）。

### B · 减新增（增量 diff + 让 spill 接住异常大回执）

**B1 增量 diff**：按 `多会话防冲突-实施方案.md` §8 做（主键 `backendNodeId`、semanticKey 兜底、
重建检测退全量、`full: true` 逃生舱、基于模型所见视图），**外加 §2.1 / §2.2 两条订正**。
收益见 §2.3（这两次会话里 ~2%）；真正场景是长会话反复观察。

**B2 大回执交给 spill，不自己做预算**：`maxInlineBytes: 50000` → **16,000** 左右。
选这个数的依据是实测分布：快照中位 ~5.5K、最大 13.8K（**不能被 spill**，否则 ref 表没了），
`network list` 34.2K / `console` 类（**应该被 spill**，它们本来就是可截取的日志）。

**利弊分支**

| 分支 | 做什么 | 判据 |
|---|---|---|
| B2 | 改一行配置 + 验证取回可用 | 单条 >16K 时回执出现定位信息与预览；全文可按段取回 |
| B1 | 仅在 A/C 落地后仍有「同文档反复全页快照」时开工 | 同文档重复快照 ≥ 3 张/会话 |
| B1 前置 | 门禁口径改成剥 ref 后算 + ref 语义选一条写进 schema | 不先做这两条 → 一定退化成全量或 ref 对不上 |

**风险**：B1 是本表里唯一「改协议」的；口径写错会静默退化（读数全绿、实际每次都全量）。
**代价**：实现期最长，且与 P1 写前门/`revalidate` 的 epoch 语义耦合（§2.2 出路一）。

### C · 减前缀（工具 schema 精简，纯文案）

`webpage_*` 16 个工具的 description 合计 **24,854 字符**，是每步都发的固定成本。做法：

- 公共口径（refs 有效期、`untrusted external data` 声明、区域快照不废 ref、folded 语义）**只在系统提示里写一份**，
  16 份工具描述里不再各写一遍；
- 每个工具的「什么时候用/不用」压成一句，长篇示例合并到系统提示的同一个小节（系统提示只发一次 13.6K，边际成本低于 16 份描述）。

**利弊分支**

| 分支 | 做什么 | 判据 |
|---|---|---|
| 做 | 目标：`webpage_*` schema ≤ 12K（省 ~13K/步） | 省 ≥30% 且 §6 场景 A/D/E 的照做率不回退 |
| 不做 | 若照做率回退 | 全额回滚（描述是刚交付的 B2-c 五条提示词的载体） |

**风险**：这是**刚精修过的文案**，精简与「让模型照回执走」直接冲突 → 必须有行为门禁，不能只看字符数。
**代价**：低（无协议变更），但收益不确定（取决于前缀是否走 cache，见 §1.4）。

## 4. 建议

**顺序：前置体检 → A2 → C → A1 → B1。理由逐条：**

1. **前置体检（今天，零代码）**：确认 §1.4 的前缀计价口径；若支持 cache 折扣，下面的排序要重排。
   顺手看一眼按**小窗口模型**（u2 163,840 / glm-5.1 206,848）跑网页任务时的 `thresholdRatio: 0.8`
   （阈值 ≈ 13–16 万 token）是否偏低 —— 大窗口模型不动它。
2. **A2（半天）**：工具正在主动下「跑全页快照」的指令，且触发者是遥测令牌。**先停掉错误的信号，
   再谈优化**，比反过来便宜也安全。
3. **C（1 天）**：唯一作用在「每步都发生」的那一项上的方案，收益上限 10–13%，风险靠 §6 走查兜。
4. **A1（1–2 天）**：动回执文本，按 A2 之后剩下的 `execute` 往返量决定做不做。
5. **B1（最重，最后）**：它服务的是「长会话反复观察同一页」，而那类会话在这两次样本里**还不存在**。
   开工前必须先落 §2.1 / §2.2 两条订正，否则做了也会退化成全量。
6. **B2 随前置体检一起做**（改一行配置）。

**验收口径**（前后对比都用这一条，别换）：
同一会话的「各步上下文之和」（§1.2 表）与「新增回执字符累计」。基线：Google 429 万 / 130,459，
知乎 555 万 / 50,331。**目标：先把 555 万那一档压到 400 万以下**，而不是先压快照。

**明确不做**

| 项 | 为什么 |
|---|---|
| 自己造「输出预算 + 落盘」（B2 的另一种做法） | 上游 `dsh-spill-policy` 就是干这个的，配置层能解决就别写代码 |
| 调低 `tool-result-pruner.thresholdChars` | 它剪的是**中间**（head 4096 + tail 1024），对快照 = 把 ref 表剪出空洞，而 ref 是唯一可操作句柄 |
| 一刀切调低 `compaction-basic.thresholdRatio` | 512K 窗口下调了仍然很晚；且每次压缩 = 多一次模型调用 + 打断 KV cache 复用。只对小窗口模型按模型覆盖 |
| 为省前缀而「合并工具」 | 与 `webpage交互改进` §5「不新增工具」同源的克制：先做文案精简，再看数据 |
| 增量 diff 当「防撑爆」卖 | 见 §2.3，它只值 ~2%，是长会话优化不是安全阀 |
