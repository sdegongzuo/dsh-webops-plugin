> 按**事故轴 × 时刻轴**重排。取代原「并发轴」骨架与 T0-T5 编号（映射见 §9）。
> **目标与验收判据在 §0** —— 要往本文加任何任务，先把它填进 §0.3 的追溯表，填不出「服务 J 几」就不做。
> 依据：`docs/多会话防冲突设计评估.md`、本文 §8 的实测数据。
> 原文各节论证保留在 §10 对照区，便于查「为什么当初那样判断」。

## 0. 目标

### 0.1 一句话目标

**让人工与多会话共用同一个页面时，agent 不再「基于旧认知静默点错」：要么动作正确落地，要么明确失败并告诉它为什么、下一步做什么。**

不追求的是「防止人工和 agent 同时操作」——那做不到，也不需要。**追求的是不静默。**
判据全在「静默」两个字上：报错但没人知道，等于没防住；防住了却把正常路径也堵住，那是另一种事故。

### 0.2 三条验收判据（每条都能测；说不出服务哪条的任务一律不做）

| # | 判据 | 怎么算达标 | 阈值来源 |
|---|---|---|---|
| **J1** | **零静默** | 任何一次基于 ref 的动作，若落地时的页面状态与模型拍快照时不是同一份 → **报错且动作未发出**（不是事后告警） | 走查用例：SPA 换路由、同文档改 DOM（含列表重排）、D-5 那条区域快照改绑 |
| **J2** | **不误伤** | 人工没动时，写前门不得让正常路径失败、也不得多出无谓重拍 | 误伤率上限等 P0 出数（§4） |
| **J3** | **不炸上下文** | 新增通知字段 + 强制重拍的 token 成本，不得吃掉单次快照的预算 | 单次全量 snapshot 的 token 量，P0 量 |

**这三条同时是砍刀的落点**：判据不达 → 对应任务砍或降级，不是补更多字段。已有的三处砍掉条件
（§4 纯推理标注、§6.4 模型无视即整条砍、§12 止损表）都挂在这里。

### 0.3 任务 → 目标追溯（对不上号的就不该在本方案里）

| 层 | 服务 | 怎么服务 | 不达时 |
|---|---|---|---|
| **P0** 量事故分布 | J1/J2/J3 的阈值全出自它 | 没有分布就定不出默认档位与阈值 | 出数与本文排序冲突 → **以 P0 为准，回写本文** |
| **P1** 写前门 | **J1 的主防线** | 唯一在「提交那一刻」还来得及拦的机制 | J1 就是达不成，全案作废 —— 其它层都替代不了它 |
| **P2** 决策时通知 | J1 的「告诉模型下一步」+ J3 的减负 | 让模型早一轮重拍，而不是白撞一次错误 | 模型无视 → 整条砍掉（§6.4），**不许当兜底**（§6.3） |
| **P3** 记账与互斥 | J1 的窄子集 | 只管「跨会话共用同一 sessionId」这一条路径 | P0 显示从未发生 → 一直不做 |
| **P4** 增量 diff | **只服务 J3** | 降低重拍成本，与防错无直接关系 | 两道门禁不达标即出局；**别把它当防错手段卖** |
| **D-5** `adopt()` 改绑 | J1 | 目前唯一「连错误都不会报」的路径，J1 在它面前是空的 | 不拍板 = 已知漏洞长期挂着 |

「明确不做」清单见 §11 —— 那些条目分两类：一类**做不到**（Web Locks 锁在浏览器里、`expected` 模型手上没有），
一类**做得到但不服务上面的判据**（整页版本号、semanticKey 当主键、提精度）。后者才是本目标管得着的。

### 0.4 骨架与任务分层

**要防的错发生在「模型基于旧认知做决策 → 几百毫秒后动作落地」这两步之间 —— 它是异步的时间性错位，不是并发。**
串行化与互斥锁都作用不到「轮次之间人工点了一下」，唯一能挡的是**提交前的写前门**。
本轮修订就是把全案重心从「锁」挪到「门 + 通知」。

| 层 | 内容 | 前置 | 性质 |
|---|---|---|---|
| **P0** | 量事故分布（D-7=B：插件侧自计 STALE_REF 分桶 + 人工并发频率 + snapshot token 量） | 要写一小段生产代码 | **必做，最先**（落点见 §4） |
| **P1** | 提交前把关：写前门分档 + `adopt()` 就地换指针的处置 | 已批每次 mutate +1 往返 | **必做**（当前唯一的静默点错防线） |
| **P2** | 决策时通知：**跨轮次脏累加器** + 全回执夹带 + **tool 层与提示词落点**（不是实时推流） | P1 | **必做便宜半边**；①②③ 全套的排期判据见 §6.4 |
| **P3** | 记账与互斥：调用方归属 + 跨会话共用同一标签页的互斥 | P0 结论 | 条件性 |
| **P4** | 增量 diff | P0 两道门禁达标 | 条件性 |

## 1. 本轮修订的四条依据（都实测核对过）

1. **宿主已把工具调用串行化**。`webpage_*` 全部没声明 `isConcurrencySafe`，被宿主 fail-closed 闸门
   （`dsh-tools/lib/index.js:2953`）判 `exclusive`，agent loop 退化成 `for...await`
   （`dsh-agent-loop/lib/index.js:529-530`）。探针：`scripts/probe-tool-concurrency.mjs`
   （16/16 exclusive；`--selftest=leaky` 反向验证会翻成 parallel）。**证据只对它解析到的版本槽成立**，
   当前是 `.desktop-base/0.1.6-alpha.2/app/resources/dsh`（探针会印一行来源，别拿旧结论当新的）。
   → 初版 §3 的核心前提「两个 `webpage_click` 打同一 session 会真正交错」**在单会话内不成立**。
2. **「会话之间有隔离」是假象**。逻辑上确实一会话一标签页（`open()` 每次 `createTarget` + 独立
   `CdpConnection` + 独立 `RefRegistry`，`provider.ts:357-370`），但**权限上零隔离**：
   `require(sessionId)`（`provider.ts:1027`）对任何调用方给的任意 sessionId 都放行，
   `BrowserRuntime` 是进程内共享服务（`src/browser/index.ts:93`）。
   → **同一个 sessionId 就是同一份 ref 表、同一个连接**，两个对话各拿这个号即可互相踩。
3. **人工不经过 provider**，任何进程内串行与锁都作用不到它（初版 §4.5 已写对，本版挪为主轴）。
4. **同文档导航不会报 STALE_REF**：`backendNodeId` 不重新编号，常驻节点跨路由存活 →
   **静默点错是真实存在的**。初版「跨文档不会静默点错」只对**跨文档**成立（22/22 解析失败），
   本版把结论改窄。

## 2. 事故时序 × 现有保护（本方案的骨架）

```
① agent: webpage_snapshot  →  模型拿到 ref e12 + url
   ⋯⋯ 一轮推理，几秒~几十秒，页面期间被改 ⋯⋯
② agent: webpage_click(e12)  →  动作发出，打在模型从未见过的页面状态上
```

| 时刻 | 性质 | 现有保护 | 缺口 |
|---|---|---|---|
| ①→② 期间 | **异步，串行化原理上无效** | **无** | 跨轮次脏累加器 + 全回执夹带 → P2（§6.2） |
| ② 动作发出前 | 同步 | **无**（`click` 动作前只记 `beforeUrl` 供事后比对，`provider.ts:1502`） | **写前门 → P1，当前唯一防线** |
| ② 动作发出后 | 同步 | `detectNavigation`（`provider.ts:1866`，事后检出并作废） | 已「晚一步」，无法回收已发生的动作 |
| 同一时刻真并发 | 并发 | 宿主串行化（单会话内） | 仅剩跨会话共用 sessionId（`require` 无鉴权）+ 事件/通报链 → P3 |

## 4. P0 · 量事故分布（最先做，产出决定 P1-P4 的排期）

**取数入口（按 D-7=B 定为「插件侧自计」）**：本仓 `src/debug.ts` 只有 `DSH_BROWSER_PLUGIN_DEBUG`
与 `noteLoaded`，**既没有工具调用日志、也没有 debug 目录**（只有 stdout；且写 stderr 等于不写，
见 `debug.ts:8-10` 的注释）。所以 P0 要自己造一个计数落点，形态定成这样：

| 项 | 决定 | 理由 |
|---|---|---|
| 记什么 | `BROWSER_STALE_REF` 的抛出次数，按 `code` + 「哪道门拒的」（`resolve` 纪元不匹配 / `node_gone` / `identity_mismatch`）分桶 | 光有总数答不了 §4 表第一行 —— 要区分「换文档导致的旧号」和「同文档静默改绑」，后者才是 P1/P2 的目标 |
| 写在哪 | 新环境变量 `DSH_BROWSER_PLUGIN_METRICS=<目录>`；**未设置则整条计数为 no-op** | 不开关就等于默认关，正常运行不产生 IO；也不复用 `DSH_BROWSER_PLUGIN_DEBUG`（那个的语义是「打一行到 stdout」） |
| 落地形式 | 每会话一份 JSONL 追加行，进程退出/会话关闭时 flush | 崩溃丢最后几行不影响「分布」结论 |
| 退出条件 | **P0 结论写进本文件 §4 之后，整个计数模块连同调用点一并删掉** | 只为测量而写的生产代码，留着就是长期负债；留着必须在本文件标注「它还活着、为什么」 |

⚠️ **与 D-4 相冲**：这一条是**要写插件侧生产代码**的，不属于「本轮只重排文档」。动码前单独点头。

**三个数，分别卡住不同的门**：

| 要量什么 | 卡住哪个决定 | 判据 |
|---|---|---|
| `BROWSER_STALE_REF` 每会话命中次数 / 每会话轮次数 | P1 的细门要不要默认开、P2 的通知有多急 | 命中率高 → 优先做；接近 0 → P1 只做粗门 |
| 真实目标页面**单次全量 snapshot 的 token 量** | **P4 的总收益上限**（收益 = 变化率 × 单次体积） | 页面本身只有 3KB 级 → P4 直接出局，不必再测存活率 |
| 真实页面连拍两次的**模型可见行文本不变率** | P4 的第二道门禁 | ≥ 80% 才做，见 §8 原数据 |

**纪律**：P4 的判据必须是**行文本不变率**而不是 `backendNodeId` 存活率 —— 改 `value` 时后者存活、
前者已变（`snapshot.ts:338` 把 `value="…"` 印进行文本）。**口径混报本仓库已付过两次代价。**

**砍掉条件**：计数模块来不及建（或建了但跑不出样本）→ P0 降级为「2-3 个真实目标页面的 scripted
走查」（原选项 C），且必须在本文件标注
「P1/P3 的优先级是纯推理得出、未经数据验证」，不许日后被当成实测结论。

## 5. P1 · 提交前把关（核心，本轮查出的唯一静默点错防线）

### 5.1 写前门分档

`assertPreActionGate(session, target)`，与 §7 的队列语义**互不依赖**（没有锁也必须做），
插在 `resolveObjectId` 之后、派发输入事件之前。

| 档 | 查什么 | 开销 | 覆盖 | 不覆盖 |
|---|---|---|---|---|
| 粗 | `url` 变了 | 0 次额外往返，**但要先存**（见 §5.1.1 / D-6） | SPA 路由、人工导航、`location.href` | 同 URL 的局部改版、列表重排 |
| 中 | `loaderId` 变了 | 1 次 `Page.getFrameTree` | 换文档 | 同文档一切变更 |
| 细 | role / name / `isConnected` | 已在 `locate` 路径实测（`provider.ts:931-940`） | 元素被换掉 | **列表重排复用节点**（§10.5 已知缺口） |

**三档都要，但失败原因分开报**，复用既有语义不新造码：`document_changed` / `node_gone` /
`identity_mismatch`。D-3 已批 +1 往返，所以按
**「一次 `Runtime.evaluate` 同时读 url + 身份探针 + `isConnected`」** 实现，把三档压进 1 次往返。

**必须写清的边界（否则会被误当兜底完备）**：
「URL 变了 → 旧 ref 作废」是**充分**条件，不是**必要**条件。tab 切换常用
`history.replaceState` 改 URL 而文档没变 → 粗门会**误伤**；列表重排不改 URL → 粗门**完全漏**，
只有细门能挡一部分。**没有哪一档是全集**，这就是分档而不是单门的原因。

**不做调用方传 `expected`**。原 T2 让调用方传 `loaderId` / `backendNodeId`，但**模型只看得见
ref 号 `e12`**，这两个值从没出现在 outline 里 → 没人能传，约等于死代码；且
`BrowserMutationRequest` 是 5 分支 union（`src/browser/types.ts:241-274`），共享字段要改 7 处。
provider 侧东西全在手边：发布时刻的 `RefRegistry.loaderId`（`refs.ts:101`，`publish` 时写入 161）
+ `RefTarget` 的 role/name（`refs.ts:32-42`）。

**验收**：人工在 SPA 上换路由后拿旧 ref 操作 → 明确报错且**动作未发出**；
不传任何参数的正常路径 → 与今天行为一致（只是多一次内部往返）。

#### 5.1.1 前置：粗门今天**没有数据源**（本轮自查出的漏写）

上表写「粗门 0 次额外往返，`session.url` 是现成的」—— 这话只对了一半：`session.url` 是
**此刻**的地址，而粗门要比的是「**模型拍下那份快照时**的地址」。这两个值今天不存在任何一处记录里：

- `RefTarget` 只有 `ref / role / name / backendNodeId / semanticKey`（`refs.ts:32-42`），**没有 url**；
- `ArchivedEpoch` 只有 `epoch / loaderId / target`（`refs.ts:59-62`），也没有；
- `session.url` 会被**任何**一次读页面动作刷新（`provider.ts:1107`），刷新者未必是发起操作的那个调用方。

所以「0 额外往返」的成立条件是：**先有一个地方存住发布时刻的 url**。**D-6 已定为 B** ——
不在 `RefTarget` 上加字段，而是在 `RefRegistry` 上加「**纪元 → url**」一条记录（`publish` 时与
`loaderId` 同时写入，见 `refs.ts:161` 的相邻位置），粗门查的是 `ref → 它所属纪元 → 那份 url`：

- **为什么不选 A（每条 ref 带自己那份 url）**：`RefTarget` 已经在 `exportBindings()` / 软淘汰 /
  LRU 那条持久化链上，每条都加一份长 url 是把体积成本转嫁给刚做过瘦身的那条链。纪元级记录一条顶一千条。
- **代价（要认的）**：多一层「ref 属于哪个纪元」的间接，`restore` / `adopt` 路径各要对齐一次 ——
  `adopt()` 不推 epoch（§5.2），所以**区域快照装上的 ref 天然共享当前纪元的 url**，
  那份 url 可能是更早一次全量 snapshot 写进去的，**比 ref 本身旧**。粗门对此的诚实表述是
  「快照纪元的地址」，不是「这个元素的地址」。
- **B 之外的第三选项 C（只查 `ArchivedEpoch.loaderId`）已否**：那等于放弃 SPA 覆盖，
  而 SPA 恰是 §1.4 唯一没被兜住的场景。

这一条要连同「软淘汰 / 同号复活」一起过一遍持久化口径：`exportBindings()` 落盘的是 `{ref, semanticKey}`
（`refs.ts:73-82`），**restore 回来的 ref 天生没有 url / loaderId** → P1 的细门对「重启恢复的 ref」
按现成纪律走 revalidate 四道门，不许直接信任裸 `backendNodeId`（跨文档那个 id 会重新编号）。

**顺带一处注释与实测冲突**：`refs.ts:28-30` 称 `backendNodeId` 是「CDP 的跨导航稳定 id」。
按 §10.4 的实测（跨文档 22/22 解析失败），它在**跨文档后并不稳定**，稳定的只有同文档内。
下轮改代码时顺手把这句注释改窄，否则会误导下一个接手的人拿它当跨导航锚点。

### 5.2 待决项 D-5 · `adopt()` 会就地换指针（本轮查出，未修）

**一句话**：区域快照会让「ref 号没变」这件事失去含义 —— 号还是 `e12`，指的东西已经换了，
而且**从换掉那一刻起到下次点击之间，没有任何一处代码知道发生过什么**。

逐步看这条链（每步都能回源码）：

| 步 | 发生什么 | 依据 | 位置 | 模型看得见吗 |
|---|---|---|---|---|
| 1 | 模型拍全量快照，拿到 `e12 = 提交按钮`（`backendNodeId=4501`），epoch=7 | `publish()` 推进 epoch、记 loaderId | `refs.ts:161-162` | ✅ 回执里有 e12 |
| 2 | **人工在同一个文档里改了页面**（SPA 重渲染，把「提交」换成「提交并抄送」） | —— 插件不参与 | —— | ❌ 无事件可订 |
| 3 | 模型为了看某个区域，拍一次**区域快照** | `snapshot()` 走 `adopt()` 而不是 `publish()` | `provider.ts:1103` | ⚠️ 回执只含那个区域 |
| 4 | `adopt()` **不推进 epoch、不改 loaderId** | 对照 `publish()` 的 161-162，这里两行都没有 | `refs.ts:174-188` | ⚠️ 回执还是「epoch 7」 |
| 5 | 「提交并抄送」的 semanticKey 恰好与 `e12` 唯一命中 → **复用同一个号**，把 `backendNodeId` 就地改成 4788 | `bindRow` 的 `live.set(existing.ref, updated)` | `refs.ts:325-330` | ❌ 回执只说「区域里有 e12」 |

所以它防不了这次改绑 —— 它会告诉模型「e12 没问题」。

## 6. P2 · 决策时通知（本轮重做：落点从「provider 加字段」改成「跨轮次累加器 + 全回执」）

### 6.0 原则：拉而不推

**人工动的那一刻模型没在读上下文**，推给它的消息要么打断当前 turn（要宿主配合开一条注入通道），
要么落到没人看的地方。真正需要通知的时机是**它下一次伸手的时候，告诉它刚才有人伸过手**。
所以 P2 的形态是「**攒着，下一次回执夹带**」，不是「实时推流」。

### 6.1 现状：这条链路已经有一半，缺三处（全部实测核对）

| 环节 | 现状 | 位置 |
|---|---|---|
| 信号源 | 宿主发私有编排消息 `{type:'takeover', tabId, active}`，**故意不走 CDP 事件流** | `src/browser-electron/bridge.ts:220`、`:576-581` |
| 接收 | `transport.onTakeover(...)` → `setTakeover()` 置**幂等状态位** `session.takeover` | `src/browser-electron/provider.ts:105`、`src/browser-cdp/provider.ts:1006-1008` |
| 交给模型 | 只有 `webpage_snapshot` 回执头一行 `NOTE: a human has DevTools open…` | `src/tool-browser/index.ts:220-223`、`provider.ts:1128`、schema `:1204` |

三个缺口：

1. **语义是「DevTools 开着」，不是「人工改过页面」**。人工点了按钮、改了地址栏而没开 DevTools → 零信号。
   且 `provider.ts:999` 自己写明：直连外部 Chrome 的 `cdp` provider **没有这条通道，状态位恒 `false`**。
2. **通知面只有 snapshot**。人工操作落在两轮之间，而模型下一轮往往是 `webpage_click` —— 那条回执上
   没有任何痕迹，于是它**结构性地看不到**：只有恰好在动手前拍了一次快照才看得见。
3. **`markTakeover` 在生产里没有调用者**（只有 `state.test.ts` 在调）。`TargetStateRegistry` 的
   `{owner, at, applied, previous}` 记账与 `contended()` 的「谁占着、何时」文案（`state.ts:245-251`）
   全是现成的，但 takeover 通道没接它（`provider.ts:1008` 只翻状态位）→ 「谁改的、几点改的」无从可报。

### 6.2 要做形态（按性价比排，三条都不引入新机制）

| # | 做什么 | 复用的既有件 | 为什么便宜 |
|---|---|---|---|
| ① | `session.takeover: boolean` → **跨轮次脏累加器**：分类计数 `navigated`（`Page.frameNavigated`）/ `withinDocument`（`Page.navigatedWithinDocument`）/ `takeoverWindow` | `Page.enable` 在 `open()` / `adoptSession()` 已经发过（`provider.ts:373`、`:437`）；事件订阅照 `console.ts:209` 的 `connection.on(...)` 形状 | 不用多开任何 CDP 域 |
| ② | **挂到所有回执**（至少 snapshot + mutate 全族），文案给**动作**不给状态 | `tool-browser/index.ts:205-224` 的 `notes.unshift(...)` 已是这个形状 | 改渲染 + output schema，不动判定逻辑 |
| ③ | 脏累加器同时写进 `TargetStateRegistry`，让「谁 / 何时」真的可报 | `state.ts` 的 owner 记账 + `contended()` 文案 | 把 ① 的事件顺手接上，别另起炉灶 |

**文案口径**：不要「内容随时可能变」（描述状态，模型无从决策），要
「上次快照之后页面导航过 1 次（`A → B`），你手里的 `e12` 来自旧文档 → 先 `webpage_snapshot` 再操作」。

### 6.3 边界与不做（原判断全部保留）

- **⚠️ 不做「检出即 `invalidate()`」**：核武器，时钟/轮询/SSE 都会被判成变更 → 反复作废 →
  上下文暴涨。教训已在 `src/browser/types.ts:183` 写过一遍（开合 DevTools 绝不推进纪元），
  不犯第二次。只有**真导航**（离散事件，不刷屏）配触发作废。
- **不做 DOM mutation 实时推流**：要 `DOM.enable` 多开一域事件流，而 `[V36]` 实测证明整条定位链路
  本来不需要它；代价是轮询类页面把通知刷成噪声（与上一条同源的教训），收益只是省一次 snapshot 往返。
- **事件通道会漏，别当全集**：`provider.ts:2047` 已记下 `Page.loadEventFired` 的两个坑 ——
  事件可能在 `Page.enable` **之前**就发过（空白页、缓存页），SPA 软导航又可能根本不发。
  `navigatedWithinDocument` 覆盖 pushState 这条**尚未实测**，落地前要用 live 组（`DSH_CDP_ENDPOINT`
  + 无头 Chrome）验一次，别照 CDP 文档的承诺写进回执文案。
- **通知不是兜底，是优化**：纯 JS 改 DOM（`textContent`、列表重排）不产生任何导航事件，P2 完全看不见；
  D-5 那条静默改绑链就是这么来的。**保命靠 P1 的写前门。**
- **与 `detectNavigation` 去重**，与 `takeover` 定清是一个维度还是两个：`takeover` = 「有人在操作」，
  `dirtySince` = 「页面自那份快照之后变过」，两者不等价。否则回执会出现
  `takeover:false` + `changed:true` 这种自相矛盾的信号。

### 6.4 最后一公里与砍掉条件（原 §6.1 保留）

初版全部落点都在 provider + `types.ts`，**`src/tool-browser/index.ts` 一次都没出现** ——
而「告知模型」的落点是**工具回执字段 + 工具 schema + 系统提示词**
（提示词在 `tool-browser/index.ts:2029-2040`）。没有这一层，「加一个回执字段」等于没做：
字段塞进去了，模型不知道该拿它做什么。

**必须一并交付**：回执字段名与文案、`webpage_snapshot`/`mutate` 的 output schema、提示词里一句
「看到 `changed=true` 时先重新 observe 再操作」。**砍掉条件**：真机走查发现模型无视该字段 →
整条砍掉，不留装饰性信号。

**排期判据**：①②③ 整条只在 P0（D-7=B 的自计）显示「人工操作落在 agent 两轮之间」的频次高到
snapshot 白跑次数可观时才做；否则 P1 的门就够，P2 可以一直不做。

## 7. P3 · 记账与互斥（原 T5 + T1 合并评估）

**先纠正一个假前提**：「会话之间有隔离」只成立于「一会话一标签页」这一层（§1.2）。
provider **没有任何调用方鉴权**，`require()` 照单全收。所以：

- **两个对话各开各的标签页 → 天然互不干扰**，不需要锁；
- **两个对话操作同一个标签页，唯一途径是共用同一个 sessionId**（人工把号传过去，或子 agent
  继承上下文）。此时锁键相同，互斥**正常生效** —— 初版「互斥永不触发」的推论是错的。

**因此第一件事不是锁算法，是归属**：`Map<sessionId, {holder, at, ttl?}>` 落在 provider 实例上
（不是页面里，Web Locks 用不上）。没有 `holder`，冲突时既回不了「谁占着这个标签页」，
也做不了「只有持有者能续约 / 释放」。沿用 `state.ts` 的 `{owner, at, applied, previous}` 记账风格，
owner 取值从 `'agent' | 'human'`（`state.ts:50`）扩成调用方 id，**别另起炉灶**。

- **TTL 取决于跨进程与否**（仍待确认）：同进程崩溃即全挂，`try/finally` + `AbortSignal` 够；
  跨进程崩溃会留僵尸锁，TTL 才有价值。**没有证据前不做 TTL。**
- **串行队列只保护「同一标签页上的并发写者」**（跨会话共用 sessionId + 事件/通报链）。
  它**不是**任何事故的主防线，主防线是 P1。排期在 P0 出数之后，若 §4 显示共用 sessionId 从未发生，
  **整条 P3 可以一直不做**。
- **入队带 epoch 栅栏**（若真做队列）：入队记 `refs.epoch`，出队时 epoch 已推进就以既有
  `BROWSER_STALE_REF` 失败 —— 排队期间页面被顶替的意图不该被执行。约 5 行，零新错误码。

## 8. P4 · 增量 diff（条件性，两道门禁都在 P0）

只在 P0 两道门禁都达标后做。四条硬要求原样保留：

1. **主键 = `backendNodeId`**，semanticKey 只做兜底（未命中且两侧唯一才复用）。
2. **`changed` 判定必须含 value + reported properties**，不能只比 `name`。
3. **重建检测**：存活率低于阈值（建议 50%）自动退全量。
4. **逃生舱** `full: true`；首次 / 导航后 / 距上次超 N 步强制全量。

**口径纪律**：diff 必须基于**模型所见视图**（折叠后 + `unfoldedLines` 语义），不能基于全量 `rows`，
否则出现「我视图里没有的 ref 被列为 unchanged」—— 这正是 `FOLD_MARKER_PREFIX` 存在的原因。
`changed` 计数与 `droppedElements` / `foldedRepeats` / `truncatedByBudget` 分开报。

**实测依据（2026-09-18，无头 Chrome 153）**：

| 场景 | backendNodeId 存活 | +semanticKey 兜底 |
|---|---|---|
| 没变 / 追加一条 / 改文本 / 改 value | 100% | 100% |
| 列表整体重建（`innerHTML` 重赋值） | **8%** | **42%** |
| 整页 reload | 0% | 36% |

semanticKey 唯一命中率实测 **39.4%**（撞车只有「翻译此页」×10、「查看详细信息」×10 两组，
因为 `listitem` 无可访问名称）→ **它只能兜底，不能当主键**；且低唯一率本身是防错配的安全特性。

## 10. 保留的原始论证（对照区）

2. **同文档内 `backendNodeId` 稳定且唯一**，`revalidate` 的四道门（loaderId → backendNodeId →

3. **人工 + agent 并发：锁无用，只能靠检测与通知** —— 人工不经过 provider，锁不住人。

5. **已知缺口，记下不做**：列表重排时 DOM 节点被复用，`backendNodeId` 不变、`ancestorPath` 仍是

### D-5 · `adopt()` 就地换指针算不算缺陷 —— **未定（主上回「没懂」）**

**背景**：7 步的事故序列已经在 §5.2 逐步列全（每步带 `file:line`）。压缩成一句：
`adopt()` 不推 epoch、不改 loaderId（`refs.ts:174-188`），却会在 semanticKey 唯一命中时
把同一个 ref 号装上新的 `backendNodeId`（`refs.ts:325-330`），而 `revalidate` 对当前表命中
直接返回成功且**一次 CDP 都不发**（`provider.ts:1253-1255`）—— 所以「号没变」不再蕴含
「指的东西没变」，且这条链上没有任何机制会报警。

| 选项 | 利 | 弊 |
|---|---|---|
| A. 认定缺陷：`adopt()` 命中即推进 epoch | 语义最干净：「号没变 = 指的东西没变」重新成立 | 区域快照的核心卖点（不作废其它 ref）被废掉，等于砍功能 |
| B. 认定特性：注释 + 提示词写明「区域快照会静默改绑 ref」 | 零行为改动；诚实 | 把担子全压给模型，而它手上只有 role/name，判不出被改绑 |
| C. 折中：回执加 `reboundRefs`，只报不作废 | 保留卖点又可观测；与 P2 的脏累加器同一套机制（§6.2 ②） | 又一个模型可能无视的字段（§6.4 的砍掉条件照样适用） |

**我的建议**：C，且**只在 P2 一并交付**（单独加字段不值当）。A 需要重新设计区域快照语义，
