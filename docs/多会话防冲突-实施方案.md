> 按**事故轴 × 时刻轴**重排。取代原「并发轴」骨架与 T0-T5 编号（映射见 §9）。
> **目标与验收判据在 §0** —— 要往本文加任何任务，先把它填进 §0.3 的追溯表，填不出「服务 J 几」就不做。

## 0. 目标

### 0.1 一句话目标

**让人工与多会话共用同一个页面时，agent 不再「基于旧认知静默点错」：要么动作正确落地，要么明确失败并告诉它为什么、下一步做什么。**

不追求的是「防止人工和 agent 同时操作」——那做不到，也不需要。**追求的是不静默。**
判据全在「静默」两个字上：报错但没人知道，等于没防住；防住了却把正常路径也堵住，那是另一种事故。

### 0.2 三条验收判据（每条都能测；说不出服务哪条的任务一律不做）

| # | 判据 | 怎么算达标 | 阈值来源 |
|---|---|---|---|
| **J1** | **零静默** | 任何一次基于 ref 的动作，若落地时的页面状态与模型拍快照时不是同一份 → **报错且动作未发出**（不是事后告警） | 走查用例：SPA 换路由、同文档改 DOM（含列表重排）、D-5 那条区域快照改绑 |
| **J2** | **不误伤** | 人工没动时，写前门不得让正常路径失败、也不得多出无谓重拍 | 误伤率上限等 P0 出数（§4） |
| **J3** | **不炸上下文** | 新增通知字段 + 强制重拍的 token 成本，不得吃掉单次快照的预算 | 单次全量 snapshot 的 token 量，P0 量 |

**这三条同时是砍刀的落点**：判据不达 → 对应任务砍或降级，不是补更多字段。已有的三处砍掉条件
（§4 纯推理标注、§6.4 模型无视即整条砍、§12 止损表）都挂在这里。

### 0.4 骨架与任务分层

**要防的错发生在「模型基于旧认知做决策 → 几百毫秒后动作落地」这两步之间 —— 它是异步的时间性错位，不是并发。**
串行化与互斥锁都作用不到「轮次之间人工点了一下」，唯一能挡的是**提交前的写前门**。
本轮修订就是把全案重心从「锁」挪到「门 + 通知」。

| 层 | 内容 | 前置 | 性质 |
|---|---|---|---|
| **P0** | 量事故分布（D-7=B：插件侧自计 STALE_REF 分桶 + 人工并发频率 + snapshot token 量） | 要写一小段生产代码 | **取数已落地**（2026-09-19）；**待跑数**，出结论后按 §4 删模块 |
| **P1** | ~~提交前把关~~ **已落地**：写前门（粗 url + 细 `isConnected`，合成 1 次往返）。剩 `adopt()` 就地换指针的处置（D-5） | 已批的 +1 往返已用满 | **必做**（当前唯一的静默点错防线） |
| **P2** | 决策时通知：**跨轮次脏累加器** + 全回执夹带 + **tool 层与提示词落点**（不是实时推流） | P1 | **必做便宜半边**；①②③ 全套的排期判据见 §6.4 |
| **P3** | 记账与互斥：调用方归属 + 跨会话共用同一标签页的互斥 | P0 结论 | 条件性 |
| **6.5** | 显式控制权：标签条「接管 / 交还」按钮 + agent 持有期吞人工**键盘**（A 档） | 探针**已跑**（§6.5，8/8） | **已落地**（2026-09-19），**不替代 P1** |
| **P4** | 增量 diff | P0 两道门禁达标 | 条件性 |

## 1. 本轮修订的四条依据（都实测核对过）

1. **宿主已把工具调用串行化**。`webpage_*` 全部没声明 `isConcurrencySafe`，被宿主 fail-closed 闸门
   （`dsh-tools/lib/index.js:2953`）判 `exclusive`，agent loop 退化成 `for...await`
   （`dsh-agent-loop/lib/index.js:529-530`）。探针：`scripts/probe-tool-concurrency.mjs`
   （16/16 exclusive；`--selftest=leaky` 反向验证会翻成 parallel）。**证据只对它解析到的版本槽成立**，
   当前是 `.desktop-base/0.1.6-alpha.2/app/resources/dsh`（探针会印一行来源，别拿旧结论当新的）。
   → 初版 §3 的核心前提「两个 `webpage_click` 打同一 session 会真正交错」**在单会话内不成立**。
2. **「会话之间有隔离」是假象**。逻辑上确实一会话一标签页（`open()` 每次 `createTarget` + 独立
   `CdpConnection` + 独立 `RefRegistry`，`provider.ts:359-371`），但**权限上零隔离**：
   `require(sessionId)`（`provider.ts:1038`）对任何调用方给的任意 sessionId 都放行，
   `BrowserRuntime` 是进程内共享服务（`src/browser/index.ts:93`）。
   → **同一个 sessionId 就是同一份 ref 表、同一个连接**，两个对话各拿这个号即可互相踩。
3. **人工不经过 provider**，任何进程内串行与锁都作用不到它（初版 §4.5 已写对，本版挪为主轴）。
4. **同文档导航不会报 STALE_REF**：`backendNodeId` 不重新编号，常驻节点跨路由存活 →
   **静默点错是真实存在的**。初版「跨文档不会静默点错」只对**跨文档**成立（22/22 解析失败），
   本版把结论改窄。

## 2. 事故时序 × 现有保护（本方案的骨架）

```
① agent: webpage_snapshot  →  模型拿到 ref e12 + url
   ⋯⋯ 一轮推理，几秒~几十秒，页面期间被改 ⋯⋯
② agent: webpage_click(e12)  →  动作发出，打在模型从未见过的页面状态上
```

| 时刻 | 性质 | 现有保护 | 缺口 |
|---|---|---|---|
| ①→② 期间 | **异步，串行化原理上无效** | **无** | 跨轮次脏累加器 + 全回执夹带 → P2（§6.2） |
| ② 动作发出前 | 同步 | **写前门**（`assertPreActionGate` `provider.ts:1424`，已落地：查顶层文档 url + `isConnected`，`restore()` 会回填纪元 url） | 同文档改绑（`adopt()` 那条，§5.2 / D-5）仍全绿 |
| ② 动作发出后 | 同步 | `detectNavigation`（`provider.ts:1971`，事后检出并作废） | 已「晚一步」，无法回收已发生的动作 |
| 同一时刻真并发 | 并发 | 宿主串行化（单会话内） | 仅剩跨会话共用 sessionId（`require` 无鉴权）+ 事件/通报链 → P3 |

## 4. P0 · 量事故分布（最先做，产出决定 P1-P4 的排期）

**取数入口（按 D-7=B 定为「插件侧自计」）**：本仓 `src/debug.ts` 只有 `DSH_BROWSER_PLUGIN_DEBUG`
与 `noteLoaded`，**既没有工具调用日志、也没有 debug 目录**（只有 stdout；且写 stderr 等于不写，
见 `debug.ts:8-10` 的注释）。所以 P0 要自己造一个计数落点，形态定成这样：

| 项 | 决定 | 理由 |
|---|---|---|
| 记什么 | `BROWSER_STALE_REF` 的抛出次数，按 `code` + 「哪道门拒的」（`resolve` 纪元不匹配 / `node_gone` / `identity_mismatch`）分桶 | 光有总数答不了 §4 表第一行 —— 要区分「换文档导致的旧号」和「同文档静默改绑」，后者才是 P1/P2 的目标 |
| 写在哪 | 新环境变量 `DSH_BROWSER_PLUGIN_METRICS=<目录>`；**未设置则整条计数为 no-op** | 不开关就等于默认关，正常运行不产生 IO；也不复用 `DSH_BROWSER_PLUGIN_DEBUG`（那个的语义是「打一行到 stdout」） |
| 落地形式 | 每会话一份 JSONL 追加行，进程退出/会话关闭时 flush | 崩溃丢最后几行不影响「分布」结论 |
| 退出条件 | **P0 结论写进本文件 §4 之后，整个计数模块连同调用点一并删掉** | 只为测量而写的生产代码，留着就是长期负债；留着必须在本文件标注「它还活着、为什么」 |

⚠️ **与 D-4 相冲**：这一条是**要写插件侧生产代码**的，不属于「本轮只重排文档」。动码前单独点头。

**三个数，分别卡住不同的门**：

| 要量什么 | 卡住哪个决定 | 判据 |
|---|---|---|
| `BROWSER_STALE_REF` 每会话命中次数 / 每会话轮次数 | P1 的细门要不要默认开、P2 的通知有多急 | 命中率高 → 优先做；接近 0 → P1 只做粗门 |
| 真实目标页面**单次全量 snapshot 的 token 量** | **P4 的总收益上限**（收益 = 变化率 × 单次体积） | 页面本身只有 3KB 级 → P4 直接出局，不必再测存活率 |
| 真实页面连拍两次的**模型可见行文本不变率** | P4 的第二道门禁 | ≥ 80% 才做，见 §8 原数据 |

**纪律**：P4 的判据必须是**行文本不变率**而不是 `backendNodeId` 存活率 —— 改 `value` 时后者存活、
前者已变（`snapshot.ts:338` 把 `value="…"` 印进行文本）。**口径混报本仓库已付过两次代价。**

**砍掉条件**：计数模块来不及建（或建了但跑不出样本）→ P0 降级为「2-3 个真实目标页面的 scripted
走查」（原选项 C），且必须在本文件标注
「P1/P3 的优先级是纯推理得出、未经数据验证」，不许日后被当成实测结论。

## 5. P1 · 提交前把关（核心，本轮查出的唯一静默点错防线）

### 5.1 写前门分档 —— **已实现**（`provider.ts:1424` `assertPreActionGate`）

插在 `resolveObjectId`（`provider.ts:1384`）拿到 `objectId` 之后、任何输入事件派发之前。
`click` / `fill` / `press` / `scroll(带 ref)` / `wait(带 ref)` 五条动作路径共用这一处。

| 档 | 查什么 | 开销 | 覆盖 | 不覆盖 |
|---|---|---|---|---|
| 粗 | 当下**顶层文档**的 `window.top.location.href` != 纪元记下的 url | 与细门合并在**同一次** `Runtime.callFunctionOn` | SPA 路由、人工导航、`location.href` | 同 URL 的局部改版、列表重排、**跨源子 frame**（读不到顶层地址 = 没证据）、**子 frame 内部 `pushState`**（顶层地址不动、`backendNodeId` 不重编 → 这一档整体失明） |
| 细 | `this.isConnected === false` | 同上（不额外花命令） | 元素被换掉 / 被移除 | **列表重排复用节点**（§10.5 已知缺口） |
| ~~中~~ | `loaderId` 变了 | —— | **本轮不做**，理由见下 | |

**粗门读顶层而不是 `location.href`**（第 2 批改的，别改回去）：`objectId` 属于元素**自己那个**
文档，而纪元里存的是顶层地址（`readPageMeta` 读主 frame 的 `location.href`）—— 拿子 frame 的
`location.href` 去比，**同一个文档里的 iframe 元素必然「地址变了」**，一次正常点击会被判成导航并作废
整张 ref 表（两路 review 都独立指到这条）。现在脚本 `try { window.top.location.href } catch → null`：
同文档子 frame 仍可比（顶层地址可读），跨源子 frame 读顶层抛 `SecurityError`（**按规范推断，未实测**，
`[ ]` 待补测）→ 那一档没证据 → 放行。
**那个 `try` 的真实用途要说清**：它不是为了让粗门多覆盖一档（跨源本来就读不到），而是为了让
**同一次往返仍然带回 `isConnected`** —— 不兜住异常，整个 `callFunctionOn` 就没有返回值，
**跨源 frame 里连细门都会一起静默**。这条已由 `provider.test.ts:1041` 钉住（摘掉 `try` 即红）。

**读顶层换来的失明代价**（第 4 批认下来的，第 2 批只认了误伤方向）：同源子 frame
**自己** `pushState` 换路由时，顶层地址一动不动、`backendNodeId` 也不重编 → 粗门与细门同时失明。
代价可接受的理由：这种页面在本产品的目标站点上是少数，而反过来（读子文档）是**每次都误伤**；
两害相权取了失明。真要做，得给 `RefTarget` 存「它属于哪个 frame」并逐 frame 比 url —— 不在本轮范围。

**中门为什么砍掉**（实测口径修正，不是省事）：它能抓到而粗门抓不到的只有一类 ——
**地址不变的整页刷新**。而那类刷新必然产生新文档，旧 `backendNodeId` 解析直接失败：
`resolveNodeObjectId` 已经在门**之前**把它兜成 `BROWSER_STALE_REF`（跨文档 22/22 失败，§10.4）。
再花一次 `Page.getFrameTree` 买到的是重复覆盖。role/name 档（同文档重排）也不在本轮，
与 `locate` 的口径一致 —— 那是已知剩余漏报区间，别当已兜住。

**整条 mutate 路径的净开销 = +1 次往返**，正是 D-3 批的那一次。读页面元信息的
`Runtime.evaluate` 本来就在 snapshot 里，不算新增。

原设计是「三档都要、各查各的」，落地时按实测收敛成上面那行 ——
**别照旧表去补中门**，补了也只是把 `resolveNodeObjectId` 已经报的错提前一档说一遍。

**必须写清的边界（否则会被误当兜底完备）**：
「URL 变了 → 旧 ref 作废」是**充分**条件，不是**必要**条件。tab 切换常用
`history.replaceState` 改 URL 而文档没变 → 粗门会**误伤**；列表重排不改 URL → 粗门**完全漏**，
只有细门能挡一部分。**没有哪一档是全集**，这就是分档而不是单门的原因。

**三处与方案原设想不同，接手以这里为准**：

#### 5.1.1 前置：粗门当时**没有数据源**（自查出的漏写 → 已按 D-6=B 补上）

旧表写「粗门 0 次额外往返，`session.url` 是现成的」—— 这话只对了一半：`session.url` 是
**此刻**的地址，而粗门要比的是「**模型拍下那份快照时**的地址」。这两个值当时不存在任何一处记录里：

- `RefTarget` 只有 `ref / role / name / backendNodeId / semanticKey`（`refs.ts:33-43`），**没有 url**；
- `ArchivedEpoch` 只有 `epoch / loaderId / target`（`refs.ts:59-61`），也没有；
- `session.url` 会被**任何**一次读页面动作刷新（`provider.ts:1120`），刷新者未必是发起操作的那个调用方。

所以「0 额外往返」的成立条件是：**先有一个地方存住发布时刻的 url**。**D-6 已定为 B，并已按 B 落地** ——
不在 `RefTarget` 上加字段，而是在 `RefRegistry` 上加「**纪元 → url**」一条记录（`epochUrl`
`refs.ts:113`，与 `loaderId`（`refs.ts:102`）在 `publish` 里同时写入 `refs.ts:192` 与 `:195`；粗门读 `publishedUrl`
`refs.ts:150`），粗门查的是 `ref → 它所属纪元 → 那份 url`。**写侧两个写入点各自归一**：`publish`
（`refs.ts:195`）与 `restore`（`refs.ts:242`）都把空串归一成「没证据」，因为 `epochUrl` 的语义只有
两态 —— 让 `''` 混进来会同时弄瞎粗门和挡住下面的 `restore()` 回填。第 3 批查出的是 `publish` 那条
（少它等于 Spec#6 换个地方重现）；`restore` 那条**不是防御性冗余**：`readPageMeta` 在
`location.href` 不是字符串时返回 `{ url: '' }`，空串确实能走到这里（`refs.test.ts:386` 钉住）。

选 B 的理由与要认的代价：

- **为什么不选 A（每条 ref 带自己那份 url）**：`RefTarget` 已经在 `exportBindings()` / 软淘汰 /
  LRU 那条持久化链上，每条都加一份长 url 是把体积成本转嫁给刚做过瘦身的那条链。纪元级记录一条顶一千条。
- **代价（要认的）**：多一层「ref 属于哪个纪元」的间接，`restore` / `adopt` 路径各要对齐一次 ——
  `adopt()` 不推 epoch（§5.2），所以**区域快照装上的 ref 天然共享当前纪元的 url**，
  那份 url 可能是更早一次全量 snapshot 写进去的，**比 ref 本身旧**。粗门对此的诚实表述是
  「快照纪元的地址」，不是「这个元素的地址」。
- **B 之外的第三选项 C（只查 `ArchivedEpoch.loaderId`）已否**：那等于放弃 SPA 覆盖，
  而 SPA 恰是 §1.4 唯一没被兜住的场景。

持久化口径一并核过：`exportBindings()` 落盘的仍是 `{ref, semanticKey}`（`refs.ts:74-77`、`318`），
**纪元 url 不落盘** —— `hydrate()` 把它清空（`refs.ts:336`），所以重启后第一轮粗门无证据、
按「拿不到证据就放行」的纪律不拦。这不是漏：`hydrate` 之后 `resolve` 在未 publish 前仍是
`BROWSER_SNAPSHOT_REQUIRED`，等新进程第一次 `publish` 装上 url，粗门就重新有依据了。
细门对「重启恢复的 ref」仍按现成纪律走 revalidate 四道门，不许直接信任裸 `backendNodeId`
（跨文档那个 id 会重新编号）。

**`restore()` 只填空值，是对粗门的一处续命（第 2 批补的，别改回去）**：链条是
「粗门命中 → `invalidate()` 清空 `epochUrl`（`refs.ts:280`）→ 模型 `webpage_revalidate` 把 ref
装回当前纪元（`restore()`）→ 这一纪元从此 `publishedUrl` 为空」。没有回填的话，**被写前门拦住过
一次的纪元，反而永久关掉了写前门** —— 正是第 1 批 review 查出的 Spec#6。所以 `restore(targets, observedUrl?)`
（`refs.ts:237-244`）只在 `epochUrl` 为空时写入调用方当下读到的地址，**已有值一律不覆盖**
（全量快照那份才算「发布时刻」，`adopt` 同理由）。

**回填那份地址的来源，第 3 批改错过一次、第 4 批改回来了**（别照着第 3 版的说明写代码）：
第 3 批为了省一次往返，让 `revalidate` 把 `Page.getFrameTree` 一次读到的 `loaderId` **和** `url`
一起用（当时的 `readMainFrameState`）。问题是这两个值**不同源** —— frame tree 里主 frame 的 url
是**浏览器进程侧的镜像**，而粗门比的是**渲染进程侧**的 `window.top.location.href`；导航在飞、
重定向链、以及特权页（renderer 读回 `about:blank#blocked` 而镜像报真地址）这三类情况下两者会差
一档，于是粗门会拿着一个渲染进程**从来没报过**的地址去判 —— 直接违 J2（误伤），而且命中即
`invalidate()` 作废整个纪元。所以：
`readMainFrameState` 已改回只读 `loaderId` 的 `readMainLoaderId`（`provider.ts:1237`），
纪元地址一律走 `readPageMeta`（**与门同源**）；代价是**只在纪元缺依据时**多一次 `Runtime.evaluate`
（回填点 `provider.ts:560`-`:564`），常态仍然零额外往返。**「省一次往返」输给「两个值必须同源」**，
这条记在这儿免得下次又有人来「优化」。
（顺带说清：`revalidate` 里那次 `loaderId` 读**不是**上面砍掉的中门复活 —— 它是归档恢复的文档身份
核验，早于写前门就存在；门的判定仍然只看 url + `isConnected` 两档。）

`snapshot()` 那边本来就是两次相邻的读（`readPageMeta` 给地址、`readMainLoaderId` 给身份，
`provider.ts:1114`-`:1118`）—— 那里的注释是诚实表述（「随这份 ref 表一起落地」，不是「同一瞬间」；
粗门是启发式不是事务）。
读不到（`undefined` / 空串）就当没证据，绝不写。

**回填会外溢到同纪元其它 ref（要认的代价，第 4 批补记）**：`epochUrl` 是**纪元级**的，一次回填
等于给整张表换了一个基线，而那张表里可能有**这次根本没被恢复**的 ref。具体形态：某次 `publish`
没读到地址（`readPageMeta` 失败）+ 表非空 → 人工 SPA 到 B → `revalidate` 任意一条 → 全表基线成 B
→ 那些仍在 A 上观察到的 ref，之后 B→B 的操作门不拦。诚实说清楚：**这不比「不回填」更坏**
（不回填时门同样不拦，只是从「假装有依据」变成「明确没依据」），但别把它当成「回填只影响被恢复
的那条 ref」。要真做到不影响，得回到 D-6=A（每条 ref 自带 url），那笔体积成本 §5.1.1 上面已经否过。

诚实表述：回填进去的是「恢复那一刻的地址」，比「发布时刻」晚，所以它只保证「这一纪元重新有依据」，
不保证那条依据等于模型当初拍快照时的地址。
测试：`refs.test.ts:370`（空纪元被填上、且已有值不被 `restore` 改写）、`refs.test.ts:386`（空串/缺省算没证据）、
`refs.test.ts:399`（`publish` 的空串归一 —— 没有它，上面那句「空串当没证据」在写侧就漏了）、
`refs.test.ts:354`（`publish` 记 url、`adopt` 不改写、`invalidate` 清空）、`refs.test.ts:413`（`hydrate` 清空）；
provider 层的接线由 `provider.test.ts:1055` 钉住，**同源**由 `:1081` 钉住，**空 `pending` 也补**由 `:1100` 钉住。

**已改窄的注释**：`refs.ts` 原称 `backendNodeId` 是「CDP 的跨导航稳定 id」，按 §10.4 的实测
（跨文档 22/22 解析失败）它在**跨文档后并不稳定**，稳定的只有同文档内。本轮顺手改掉，
免得下一个人拿它当跨导航锚点。

### 5.2 D-5 · `adopt()` 会就地换指针（**已定 C**：回执带 `reboundRefs`，随 P2 一并交付）

**一句话**：区域快照会让「ref 号没变」这件事失去含义 —— 号还是 `e12`，指的东西已经换了，
而且**从换掉那一刻起到下次点击之间，没有任何一处代码知道发生过什么**。

逐步看这条链（每步都能回源码）：

| 步 | 发生什么 | 依据 | 位置 | 模型看得见吗 |
|---|---|---|---|---|
| 1 | 模型拍全量快照，拿到 `e12 = 提交按钮`（`backendNodeId=4501`），epoch=7 | `publish()` 推进 epoch、记 loaderId 与 url | `refs.ts:192-196` | ✅ 回执里有 e12 |
| 2 | **人工在同一个文档里改了页面**（SPA 重渲染，把「提交」换成「提交并抄送」） | —— 插件不参与 | —— | ❌ 无事件可订 |
| 3 | 模型为了看某个区域，拍一次**区域快照** | `snapshot()` 走 `adopt()` 而不是 `publish()` | `provider.ts:1117` | ⚠️ 回执只含那个区域 |
| 4 | `adopt()` **不推进 epoch、不改 loaderId、也不改纪元 url** | 对照 `publish()` 的 192-196，这里三行都没有 | `refs.ts:208-222` | ⚠️ 回执还是「epoch 7」 |
| 5 | 「提交并抄送」的 semanticKey 恰好与 `e12` 唯一命中 → **复用同一个号**，把 `backendNodeId` 就地改成 4788 | `bindRow` 的 `live.set(existing.ref, updated)` | `refs.ts:373-378` | ❌ 回执只说「区域里有 e12」 |
| 6 | 模型点 `e12`，以为还是「提交」 | `resolve('e12')` 当前表命中 → 过写前门（两道门**全绿**：地址没变、节点还连着）→ 派发输入事件 | `provider.ts:1384`、`1424` | ❌ 打在从未见过的元素上 |
| 7 | 就算模型谨慎，先 `webpage_revalidate(e12)` —— **照样返回 ok** | `revalidateOne` 第一句 `resolve(ref)` 命中即 `{ok:true}`，**一次 CDP 都不发** | `provider.ts:1270-1272` | ❌ 报的是「有效」 |

第 7 步是重点：`revalidate` 的四道门（loaderId → backendNodeId → `isConnected` → role/name）
**只在「当前表没命中、要从归档捞」时才走**（`provider.ts:1277-1316`）。当前表命中就是纯查表成功，
所以它防不了这次改绑 —— 它会告诉模型「e12 没问题」。

**§5.1 的写前门今天已经落地，但救不了这条链**：两道门查的是「地址换没换」「节点还在不在」，
本场景同文档、同节点（`bindRow` 是把号 *绑到另一个活节点*），两道门全绿。
唯一能分辨它的是 `adopt()` 那一刻自己 —— 所以 D-5 仍是本方案里**唯一一个「连错误都不报」的洞**
（§0.3），选 A/B/C 见 §13。

比 §10.5 那条「列表重排」缺口更主动：**是插件自己的代码在换指针**。原 T4 §6 第 1 条把
「semanticKey 唯一命中才允许复用」当成 diff 的**新要求**，其实它今天就在跑。

**三个选法的处置见 §13 D-5**（A 作废当前纪元 / B 认特性只写文档 / C 回执带 `reboundRefs`）。
第 1 批（P1 写前门 + D-6=B）已按主上「先提文档、再实现」动过码，第 2、3 批是它的两轮 review 修正，
**主上 2026-09-19 定为 C**，且按 D-5 段落里的建议**只在 P2 一并交付**（单独加字段不值当）——
三批都没碰 `adopt()` 的判定逻辑，这条链今天仍然照上面 7 步原样跑。

## 6. P2 · 决策时通知（本轮重做：落点从「provider 加字段」改成「跨轮次累加器 + 全回执」）

### 6.0 原则：拉而不推

**人工动的那一刻模型没在读上下文**，推给它的消息要么打断当前 turn（要宿主配合开一条注入通道），
要么落到没人看的地方。真正需要通知的时机是**它下一次伸手的时候，告诉它刚才有人伸过手**。
所以 P2 的形态是「**攒着，下一次回执夹带**」，不是「实时推流」。

### 6.1 现状：这条链路已经有一半，缺三处（全部实测核对）

| 环节 | 现状 | 位置 |
|---|---|---|
| 信号源 | 宿主发私有编排消息 `{type:'takeover', tabId, active}`，**故意不走 CDP 事件流** | `src/browser-electron/bridge.ts:220`、`:576-581` |
| 接收 | `transport.onTakeover(...)` → `setTakeover()` 置**幂等状态位** `session.takeover` | `src/browser-electron/provider.ts:105`、`src/browser-cdp/provider.ts:1017-1019` |
| 交给模型 | 只有 `webpage_snapshot` 回执头一行 `NOTE: a human has DevTools open…` | `src/tool-browser/index.ts:220-223`、`provider.ts:1141`、schema `:1204` |

三个缺口：

1. **语义是「DevTools 开着」，不是「人工改过页面」**。人工点了按钮、改了地址栏而没开 DevTools → 零信号。
   且 `provider.ts:1010-1011` 自己写明：直连外部 Chrome 的 `cdp` provider **没有这条通道，状态位恒 `false`**。
2. **通知面只有 snapshot**。人工操作落在两轮之间，而模型下一轮往往是 `webpage_click` —— 那条回执上
   没有任何痕迹，于是它**结构性地看不到**：只有恰好在动手前拍了一次快照才看得见。
3. **`markTakeover` 在生产里没有调用者**（只有 `state.test.ts` 在调）。`TargetStateRegistry` 的
   `{owner, at, applied, previous}` 记账与 `contended()` 的「谁占着、何时」文案（`state.ts:245-251`）
   全是现成的，但 takeover 通道没接它（`provider.ts:1019` 只翻状态位）→ 「谁改的、几点改的」无从可报。

### 6.2 要做形态（按性价比排，三条都不引入新机制）

| # | 做什么 | 复用的既有件 | 为什么便宜 |
|---|---|---|---|
| ① | `session.takeover: boolean` → **跨轮次脏累加器**：分类计数 `navigated`（`Page.frameNavigated`）/ `withinDocument`（`Page.navigatedWithinDocument`）/ `takeoverWindow` | `Page.enable` 在 `open()` / `adoptSession()` 已经发过（`provider.ts:373`、`:437`）；事件订阅照 `console.ts:209` 的 `connection.on(...)` 形状 | 不用多开任何 CDP 域 |
| ② | **挂到所有回执**（至少 snapshot + mutate 全族），文案给**动作**不给状态 | `tool-browser/index.ts:205-224` 的 `notes.unshift(...)` 已是这个形状 | 改渲染 + output schema，不动判定逻辑 |
| ③ | 脏累加器同时写进 `TargetStateRegistry`，让「谁 / 何时」真的可报 | `state.ts` 的 owner 记账 + `contended()` 文案 | 把 ① 的事件顺手接上，别另起炉灶 |

**文案口径**：不要「内容随时可能变」（描述状态，模型无从决策），要
「上次快照之后页面导航过 1 次（`A → B`），你手里的 `e12` 来自旧文档 → 先 `webpage_snapshot` 再操作」。

### 6.3 边界与不做（原判断全部保留）

- **⚠️ 不做「检出即 `invalidate()`」**：核武器，时钟/轮询/SSE 都会被判成变更 → 反复作废 →
  上下文暴涨。教训已在 `src/browser/types.ts:183` 写过一遍（开合 DevTools 绝不推进纪元），
  不犯第二次。只有**真导航**（离散事件，不刷屏）配触发作废。
- **不做 DOM mutation 实时推流**：要 `DOM.enable` 多开一域事件流，而 `[V36]` 实测证明整条定位链路
  本来不需要它；代价是轮询类页面把通知刷成噪声（与上一条同源的教训），收益只是省一次 snapshot 往返。
- **事件通道会漏，别当全集**：`provider.ts:2152` 已记下 `Page.loadEventFired` 的两个坑 ——
  事件可能在 `Page.enable` **之前**就发过（空白页、缓存页），SPA 软导航又可能根本不发。
  `navigatedWithinDocument` 覆盖 pushState 这条**尚未实测**，落地前要用 live 组（`DSH_CDP_ENDPOINT`
  + 无头 Chrome）验一次，别照 CDP 文档的承诺写进回执文案。
- **通知不是兜底，是优化**：纯 JS 改 DOM（`textContent`、列表重排）不产生任何导航事件，P2 完全看不见；
  D-5 那条静默改绑链就是这么来的。**保命靠 P1 的写前门。**
- **与 `detectNavigation` 去重**，与 `takeover` 定清是一个维度还是两个：`takeover` = 「有人在操作」，
  `dirtySince` = 「页面自那份快照之后变过」，两者不等价。否则回执会出现
  `takeover:false` + `changed:true` 这种自相矛盾的信号。

### 6.4 最后一公里与砍掉条件（原 §6.1 保留）

初版全部落点都在 provider + `types.ts`，**`src/tool-browser/index.ts` 一次都没出现** ——
而「告知模型」的落点是**工具回执字段 + 工具 schema + 系统提示词**
（提示词在 `tool-browser/index.ts:2029-2040`）。没有这一层，「加一个回执字段」等于没做：
字段塞进去了，模型不知道该拿它做什么。

**必须一并交付**：回执字段名与文案、`webpage_snapshot`/`mutate` 的 output schema、提示词里一句
「看到 `changed=true` 时先重新 observe 再操作」。**砍掉条件**：真机走查发现模型无视该字段 →
整条砍掉，不留装饰性信号。

**排期判据**：①②③ 整条只在 P0（D-7=B 的自计）显示「人工操作落在 agent 两轮之间」的频次高到
snapshot 白跑次数可观时才做；否则 P1 的门就够，P2 可以一直不做。

### 6.5 显式控制权 · 人工接管按钮（**2026-09-19 定为 A 档**）

**一句话**：标签条上加一个按钮，默认**吞掉人工在页面视图里的输入**，人工按下「接管」立即放开并把
agent 挡在外面，按「交还」还给 agent。这是 P2「拉而不推」之外的另一条腿 —— 不再猜「有没有人动过」，
而是让**人自己声明**，并且把声明变成真互斥。

**先记一笔与参考对象的差异**（免得下一个人以为照抄了 Minke）：Minke 的 `Agent Browser` 原话是
"Take control of a live tab without closing it, hand it back when ready" —— 那是**默认不禁止人工**的
交接语义（本方案的 B 档）。A 档在它之上多了一层「agent 持有期间输入被吞」，是主上明确要的更强的一档。

#### 目标与可测判据

| # | 判据（能测才算数） | 服务哪条顶层目标 |
|---|---|---|
| J4 | 控制权 = `agent` 时，人工在**页面视图**里的**键盘**输入不产生页面效果；标签条仍可点 | J1 零静默 |
| J5 | 按下「接管」→ 该会话 ref 纪元作废，且 agent 的下一次 `webpage_*` **写**操作被拒（明确文案，不是超时） | J1 |
| J6 | 按下「交还」→ agent 恢复可写，但它**必须**重拍快照才拿得到 ref（不许复用交还前的号） | J1 / J3 |
| J7 | 「接管」按钮**任何时刻**都能按（不等 agent 同意、不被 agent 阻塞）—— 人永远不会被锁在外面 | 误伤（本方案的反面） |

> **J4 已按实测改窄**（2026-09-19）：原判据写的是「鼠标/键盘输入」。探针实测
> `before-input-event` **是键盘专属**，鼠标（人工点击与 CDP `Input.dispatchMouseEvent`）
> 一次都不触发 → A 档的「吞输入」只覆盖键盘。鼠标那半边**不做拦**，只由状态条文案提示；
> 不用页面内遮罩兜（会污染 AX 树与快照，见下）。改窄后的 J4 已由探针 8/8 覆盖。

#### ⚠ 探针：**已跑完，结论如下**（2026-09-19，Electron 44 / Windows）

探针脚本：`scripts/probe-input-swallow.mjs`（真 Electron 窗口 + `debugger.attach`，逐变体跑）。

**① 覆盖范围：`before-input-event` 是键盘专属。**

| 注入方式 | 钩子收到 | 结论 |
|---|---|---|
| 人工 `sendInputEvent(keyDown)` | `keyDown` | 覆盖 |
| 人工鼠标（`sendInputEvent` mouseDown/Up） | **不触发** | 不覆盖 |
| CDP `Input.dispatchMouseEvent` | **不触发** | 不覆盖 |

→ 鼠标拦不住。J4 据此改窄为「唯键盘」（见上），**不用**页面内遮罩层兜（会污染 AX 树与快照）。

**② agent 自己那条路会不会被误伤？这是真踩到的坑，分变体才看得见。**

| agent 怎么发键盘 | 钩子收到 | 页面收到 keydown | 页面收到 keyup |
|---|---|---|---|
| `dispatchKeyEvent('keyDown')` + text（`press` 打字符） | 只有 `keyUp` | ✅ | ⚠️ **若一并吞掉就没了** |
| `dispatchKeyEvent('keyDown')` 命名键（`press` 按方向键） | 只有 `keyUp` | ✅ | ⚠️ 同上 |
| `dispatchKeyEvent('rawKeyDown')` | **`keyDown`** | ❌ 被吞 | ❌ 被吞 |
| `Input.insertText` | 不触发 | — | — |

**两条实测逼出来的修正**（都不是「按原计划写就行」的地方）：

1. **必须只吞 `keyDown` / `char`，放行 `keyUp`。** 无条件 `preventDefault()` 会把 agent 的
   `keyUp` 一起吞掉 —— `webpage_press` 是 keyDown + keyUp 一对，少一条腿会让页面里依赖
   `keyup` 的逻辑收不到。落地代码就是按这一条写的。
2. **`rawKeyDown` 是一条已知边界，不是 bug。** CDP 的 `rawKeyDown` 在钩子里报的 type
   **就是 `keyDown`**，与人工按键无法区分 —— 想吞它就得连人工的 `keyDown` 一起吞，没有第三条路。
   它当前**不可达**：`webpage_execute` 明确拒绝 `Input.*`（`execute.ts:75`），`press` 也只用
   `keyDown`/`keyUp`。**哪天有人放开 `Input.*` 白名单，这条边界就变成真缺陷** —— 探针里它是
   一条恒打印的「边界记录」，改白名单的人应当顺手把它升级成 FAIL。

**③ 带 Ctrl / Alt / Meta 的组合一律放行**（`Ctrl+Shift+I` 开 DevTools、`Ctrl+R` 刷新）。
吞掉它们等于把人锁死在页面里，与 J7 的立意相反。探针验过：`agent` 期间带 Ctrl 的组合照常落地。

**结论：A 档（唯键盘版）成立，方案按 §6.5 落点表原样落地。**

**为什么 `takeovers` 必须分账（本轮最关键的一处设计修正）**：`takeover`（有人开着 DevTools）
与 `holder`（人按了接管按钮）是两条**各自独立撤销**的线。合用一个布尔位的后果很具体 ——
「人在接管期间开一次 DevTools 又关掉」会把他自己的接管一起撤掉，于是**人在操作、agent 却被放行**，
正好把这个功能存在的意义抹掉。分账后「谁撤谁自己的」，`isTakeover()` 取并集；`state.test.ts`
有一条用例专门钉它。

**拒写范围**：`mutate`（click / fill / press / scroll / wait）+ `navigate` + `execute`。
读型（snapshot / screenshot / find / `tabs(list)`）**照常放行**。新错误码
`BROWSER_HUMAN_HOLDING`，消息里自带恢复路径（「等人按交还，然后重拍快照」）与
「不可重试」的明示 —— 与写前门同一条纪律。

**「按下接管」这一侧要同时做两件事，不能只做一件**：作废 ref 纪元（让 agent 手上的号立刻失效）
**和** 拒写（让它下一次动手就拿到明确文案）。只作废不拒写 → agent 会撞一堆 `BROWSER_STALE_REF`，
而它不知道为什么（那是「静默」的另一种形态）。这条正是 J5 两半的由来。

**判据覆盖**：
- J5 / J6 → `provider.test.ts`（假 Chrome）：拒写**零 CDP 派发**、交还后旧 ref 一律不复用、
  只影响本会话、与 `takeover` 不合并、会话关闭清账；
- 通道 → `browser-electron/index.test.ts` 端到端（宿主的通知真的把 provider 挡上了）；
- J4 / J7 + agent 侧不误伤 → `scripts/probe-input-swallow.mjs` 真机 8/8；
- 反向验证 4 条逐个隔离（闸门形同虚设 / 不作废纪元 / 来源合并成一位 / metrics 恒真），各自转红。

**`op:'control'` 出向命令存在的理由**：按钮画在另一个 `WebContentsView` 里，端到端脚本**点不到它** ——
只能靠这条通道把「人按了接管」重放出来。与 `op:'devtools'` 存在的理由同源（菜单里那条也只能靠模拟按键）。

#### 三个已知代价与对策

1. **空窗**：agent 只在一次工具调用里动手几百毫秒，剩下几十秒在推理 —— 这段时间人对着一个吞输入的页面很难受。
   对策：**holder 空闲超时自动放开**（连续 T 秒没有任何页面命令 → 自动切 human）。它把「锁」缩到
   agent 真在动手的那段，代价是 A 档在 T 之后其实退化成 B 档。**T 取值等主上点头（见 §13 D-11a）**；
   没有 T 的话，本条就是纯粹的易用性欠账。
2. **困住人**：靠 J7 兜住 —— 按钮在独立的 tabbar view 上、按下即生效、不需要 agent 确认，
   所以最坏情况是多点一下，不是出不去。agent 崩溃同理（holder 不会自己抢回来）。
3. **拦不全**：人工开 DevTools 改 DOM、另开一个浏览器、同一账号在手机上操作 —— 一条都拦不住。
   所以**写前门（§5.1）不许撤**，按钮是「让冲突变少 + 让归属可报」，不是兜底。
   文案里也不许出现「已隔离 / 安全」这种话，只说「现在轮到你了 / 现在由 agent 操作」。

#### 不做

- **不锁标签条本身**（新建标签、切标签、地址栏）—— 除非 D-11b 点头把地址栏也算进「操作页面」。
- 不做「排队等 agent 做完自动交还」：那是把控制权做成了 agent 的财产，与人接管的本意相反。
- 不在页面上画吞事件的遮罩层（污染 AX 树与快照，见上面探针的退路）。
- 不给控制权做多级优先级 / 抢占协商：一个标签页一个 holder，后来者按按钮即拿走，简单到没什么可谈。

## 7. P3 · 记账与互斥（原 T5 + T1 合并评估）

**先纠正一个假前提**：「会话之间有隔离」只成立于「一会话一标签页」这一层（§1.2）。
provider **没有任何调用方鉴权**，`require()` 照单全收。所以：

- **两个对话各开各的标签页 → 天然互不干扰**，不需要锁；
- **两个对话操作同一个标签页，唯一途径是共用同一个 sessionId**（人工把号传过去，或子 agent
  继承上下文）。此时锁键相同，互斥**正常生效** —— 初版「互斥永不触发」的推论是错的。

**因此第一件事不是锁算法，是归属**：`Map<sessionId, {holder, at, ttl?}>` 落在 provider 实例上
（不是页面里，Web Locks 用不上）。没有 `holder`，冲突时既回不了「谁占着这个标签页」，
也做不了「只有持有者能续约 / 释放」。沿用 `state.ts` 的 `{owner, at, applied, previous}` 记账风格，
owner 取值从 `'agent' | 'human'`（`state.ts:50`）扩成调用方 id，**别另起炉灶**。

- **TTL 取决于跨进程与否**（仍待确认）：同进程崩溃即全挂，`try/finally` + `AbortSignal` 够；
  跨进程崩溃会留僵尸锁，TTL 才有价值。**没有证据前不做 TTL。**
- **串行队列只保护「同一标签页上的并发写者」**（跨会话共用 sessionId + 事件/通报链）。
  它**不是**任何事故的主防线，主防线是 P1。排期在 P0 出数之后，若 §4 显示共用 sessionId 从未发生，
  **整条 P3 可以一直不做**。
- **入队带 epoch 栅栏**（若真做队列）：入队记 `refs.epoch`，出队时 epoch 已推进就以既有
  `BROWSER_STALE_REF` 失败 —— 排队期间页面被顶替的意图不该被执行。约 5 行，零新错误码。

## 8. P4 · 增量 diff（条件性，两道门禁都在 P0）

只在 P0 两道门禁都达标后做。四条硬要求原样保留：

1. **主键 = `backendNodeId`**，semanticKey 只做兜底（未命中且两侧唯一才复用）。
2. **`changed` 判定必须含 value + reported properties**，不能只比 `name`。
3. **重建检测**：存活率低于阈值（建议 50%）自动退全量。
4. **逃生舱** `full: true`；首次 / 导航后 / 距上次超 N 步强制全量。

**口径纪律**：diff 必须基于**模型所见视图**（折叠后 + `unfoldedLines` 语义），不能基于全量 `rows`，
否则出现「我视图里没有的 ref 被列为 unchanged」—— 这正是 `FOLD_MARKER_PREFIX` 存在的原因。
`changed` 计数与 `droppedElements` / `foldedRepeats` / `truncatedByBudget` 分开报。

**实测依据（2026-09-18，无头 Chrome 153）**：

| 场景 | backendNodeId 存活 | +semanticKey 兜底 |
|---|---|---|
| 没变 / 追加一条 / 改文本 / 改 value | 100% | 100% |
| 列表整体重建（`innerHTML` 重赋值） | **8%** | **42%** |
| 整页 reload | 0% | 36% |

semanticKey 唯一命中率实测 **39.4%**（撞车只有「翻译此页」×10、「查看详细信息」×10 两组，
因为 `listitem` 无可访问名称）→ **它只能兜底，不能当主键**；且低唯一率本身是防错配的安全特性。

## 10. 保留的原始论证（对照区）

1. **一会话一标签页**：`provider.ts:14`，代码处处 `sessionId: session.targetId`。
   → 锁键 `${sessionId}:${tabId}` 在原设计里退化，但**跨会话共用 sessionId 时锁键相同、互斥生效**
   （原「永不触发」的推论错误，已更正）。
2. **同文档内 `backendNodeId` 稳定且唯一**，`revalidate` 的四道门（loaderId → backendNodeId →
   `isConnected` → role/name，`provider.ts:1261-1317`）是真机验证过的原语 → 匹配/校验该用它，
   不是 semanticKey。**跨文档它并不稳定**（id 会重新编号，见 §10.4 与 §5.1.1 的注释冲突）。
3. **人工 + agent 并发：锁无用，只能靠检测与通知** —— 人工不经过 provider，锁不住人。
   既有设计选「整体让渡 + 延迟回读探测」（`state.ts`）是**对的**。
4. **实测：跨文档不会静默点错**（`.probe-human-nav.mjs`，22 个按钮跨域导航后 `DOM.resolveNode`
   全失败）→ 但**该结论不覆盖同文档 pushState**（§1.4），本版已改窄。
5. **已知缺口，记下不做**：列表重排时 DOM 节点被复用，`backendNodeId` 不变、`ancestorPath` 仍是
   `list>listitem`、role/name 也不变 → 「第 3 条的按钮」被移到第 8 条，**现有所有机制都挡不住**
   （含 semanticKey）。要挡就得让路径带兄弟标题，而那会有反作用（插入一条导致后面全体错位）。
6. **并行改动备案（2026-09-18）**：`refs.ts` 已落地 LRU 软淘汰（`LIVE_BINDING_CAP=2000` +
   `evicted` 索引 + `bindRow` 同号复活）。两条 follow-up 中 **F1 原判被更正**：`evicted` 在
   `publish()`（`refs.ts:170-171`）与 `invalidate()`（`refs.ts:282-283`）都会清空，**不跨快照无界增长**，
   上界是「单次 publish 行数 − 2000」→ 优先级降一档。**F2 仍成立**：`trimLive()` 每淘汰一条
   全表扫一次 `lastSeen`，淘汰 k 条是 O(k·n)。

### D-5 · `adopt()` 就地换指针算不算缺陷 —— **已定 C**（回执带 `reboundRefs`，只报不作废）

**背景**：7 步的事故序列已经在 §5.2 逐步列全（每步带 `file:line`）。压缩成一句：
`adopt()` 不推 epoch、不改 loaderId、也不改纪元 url（`refs.ts:208-222`），却会在 semanticKey 唯一命中时
把同一个 ref 号装上新的 `backendNodeId`（`refs.ts:373-378`），而 `revalidate` 对当前表命中
直接返回成功且**一次 CDP 都不发**（`provider.ts:1270-1272`）—— 所以「号没变」不再蕴含
「指的东西没变」，且这条链上没有任何机制会报警。

| 选项 | 利 | 弊 |
|---|---|---|
| A. 认定缺陷：`adopt()` 命中即推进 epoch | 语义最干净：「号没变 = 指的东西没变」重新成立 | 区域快照的核心卖点（不作废其它 ref）被废掉，等于砍功能 |
| B. 认定特性：注释 + 提示词写明「区域快照会静默改绑 ref」 | 零行为改动；诚实 | 把担子全压给模型，而它手上只有 role/name，判不出被改绑 |
| C. 折中：回执加 `reboundRefs`，只报不作废 | 保留卖点又可观测；与 P2 的脏累加器同一套机制（§6.2 ②） | 又一个模型可能无视的字段（§6.4 的砍掉条件照样适用） |

**我的建议**：C，且**只在 P2 一并交付**（单独加字段不值当）。A 需要重新设计区域快照语义，
不在本轮范围。

**已定（2026-09-19，主上拍 C）**：回执加 `reboundRefs`，**只报不作废** —— 保留区域快照
「不作废其它 ref」的卖点，同时让改绑变得可观测。落点与 P2 共用同一套机制（§6.2 ② 的跨轮次
脏累加器），所以排期上跟 P2 走，不单独开工。C 自带的代价照 §6.4 的砍掉条件适用：
**模型持续无视这个字段 → 与 P2 一起砍**。

### D-11 · 人工接管按钮 —— **主上 2026-09-19 定 A 档**（默认吞人工输入），剩两个子待定点

**背景**：现在的「人工在操作」只有一个启发式来源 —— 开合 DevTools（§6.1 缺口 1），
人工没开 DevTools 就零信号。主上要的是**真互斥**：agent 操作期间人工动不了，要动先按按钮。
Minke 的 `Agent Browser` 是 B 档语义（默认不禁止人工，显式 take control / hand back），
A 档在它之上多一层默认吞输入 —— 差异已在 §6.5 记档。

**已定（A）**：默认 holder = `agent`，期间人工在页面视图里的输入被吞；按「接管」立即放开
（不等 agent 确认 → J7），agent 侧同时作废纪元并拒绝写操作；按「交还」还给 agent。
落点、判据 J4-J7、三个代价与「不做」见 §6.5。**动手前必须先跑 §6.5 那根 `before-input-event` 探针。**

### D-13 · 真 Chrome 上 `dispose()` 恒报错 —— **已按 A 修掉**（与门无关，2026-09-19 真机走查顺手查出）

**背景**：门探针每次收尾都抛 `BROWSER_DISPOSE_FAILED`，稳定复现。根因不在门的代码，在 HTTP 传输层：
Chrome 的 `/json/close/<id>` **成功时回的是纯文本** `Target is closing`，而 `requestRaw`
（`protocol.ts:495`）只接受 JSON → 抛 `BROWSER_PROTOCOL_ERROR`。`close()` 因为
`.catch(() => undefined)`（`provider.ts:585`）把它吞掉了，`dispose()`（`provider.ts:990`）不吞，
于是聚合到 `src/browser/index.ts:237` 的卸载路径上上报。**标签页是真关掉了**（`/json/list` 复查为空），
所以是噪音级缺陷 —— 但「卸载报红」这件事会污染日志与自检判读。

| 选项 | 利 | 弊 |
|---|---|---|
| **A（已选）** 在 `closeTarget` 里认「200 + 非 JSON 文本」为成功 | 语义最准（这是 Chrome 文档化的成功响应） | 要动 `protocol.ts` 生产代码 + 补 fake 用例 |
| B 让 `dispose()` 学 `close()` 一样吞 | 改动最小 | 把 403/500 这类真错一起吞掉，等于再挖一个「静默」——与本案的立论相反 |
| C 不修，只记档 | 不动码 | 每次真机走查/卸载都会看到一条假红，容易被误判成包坏了 |

**落地时挖宽了一点**：修之前起真 Chrome 把两个端点各量了一遍 —— **这不是 `close` 一处**。
`/json/activate/<id>` 成功时同样回纯文本（实测 Chrome 153：`Target is closing` / `Target activated`；
target 不存在时两者都回 404 + `No such target id: <id>`）。所以 `activateTarget`（窗口置前那条路，
`provider.ts:598`）迟早会以同样方式报红 —— 只修 `close` 等于留一颗同型号的雷。

**改了什么**：从 `requestRaw` 里抽出**不解析响应体**的 `requestText`（`protocol.ts:510`；仍按状态码抛错，
所以 403/500 照抛，`isTargetGone` 只看状态码不受影响），`closeTarget` 与 `activateTarget` 改用它；
`version` / `newTab` / `list` 这些**真该解析 JSON** 的端点一行没动。

**断言与验证**（`protocol.test.ts`）：
- 新增 `respondText` 夹具 —— **必须按真 Chrome 的响应形态构造**，用 JSON 体测不出这个坑；
- 「close 认 200 + `Target is closing`」「activate 认 200 + `Target activated`」两条**逐个反向验证**：
  把对应一处改回旧写法即红（各 `1 failed | 29 passed`），改回即绿；
- 第三条「404 + 文本体也算幂等成功」是**形态钉不是判据**：新旧实现下都绿（非 2xx 在解析之前就抛了），
  留着只防以后有人去解析 404 的响应体；
- 真机：`scripts/probe-gate-live.ts` 由 6 项变 **7 项全绿 / exit 0**，第 7 项「dispose 干净：不抛错且
  标签页已回收」**恒报**（原先只在失败时打印 —— 静默通过和静默没跑长得一样），且两半判据都要：
  只查「标签页没了」会把假红修成假绿，因为旧缺陷里标签页本来也关得掉。反向验证：改回旧写法 → 该项 FAIL、`exit=1`。
