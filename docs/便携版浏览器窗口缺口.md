# 便携版「开不了浏览器窗口」根因分析

> 2026-09-15，主上在另一台机器上实测 v0.2.0 便携版反馈「没法调用打开新的窗口」。
> 本文是静态排查（读代码 + 读包）的结论，**尚未在真机上复现确认**。

## 结论

**便携版当前不具备「打开浏览器窗口」的能力。** 这不是环境问题，是出货配置的缺口 ——
开窗口的那条链（`browser-electron`）在打包形态下**从未被接上**。

## 根因链（三个环节，缺一不可，全中）

### 1. `browser-electron` 没有被启用

它的 `available()` 多一道闸门（`provider.ts:33`，注释里写明理由：不加会和 `browser-cdp`
同时「可用」而触发 `BROWSER_PROVIDER_AMBIGUOUS`）：

```ts
// src/browser-electron/index.ts:130
const enabled = config.enabled ?? process.env[PROVIDER_ENV] === PROVIDER_ID
//  PROVIDER_ENV = 'DSH_BROWSER_PROVIDER'，PROVIDER_ID = 'electron'
```

两条启用途径，便携版**一条都没走**：

| 途径 | 便携版实际情况 |
|---|---|
| profile 里写 `config: { enabled: true }` | 出货 patch（`cordis.patch.yml`）只 `insert` 插件行，**没有任何 `config`** |
| 环境变量 `DSH_BROWSER_PROVIDER=electron` | `启动.cmd` 只设了 `DSH_HOME`，**没设这个** |

### 2. 于是 `webpage_open` 只能落到 `browser-cdp` —— 而它在桌面端里是死路

`docs/实现与踩坑.md` 第 142 行起已实测记录过：

- 桌面端自己的 `--remote-debugging-port` 就是**它自己的渲染进程**，不是可开标签的浏览器；
- 内置 Chromium **不实现 `PUT /json/new`**，实测只回一句 `Could not create new page`；
- 桌面端 host 又跑在**纯 Node** 子进程里（不是 Electron），拿不到 `BrowserWindow`。

这正是用户看到的「没法调用打开新的窗口」。

### 3. 即使补上启用开关，包里也没有可 spawn 的 Electron 二进制

`browser-electron` 的实现是：host 进程 **spawn 一个 Electron 窗口宿主**
（`src/browser-electron/host.cjs`），窗口由那个独立进程创建。

而便携版的 `app/resources/` 只有三项：

```
app.asar   dsh   runtime
```

**没有独立的 Electron `dist`**（开发态用的是 `apps/desktop/node_modules/electron/dist/electron.exe`，
367MB）。包里那个 `app/DeepSeek Harness.exe` 是 **electron-builder 打包后的应用**，
`DeepSeek Harness.exe host.cjs` 这种用法不成立 —— 打包应用的 app 路径固定在 asar 里，
argv 里的脚本路径会被忽略。

## 为什么开发态一直没发现

| 验证手段 | 为什么没覆盖到 |
|---|---|
| `pnpm run window:desktop` | 在**开发态**跑的，那里 `electronPath` 指向未打包的 `electron.exe`，且 `dev-desktop.mjs` 会设 `DSH_BROWSER_PROVIDER` |
| `pnpm run verify:portable` | **[5/5] 明写「跳过浏览器验证（没给 `--browser`，客户端注册那一步未验）」** —— 浏览器这条链在打包形态下**从未被验过** |
| CI 发版前自检 | 同上，`verify-portable` 的浏览器段是跳过的 |

教训与「profile 少了 `desktop-runtime-state.json`」是同一类：**开发态能跑 ≠ 打包态能跑**，
而区别恰好落在「二进制路径」和「环境变量」这两个打包时才会变的东西上。

## 修复方案（三选一）

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A. 把未打包 Electron 打进包** | 打包脚本复制 `electron/dist` 到 `app/resources/electron/`，profile 里配 `electronPath` | 包 **+367MB**（226MB → ~600MB） | 改动最小但体积代价大 |
| **B. 复用主 exe（推荐）** | 给 `docs/harness-desktop-build.patch` 再加一条：`main.ts` 最前面识别 `--dsh-browser-electron-host=<host.cjs>`，命中则**跳过单实例锁与主窗口**，直接 require 那个 cjs 跑窗口宿主。插件端 spawn 主 exe + 这个参数 | **0 额外体积**；要动 harness 补丁 + 插件 spawn 参数 | 复用已成熟的补丁机制，见下 |
| **C. 主进程代开窗口 + IPC** | 由 Electron 主进程提供「开窗口」的 IPC，host 进程通过 fd3/fd4 通道调用 | 架构改动最大，但最「正统」 | 长期最优，本期成本高 |

**推荐 B**，三个理由：

1. **0 体积开销**（A 会让包膨胀 1.6 倍，对一个靠 zip 分发的便携版很难接受）；
2. 复用已经跑通的补丁机制（`harness-desktop-build.patch` 已有两条真需要的补丁，加第三条是既有路径）；
3. 打包应用的主 exe 本来就是 Electron，`require('electron')` 在主进程里拿到的就是完整 API，
   `host.cjs` **一行都不用改**。

B 的实现要点（动手前需确认）：

- `main.ts` 的拦截必须放在**最前面**（早于 `requestSingleInstanceLock`），否则第二个实例会因单实例锁直接退出；
- 传给宿主进程的环境变量（`DSH_HOME` 等）要保持一致，不能让宿主模式再去碰 profile；
- 插件端的 `electronPath` 在打包态应当取**主 exe 路径**。目前 `resolveConfig` 只认
  `config.electronPath` 或 `DSH_BROWSER_ELECTRON_PATH`，而「用户机器上的绝对路径」打包时不可知 ——
  和 `links` 的处理同理，需要一条**相对包根的运行时解析**规则。

# 方案 B 与方案 C 的逐项对比

> 2026-09-15 补充。两者的**共同前提**（都得做，不构成区别）：
> 出货 patch 里给 `browser-electron` 那行补上 `config: { enabled: true }`；
> 以及 `electronPath` 的**运行时解析** —— 它必须指向用户机器上的绝对路径，打包时不可知，
> 与 `links` 同理，需要一条「相对包根解析」的规则。

## 架构差别

```
B（主 exe 加 argv 模式）
  Electron 主进程 ──spawn(exe + --dsh-browser-electron-host=<host.cjs>)──► 第二个 Electron 实例
        │                                                                        │
        └── fd3/fd4 管道（原有）                        host.cjs 开 BrowserWindow，
            dsh-app:// 转发                            用 webContents.debugger 驱动
                                                              ▲
  host(纯 node) ──────── TCP + CDP（原有）────────────────────┘

C（主进程代开窗口 + 反向 RPC）
  Electron 主进程 ──┬── BrowserWindow（新增窗口管理模块）
                    │        ▲
                    │        │ 新增的 RPC（协议要自己设计）
                    └────────┴──── host(纯 node) ── transport 要换成 IPC 版
```

## 逐项对比

| 维度 | **B** | **C** |
|---|---|---|
| 额外体积 | 0 | 0 |
| 额外进程 / 内存 | 多一个完整 Electron 实例（约 150–250MB + GPU 子进程） | **0**（复用主进程） |
| 改 harness 的面 | `main.ts` 加约 10 行早期 argv 分支 | ① 新增 host→main 反向 RPC ② 把 `host.cjs` 的窗口逻辑搬进主进程 ③ 可能要升 `DESKTOP_HOST_PROTOCOL_VERSION` |
| 跨进程协议 | **不新增** | **必须新增** |
| `host.cjs`（含 tabbar / 多标签 / 接管） | **一行不改** | 逻辑全部搬走，等于重写 |
| CDP 传输层 | `ElectronWindowTransport` 原样复用 | 要写 IPC 版 transport，且**异步事件推送**（`Inspector.detached`、`Page.frameNavigated`）要重做 |
| 上游漂移风险 | 补丁是独立分支，只赌「插入点」不漂 | 动 `host-protocol.ts` —— 那是**版本化的跨进程契约**，升级冲突面大 |
| 验收成本 | `smoke:window` / `window:desktop` 可改造复用 | 要新写一套（新协议 + 新 transport 都得有测） |
| 崩溃域 | 浏览器窗口独立进程，崩了不拖累主应用 | 主进程崩 = 浏览器窗口全没 |
| 与开发态一致性 | **完全一致** —— 开发态本来就是 spawn 独立 Electron | 引入一套开发态没验过的新行为 |

## 为什么现有通道撑不起 C

C 的命门在「host 进程怎么把 CDP 命令送进主进程的窗口」。我查了 `host-protocol.ts` / `host-process.ts`：

- `fd 3`（`DESKTOP_REQUEST_PIPE_FD`）是 Electron **写**、child 读 —— 方向固定为「主进程 → host」；
- `fd 4`（`DESKTOP_RESPONSE_PIPE_FD`）是 child 写、Electron 读 —— 是**响应**，不是双向流；
- 两者承载的是 **HTTP-fetch 语义的帧**（`DesktopHostRequestStart` 有 `url/method/headers/body`），不是通用双向流；
- `fd 5`（Node IPC）上只保留 `shutdown` 一条命令 + `ready` 事件。

也就是说**没有现成的 host → 主进程 RPC**。要做 C，就得在下面三条里挑一条，每条都比 B 贵：

| C 的子方案 | 代价 |
|---|---|
| C1. 在 fd5 IPC 上加 `browser-host` 命令族 | CDP 是长连接 + 高频事件流，IPC 是 JSON 序列化，截图要走 base64 —— 语义和性能双重别扭 |
| C2. 新增一对 fd 做通用双向流 | 要改 `spawn` 的 `stdio` 数组（现在固定 `['ignore','pipe','pipe','pipe','pipe','ipc']`），**动的是 harness 的进程启动契约** |
| C3. 让主进程开一个本地端口给 host 连 | 等于在 Electron 主进程里再实现一遍窗口宿主 —— 就是 B 要做的事，只是换个宿主进程 |

## 结论

**推荐 B**，四项全胜：改动面、上游维护、验收成本、风险集中度。

最关键的一条是**证据基础**：B 是把开发态**已经实测通过**的行为（`window:desktop` 那组证据：
`providerId: electron` / `refs: 27` / `screenshotBytes: 207285`）原样搬到打包态；
C 则是新写一套没人跑过的机制，而这次的教训恰恰是「**没在打包形态下验过的东西，就是会坏**」。

**C 什么时候才值得做**：当需求升级为「浏览器窗口与主窗口深度集成」——共享标签栏、
接管用户已有的窗口、窗口状态随主应用保存、复用主进程 session 的登录态。那时 C 是正路；
而只为「让 `webpage_open` 能开出窗口」，B 的性价比是压倒性的。

## B 的实现要点（已核对代码）

1. **拦截必须在 `claimDesktopSingleInstance()` 之前** —— 它在 `main.ts:507`，
   内部 `requestSingleInstanceLock()` 失败会直接 `app.quit()`。分支要插在 import 之后、507 之前。
2. **必须给第二实例独立的 `--user-data-dir`** —— 否则它和主应用共享 userData，
   可能撞锁或污染。当前 `bridge.ts:235` 的 `spawn` 只传了 `env` 和 `stdio`，要补 argv。
3. **spawn 的 args 要改**：`[options.hostScript]` → `['--dsh-browser-electron-host=' + hostScript]`；
   `electronPath` 在打包态解析成 `app\DeepSeek Harness.exe`。
4. **`host.cjs` 是 CJS，用 `createRequire` 加载** —— 它在 asar 之外
   （`app/resources/dsh/node_modules/dsh-webops-plugin/lib/browser-electron/host.cjs`），绝对路径加载没问题。
5. **窗口归属要说清**：第二实例有独立 userData，意味着那个浏览器窗口的登录态**不持久、
   也不与主应用共享**。这与开发态现状一致，但需要在文档里写明，免得以后被当成 bug 报。

### 补丁新增的两处

1. **`main.ts` 顶部**：`process.env.DSH_APP_EXECUTABLE = process.execPath`
   —— 让 host 子进程（以及跑在里面的插件）知道主 exe 在哪。
2. **`main.ts` 尾部**：把原来的「单实例锁 + 主窗口」那几行包进 `else`，前面加一个分支读

`!/^DSH_DESKTOP_/u.test(name)`，会把该前缀的变量**全部剔掉**，插件根本收不到。
这条约束已经写进测试钉死。

- `pnpm typecheck` 干净；`pnpm test` **299 passed / 3 skipped**（原 289，新增 10 条）。
- 补丁**反向验证**过：`git checkout --` 还原 harness 三个文件 → `git apply --check` 通过。

### 还没验证的（必须补上）

**app 模式的真实行为**。本机跑不了 Electron（见 `docs/实现与踩坑.md` 与项目记忆：
`(./app/*.exe &)` / `cmd //c 启动.cmd` / `Start-Process` 进程都不出现；宿主进程单独跑也会因
缺 fd3/4 管道 + IPC 被拒），所以下面这条链**只有打包态真机能验**：

```
主 exe 以宿主身份启动（argv 带 --user-data-dir）
  → main.ts 早期分支命中，跳过单实例锁
  → require(host.cjs)，窗口宿主起来并从 stdout 宣布端口
  → 插件侧 TCP 连上、CDP 通道建立
  → webpage_open 开出窗口
```

**风险最高的一环**是「打包后的 Electron 主 exe，在那个早期分支里 require asar 外的 `host.cjs`」。
`createRequire` 加载 asar 之外的绝对路径 cjs，在 Electron 里是支持的用法，但**本项目没有实证**。
万一它不成立，退路有两条：把 `host.cjs` 一并塞进 asar（改打包脚本），或回落到方案 A / C。

# 2026-09-17：链通了，但没人选 provider —— 真机撞上 `BROWSER_PROVIDER_AMBIGUOUS`

## 现象

修完 `run_code` 的沙箱 runner 之后，主上在真机上新会话里测：

```
CALL webpage_open {"url":"https://www.baidu.com"}
Error: multiple usable browser providers are registered (cdp, electron); configure one explicitly
```

注意这**不是** 2026-09-15 那个「打不开窗口」。那次是「electron provider 根本没启用，
`webpage_open` 落到死路 cdp」；这次是**两个都启用了、却没人告诉缝隙选哪个**。
症状从「选择落错」变成了「选择失败」—— 恰好是本文件第 29 行早就写破的那条：

> | 环境变量 `DSH_BROWSER_PROVIDER=electron` | `启动.cmd` 只设了 `DSH_HOME`，**没设这个** |

当时只把注意力放在「启用」上（补了 `config.enabled: true`），没意识到**启用**和
**选择**是两件事：`enabled: true` 让 electron 进入候选，可候选有两个时缝隙不会替你选。
（`browser-cdp` 的 `available()` 是**乐观**的 —— 探测拿不准就返回 `true`，把精确诊断留给
`open()`；所以「同时可用」在桌面端是常态，不是异常。）

## 修法

在 `apps/desktop/src/main.ts` 顶层（与 `DSH_APP_EXECUTABLE` / `DSH_PTC_NODE` 同一处）落默认值：

```ts
if ((process.env.DSH_BROWSER_PROVIDER ?? '') === '') process.env.DSH_BROWSER_PROVIDER = 'electron'
```

三个理由：

1. **为什么不是写 profile 的 `config.provider`**：桌面端 profile 每次重建，写进去活不过一次重启
   —— 这正是当初把 env 定为「唯一稳定旋钮」的原因（`src/browser/index.ts:85`）。
2. **为什么不只写 `启动.cmd`**：`使用说明.txt` 明写「双击 `启动.cmd`」与「双击 `app\<exe>`」
   等效（v0.2.2 起 `main.ts` 有便携 home 兜底），只写脚本等于双击那条路依旧撞墙。
   放 `main.ts` 顶层则两条路一起覆盖。
3. **为什么是「判空后兜底」而不是无条件赋值**：留出覆盖口子 —— 想改用外接 Chrome 仍然
   `set DSH_BROWSER_PROVIDER=cdp` 就行（`使用说明.txt` 里那条路还成立）。

## 这一轮拿到的实证

之前「待确认」里那句「风险最高的一环：打包后的 Electron 主 exe，在那个早期分支里 require
asar 外的 `host.cjs`」——**现在有实证了**。用已发布的 v0.2.4 包直接复现启动契约：

```bash
"app\DeepSeek Harness.exe" --user-data-dir=<tmp>      # env: DSH_BROWSER_ELECTRON_HOST=<包内 host.cjs>
# stdout: {"type":"listening","port":54915}
```

端口宣布出来了，说明 `main.ts` 的早期分支命中、`createRequire` 成功加载 asar 外的
`host.cjs`、窗口宿主真的起来了。退路（把 `host.cjs` 塞进 asar / 回落方案 A、C）都不需要。

## 同一件事的自动化：`pnpm run verify:browser-host`

「开窗口」这条链此前**只能靠真机点一遍**（本文件第 57–63 行那张表：三道自检全都覆盖不到它）。
现在有了 `scripts/verify-browser-host.mjs`，它把**包内编译产物**当生产代码跑：

- spawn 主 exe（app 模式）→ 等宿主宣布端口 → 真导航一个本地探针页 → 取快照 + 截图；
- provider 选择做**正反两向**断言：不设 env 必须抛 ambiguous（证明这段检查真能发现问题），
  设成 electron 必须选中 electron；
- 截图落盘，`--out` 指定路径，主上可以直接看窗口长什么样。

它不覆盖的两件（必须留给人）：**模型真的调用 `webpage_open`**（要 API key）、
**窗口外观**（截图能替代一部分，「在屏幕上、拖得动」只能人看）。

## 教训（第三次同一类）

`docs/实现与踩坑.md` 里已经写过两遍「开发态能跑 ≠ 打包态能跑」，区别都落在
**二进制路径**和**环境变量**上。这次是第三遍，换了个变量名而已：
`DSH_BROWSER_PROVIDER` 在开发态由 `dev-desktop.mjs` 设好，打包态没人设 —— 与
`ELECTRON_RUN_AS_NODE`（沙箱 runner）、`DSH_PTC_NODE`（ptc）是同一个形状。

**可复用的判据**：凡是「开发态某个脚本会替我们设的变量」，都要在 `main.ts` 里找一遍
有没有对应的兜底；没有的，打包态就是一个必然的 bug。


## 补充：窗口「整片变白」这一格也补上了（2026-09-17 晚）

上面「还没走通」里有一格是**窗口内容整片空白**。主上真机第二轮复现到了，根因已定位并修复，
完整取证过程写进 `docs/实现与踩坑.md` 踩坑 #7。结论压成四句话：

- 空白的形态是「壳窗口只显示自己的 `backgroundColor`（`#f2f3f5`，采样 avg≈243.5），
  标签条 + 页面两个子视图一个像素都没有」，而 CDP / 快照 / 截图全部正常 —— 页面活着，
  是**视图层面全废**。
- 触发条件只有一个：**窗口最小化（或隐藏）期间跑了一次 `layout()`**。此时
  `getContentBounds()` 返回 `{x:-16000,y:-16000,width:0,height:0}`，视图被 `setBounds` 成
  0 宽；而恢复窗口**不触发 `resize`**（实测恢复后窗口 bounds 已回到 1087x759，视图仍是 0），
  于是窗口一直白着。
- **它可逆**（这一条纠过一次）：窗口可见时**再跑一次 `layout()`** 画面就回来
  （实测 11196 字节纯色 → 26486 字节正常）。真机之所以白到用户放弃，是没有任何代码会去补
  那一次，不是救不回来。所以修法是两半：`layout()` 不采信退化读数（不制造伤害）+
  `restore`/`show` 时补跑一次（出事能自愈），任一半单独都够，两半都在是纵深。
- **两个入口，同一个根因**：①模型发 `activate`（切标签）跑 `layout()`；②**`openTab()` 末尾
  那次无条件 `layout()`** —— 页面弹窗转标签（`target=_blank` / `window.open` →
  `setWindowOpenHandler` → `openTab`）走这里，会把**已经在渲染的旧标签一起**钉成 0 宽。
  ②才是贴合主上描述的那条：「让它看热搜第 5 条之后才空白」——点热搜第 5 条就是一次
  `target=_blank` 弹窗。

对照实验（都在打包 exe 上做的）：两标签、切回标签、隐藏 70 秒、最小化 70 秒、被全屏置顶窗
盖住 40 秒 —— **六种情况全部正常渲染**。只有「最小化期间再发一条会触发 layout 的命令」
（`activate`，或点一个 `target=_blank` 链接）才转白。所以这条缺口不是「窗口一不小心就白」，
而是有确定的命令时序前提。

出图（`dist/复现B-*.png`）：`最小化期间点 target=_blank` 未修复 → 恢复后只剩标题栏 + 菜单栏；
已修复 → 标签条两页、地址栏、页面全在。

另外，窗口标题统一改成 **`dsh网页窗口`**（原来是 `dsh browser`）：宿主是 `BaseWindow`，
标题只认创建时那一个值、不跟页面标题走，所以在任务栏 / Alt-Tab 里是一眼能认出的固定名字。
