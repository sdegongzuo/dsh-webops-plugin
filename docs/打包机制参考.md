# 打包机制参考

本文件说明桌面补丁、缓存、运行时布局及故障判据。当前执行顺序和发布门禁以 [打包与发版](打包与发版.md) 为准；修改上游版本时重新核对事实，不把旧版数字和路径当固定契约。

## 1. 四个前置（缺一必挂）

桌面补丁由 [harness-desktop-build.patch](harness-desktop-build.patch) 管理；workflow 的 HARNESS_REF 与补丁基线一致。补丁理由按职责核对：

| 职责 | 当前约束与验证 |
|---|---|
| 运行时外置 | electron-builder 的 extraResources 与 main.ts 的 resources/dsh 配套；运行时描述符和全量文件哈希校验一致 |
| 桌面启动环境 | 便携 DSH_HOME、provider、窗口宿主与包内 Node 默认值在 resolveDesktopPaths 前注入；显式设置优先 |
| 窗口宿主 | 单实例锁前识别 DSH_BROWSER_ELECTRON_HOST，否则第二个实例直接退出 |
| 回环认证 | localhost、127.0.0.1 与 IPv6 候选使用真实认证判断；Node fetch 与 Chromium 栈都通过才选为转发地址 |
| WebSocket | cookie 注入名单与实际选定主机名配套，不能只支持其中一种回环地址 |
| 欢迎页 | 按消费者使用的请求栈分别探测，不沿用另一栈的认证结论 |
| Windows 沙箱 | runner 与 PTC 使用实际包内 Node；清理环境后仍可运行 |
| asar 与冒烟 | 外置运行时不再按 app.asar/dsh 路径校验；外置目录仍做完整性和 Office→PDF 验收 |

升级时在干净上游核对补丁可应用，再核对每个 hunk 的语义；本地已打补丁的工作树可用反向 apply 检查判定。自动合并成功不能替代语义审查。生成补丁时包含工作区和索引里的本任务改动，避免遗漏已暂存部分。

上游可能已实现某个修复，届时只保留仍需要的定制；同时复核 developmentRuntimeDirectory、resolveDesktopBuildTarget 和 prepareDevelopmentProject 等调用契约，补丁目标 diff 不能覆盖新启动要求。

## 2. 桌面政策与路径

apps/desktop/.env.windows 必须满足当前上游桌面政策校验，release 设置不能依赖被过滤的 ambient 环境。test 模式的强制更新配置要求非空 allowedAuthOrigins；production 的约束不同，以当前政策代码为准。unsigned 仅跳过签名，不跳过政策校验。

Windows LibreOffice 载荷的路径深度会影响 DOCX/XLSX/PPTX→PDF；某一种格式成功不能证明全部成功。CI 使用短 harness 路径，终端用户的解压目录也保持简短。

本机镜像与路径由 scripts/local-env.mjs 读取，配置来源和环境优先级见 [开发规则](agent-rules/开发.md#2-本机路径)。构建脚本的删除、移动与临时补丁恢复行为必须先检查；使用新的输出与保留证据模式。

## 3. 本体缓存

缓存按 dsh 版本分槽，cache.json 表示已完成；只有标记、布局和实际文件校验全部通过才使用该槽。写入顺序为创建目录、复制、校验、完成标记，不用目录重命名解决 asar 句柄问题。

CI 缓存键同时包含上游提交与补丁 hash；改变上游或补丁触发缓存失效是预期行为。环境不满足时明确失败，不静默选其他版本。scripts/package-desktop-portable.mjs 负责缓存与组装，参数以当前源码为准。

## 4. profile 与增量加载

桌面 profile 的插件目录是实际文件；宿主核心包由 app/resources/dsh/node_modules 提供。旧版 desktop-runtime-state.json 与 profile 核心包链接不是当前出厂条件。

applyRelease 在状态自洽时不会因插件增量覆盖重新跑包管理器。插件版本与 bundle 来自已安装插件的 package.json；用户 profile/package.json 中的登记和启用列表单独保留。

三轮 verify-plugin-update 分别验证原始产物无探针、增量产物有探针、恢复产物无探针。比较客户端 bundle 前剥除 sourceMappingURL 的动态 rev；其他字节仍应一致。最终 ZIP 安装与用户数据哨兵另外核对，不能用三轮探针包替代。

### 出厂 bundle

出厂 bundle 清单由两个打包脚本的 `FACTORY_EXPERIMENTAL_BUNDLES` 维护；修改时同步两处和 `verify:portable` 断言。2026-10-18 起默认额外开启 agent-team-profile、auto-review、tool-worktree、terminal-bundle、session-search。

登记方式与 UI 的 `setBundleEnabled` 一致：追加到 `dsh.profile.bundles`，不写 `dependencies`，包体由随包运行时提供。这些 bundle 不注入侧边栏。`verify-portable` 的 [2/5] 检查它们已启用且运行时文件存在。升级保留用户 profile。

### vendor 依赖登记

| 位置 | 用途 |
|---|---|
| 插件自身 `package.json.dependencies` | 插件声明的依赖；已打进 bundle 的包无需额外解包 |
| `manifest.plugins[].runtimeDependencies` | 指定该插件需要额外解包的运行依赖，如 ws、yaml、zod |
| `manifest.dependencies` | 上述运行依赖的版本、tarball 和 integrity 登记 |

打包先写 profile 的精确版本依赖，再追加 bundles，最后运行 `materialize-vendored-plugins.mjs --profile-dir`。脚本校验插件和依赖的 sha512，按 `runtimeDependencies` 查表解包；缺登记或身份不符即失败。vendor bundles 追加在内置两个 bundle 与本插件之后。

插件版本、tgz 和校验值统一登记在 `vendor/plugins/manifest.json`。新增或升级时一并更新 tgz 与 integrity，sha512 与 registry 的 `dist.integrity` 一致；先生成 profile 登记，再运行 `scripts/materialize-vendored-plugins.mjs --profile-dir <STAGE>/home/profiles/desktop`。`verify:portable` 的 [2/5]/[3/5] 检查登记和实际文件一致。

better-sidebar 自带 `dsh.bundle.patch`，由 profile boot 合并，使用 insert 和 `!!js` 防重复挂载，不手写进用户 `cordis.patch.yml`。旧版本适配见 §9。

### 包类型与组装

| 包类型 | 内容与用途 |
|---|---|
| overlay 自检包 | 仅含 `home/profiles/desktop/node_modules/dsh-webops-plugin` 下的 lib、package.json、cordis.patch.yml，以及根目录更新说明.txt；核对五个 Electron 资产，排除 fake-llm 文件和导出；仅供三轮自检 |
| 独立插件发布包 | 根目录即插件内容，包含完整生产 lib、cordis.patch.yml、发布版 package.json、README、LICENSE、INSTALL.md，缺项失败；lib 含 browser-electron 资产、排除 fake-llm，package.json 剔除 devDependencies、scripts 和 fake-llm 导出 |
| 完整便携包 | `package-release-portable.mjs` 只取已验收基包 app，新建出厂 home，装入本次插件 ZIP 与 vendor 插件，不复制用户数据；release-manifest.json 分记 pluginVersion 与 dshVersion |

两个插件打包脚本必须显式传 `--lib-dir`，缺失时在写入前拒绝。`package-portable.mjs` 在 stage-root 下创建唯一暂存目录，全程保留文件，`--keep-stage` 仅统一参数。输出父目录自动创建，路径直接传 Python，不拼接 PowerShell。

两个插件打包脚本使用 `zip-stage.py --no-overwrite` 独占创建 ZIP，拒绝既有目标及检查后出现的目标。旧覆盖分支不用于本机；行为回归见 `src/package-portable.test.ts`。

完整包组装要求三个 DSH peer 声明与基包运行时版本精确匹配。含便携数据接线的新基包直接使用，不重复运行仅支持 alpha.2 的 `prepare-release-app.mjs`。

组装时，`planSlimAppCopy` 先只读核对中英文语言包和两份 pnpm 的逐文件一致性，再在复制时排除其他语言包及已证明重复的旧 pnpm，保留输入和暂存。旧 `slimApp`/CLI 会删除文件，不用于本机；此保留路径不代表桌面本体旧入口也安全。

### 便携数据归属

| 目录 | 保存内容 |
|---|---|
| home | 会话、配置、凭据、插件与依赖运行时 |
| data | Electron 数据、缓存、日志、临时文件及用户工具目录 |
| data/browser | 浏览器 Cookie 与站点数据，同一实例的所有标签和对话共享 |

不同包目录可并行，同目录重复启动聚焦原实例。启动脚本使用 `setlocal` 并转发参数。升级保留用户 home、data 和 profile 登记；新目录隔离行为需要更新桌面壳，只更新插件无效。

桌面补丁在获取单实例锁前，将 DSH_HOME、Electron userData/sessionData 及已知全局写入目录绑定到本包 home/data，不接受其他实例继承的目录覆盖。首次默认工作区在 data/documents/deepseek-harness/default-workspace；已有、主动选择或明确配置的工作区不搬迁。

旧系统 Electron 偏好与登录态不自动导入。需要保留偏好时，退出实例，把明确属于它的 keybindings.json 和 desktop/settings.json 复制到 data/electron 对应位置，保留原文件。

旧版 data/temp/dsh-browser-electron-host 不自动迁移，旧数据保留，用户需重新登录。开发态默认用当前 DSH_HOME/data/browser，非空的 DSH_BROWSER_USER_DATA_DIR 显式设置优先。用户操作见 [安装说明](portable-install.md#网页登录态与数据保留)，验证见 [浏览器登录态验证](浏览器登录态验证.md)。

## 5. 真机证据与常驻进程

桌面进程需要脱离工具调用的 job object；同一调用内等待后查询不能证明它存活过工具退出。优先使用 portable-dev.mjs launch，并跨调用检查实际进程和 renderer CDP。

workspace 初始化、凭据登记和 __DSH_BOOT__ 能证明部分加载状态；真实模型回复、工具调用、鼠标交互和人工接管按钮必须另外验收。不要在证据输出中打印当次认证 token。

窗口标题正常仍可能被其他透明窗口遮挡。定位时列出所有 renderer target，核对正文、可见性与焦点；单页 elementFromPoint 无法发现跨窗口遮挡。历史 shell 页面 404 故障已修，若复现则按实际页面和上游实现重查。

## 6. 包内 node 路径（打包态专有坑，已修）

process.execPath 在 Electron 打包态指向主 exe。环境清理后将 Node 脚本交给这个 exe，可能起 GUI、撞单实例锁或等待协议超时。

当前 Node 在 app/resources/runtime/primary-runtime/dependencies/node/bin/node.exe；由 runtime 描述符、存在性及运行结果校验确认。resources/runtime/bin/node.cmd 依赖环境变量，不适用于清理环境后的 PTC 子进程。

PTC 的 `launch.executable` 通过插件 cordis.patch.yml 覆盖（0.1.6 时代的上层键 `nodeExecutable` 已被上游 2026-09-12 改名废弃，写它不报错但服务不读）；verify-ptc 使用真实 compose + 真 schema 解析双重验证。sandbox runner 的选择与主进程注入同时核对，避免只修其中一条链。

## 7. 压缩、解压与诊断

ZIP CRC 校验与写盘内容校验是两项证据。testzip 通过后仍需检查解压产物无 NUL 污染；字节数正确不能替代内容检查。scripts/unzip-portable.py 的 only-prefix 自检只覆盖本次写出的文件。

文件锁导致 Compress-Archive 失败时，Python zipfile 的共享读可用于压缩；zip-stage.py 统一 stdout/stderr 为 UTF-8，避免 Windows runner 的 cp1252 中文编码错误。输出路径已存在时仍可能走删除分支，执行前选择未存在路径。

host never announced a port 只表明未取得端口。继续查 Electron 主进程异常、被 external 化的 workspace 依赖、产物加载路径及 UI 异常框；缺少 stderr 不代表没有异常。

## 8. 发布链的职责

`release.yml` 发布独立插件包和完整便携包；`release-desktop.yml` 用于升级 DSH 本体。两个 workflow 都签出目标 tag 并验证版本；dispatch 选 main 不会把 main 修复带入旧 tag。

### 日常插件发布的自动步骤

| 步骤 | 自动检查 |
|---|---|
| 构建插件 | `tsdown --no-clean`，复制 Electron 资产 |
| 打独立插件包 | 显式传构建目录和保留参数，拒绝覆盖旧 ZIP |
| 组装完整包 | 下载固定基包并校验 SHA256，只取 app，重建出厂 home，装入本次插件和 vendor 插件 |
| 验最终 ZIP | 解压并运行 `verify-release-portable`，校验运行时哈希、出厂数据边界、三个插件版本和真实宿主首页加载图，不依赖 harness lib |
| 发布 | 上传两个附件到草稿，校验均已上传且 GitHub digest 与本地 SHA256 一致，再公开；失败保留草稿和验证目录 |

本机验收和发布后核对按 [日常发版三步](打包与发版.md#日常发版三步) 执行。

类型检查和单测依赖本机构建的 harness workspace 产物，当前作为本机发布门禁；改变 CI 门禁前先保证完整依赖链，另建验证 workflow 不等于发布 workflow 已具备这些产物。

同一目标 tag 的 push 与 dispatch 必须落在同一 concurrency 组，后来者等待，避免同时写附件。收尾 Summary 无论成败列产物状态；失败 runner 不必保留可下载 ZIP，Summary 也不能证明发布成功。

同名 Release 的上传覆盖分支涉及删除已发布附件，不受日常重跑授权覆盖。改源码后发布新版本，保留旧 tag 和附件；新的 workflow 结论与 Release 完整性分别核对。实际版本结果见 [验收记录](验收记录.md)。

## 9. 随包侧边栏适配

当前随包版本以 `vendor/plugins/manifest.json` 为准；0.28.0 未启用 `hostCompatibility`。以下说明旧版适配机制，不代表当前包仍需打补丁。

| 项目 | 规则 |
|---|---|
| 启用 | manifest 设置 `hostCompatibility: connection-fence-pr905-v1`，物化脚本调用 `sidebar-host-compatibility.mjs` |
| 版本范围 | 仅接受 `SIDEBAR_COMPATIBLE_VERSIONS`；版本或补丁目标变化即失败 |
| 补丁来源 | 按上游 PR #905 的 `8f521f4` 移除必需的 `webRuntime` 注入，保留其可选调用 |
| 请求校验 | 先用原侧边栏校验，再用可选的 `connection.requestRejection()`；401 放行、403 拒绝，保留旧宿主、桌面与 loopback Origin、图片恢复特例 |
| 文件保留 | 不改官方 tgz 和 SHA512；保留原模块、上一补丁及哈希回执 |
| 验收 | 请求 `/sidebar/api/fs.read`，须返回侧边栏 JSON 方法校验信封；空 405 失败 |

上游修复后停用适配并重新验收。历史来源见 [PR #905](https://github.com/omdsh-dev/DSH-better-sidebar/pull/905)，不将其当作正式发布证明。
