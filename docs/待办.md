## 1. 大纲重复折叠：按 (role, name) 折叠 SERP 类重复按钮

**状态**：**已完成（2026-09-18）**（含一条 live 形状契约用例）
**问题**：谷歌搜索结果页等长页面，每条结果都带同一组按钮（「翻译此页」「查看详细信息」「分享」），12 条结果 × 3 按钮 = 36 行噪音，800 行大纲预算被烧光，有效信息（结果标题、摘要）反而被截断。**实测比这还大**：每个按钮下面还挂一行同名 `text`，噪声翻倍（见「实测修正」）。
**原则**：折叠只影响**展示层**，不影响**寻址层**——每个重复按钮都是真实可交互节点，硬过滤会丢精确寻址能力。

### 实施记录（2026-09-18）

落地位置与本文设计的**三处偏离**，都是实施中判定的，理由随附：

1. **折叠决策落在 `buildOutline`（不是 `renderOutline`），新增 `unfoldedLines` 视图**。
   本文原写「折叠只发生在 `renderOutline` 输出层」，但预算（`chars` / `maxLines`）是在
   `buildOutline` 里累计的 —— 折叠若只发生在渲染层，省下来的行额换不到任何正文，
   折叠就只剩「看着清爽」。所以改成**先在 `buildOutline` 里定折叠、再按折叠后的集合结算预算**，
   并把「折叠前的行序列」作为 `unfoldedLines` 一并产出（`renderOutline(..., { unfoldRepeats: true })`
   渲染它，`webpage_find` 的底稿就是这一份）。
2. **折叠单元 = 实例行 + 它的同名标签行**（本文没写这一层，实测逼出来的，见下）。
3. **「有已打印后代就不折」改成「子树里只能有与自身同名的标签行」**。原规则在真实页面上
   一个都折不到；新规则既不丢内容，也不会让子行在缩进上变成孤儿。

**实测修正（关键，2026-09-18 无头 Chrome 153 实测）**：Chrome 的 AX 树把
`<button aria-label="翻译此页">翻译此页</button>` 展成 `button "翻译此页"` **加一个子节点**
`text "翻译此页"`。第一版的护栏「有已打印子行就不折」因此把**全部**重复按钮挡住 ——
实测那一跑 `foldedRepeats=undefined`，15 个按钮一个没折；而当时的单测夹具里没有这个子节点，
26 条断言全绿。修完再跑同一张页面：**59 行 → 35 行**，15 个按钮的 ref 一个不少，
`foldedRepeats=12` 与三个 `×5` 标记严格对得上（`Σ(×N − 1)`）。

**计数口径**：`foldedRepeats` 只数**实例行**（`Σ(×N − 1)`）；跟着一起收起的同名标签行**不计**
（它不是独立元素、没有 ref）。`foldedRepeats`（折叠了几个）与 `droppedElements`（预算不够、
没输出）分开报，回执里也分开说 —— 抬 `max_lines` 对折叠毫无作用，混报会把模型引到错误动作上。

**验证**：

  **358 passed / 0 skipped**（无头 Chrome 153，`DSH_CDP_ENDPOINT=http://127.0.0.1:9333`）。
- 反向验证四组，逐条转红后恢复：① 阈值改硬编码 → 两条阈值断言红；② 删子树护栏 → 护栏断言红；
  ③ 折叠行不计入底稿 → 两条底稿断言红；④ 折叠单元退化成「有子行不折」→ 单测与 **live 用例同时红**
  （这条最要紧：它证明夹具真的照着真实树画，而不是照着我的想象）。
- 出货产物确认：`lib/` 里含折叠逻辑与标记文本。

**顺带发现（未做，建议单独立项评审）**：真实树上每条结果的标题是

**原设计（存档）**：

**问题**：见上。
**原则**：折叠只影响**展示层**，不影响**寻址层**——每个重复按钮都是真实可交互节点，硬过滤会丢精确寻址能力。

**改动点**（`src/browser-cdp/snapshot.ts` 的 `buildOutline`/`renderOutline`）：

1. 两遍构建：第一遍照常产出行并记录父节点 id（`OutlineLine` 内部字段，不进公开类型），第二遍按 (role, name) 统计。
2. **折叠规则（2026-09-18 review 修订）**：全局 (role, name) 计数 **≥4** 即折叠——只打印首次出现的那一行，其余压成一行标记：
   `- button "翻译此页" ×12（已折叠，用 webpage_find 拿全部实例的 ref）`
   原设计的「同父 ≥3 + 跨父 ≥10」双阈值**已废弃**：SERP 的重复按钮各自挂在不同的 listitem 下，同父规则一条都折不到；跨父 ≥10 在 Google 每页 8~10 条结果时又漏（×8 < 10）。「误折不同上下文同名按钮」的顾虑由 find 通道兜底（find 列出全部实例+ref），不在阈值上做双轨。
3. **ref 分配语义（review 第二轮明确，关键）**：`buildOutline` 的 `rows`/ref **仍然全量分配**（`publish()` 行为不变），折叠**只减少 `renderOutline` 打印的行**。理由是折叠标记承诺「用 webpage_find 拿全部实例的 ref」——若折叠元素不分配 ref，find 缓存里就没有它们，这句承诺直接不成立，折叠等于真丢寻址。ref 表本身不进上下文，全量分配零上下文成本。
4. **statictext 永不折叠**——搜索结果标题/摘要是区分两条结果的正文。
5. `webpage_find` 的 snapshot 缓存（`tool-browser/index.ts`）存**完整未折叠**大纲，折叠只发生在 `renderOutline` 输出层。缓存条目结构见总纲第 2 条。
6. **find 命中行补祖先上下文（review 第二轮新增，关键）**：折叠把寻址转嫁给 find，但 12 个「翻译此页」在 find 结果里**文本完全相同、无法消歧**——模型不知道该点哪个。find 回执的每行要附「所属祖先链上最近的 heading/statictext」作为上下文，形如 `button "翻译此页" [ref=e37] ← 属于：Rust 官方文档`。
   实现代价要算进来：`buildOutline` 需在遍历时记录「最近祖先 heading/statictext 文本」到 `OutlineLine`（下行时把该上下文带下去），find 检索时随行返回。**没有这一条，折叠方案不可用**。
7. 折叠统计 `foldedRepeats` 进返回值，与 `truncated`/`droppedElements` 一样如实上报（注意：折叠元素**不算** `droppedElements`——它们没丢，只是没打印）。
8. **统计口径（review 第三轮补）**：折叠统计以**本次输出集合**为基数（区域快照下就是区域内），不是全页。`foldedRepeats`（折叠了几个）与任务 5 的 `outsideRegion`（区域外还有几个）是**两套互不相干的计数**，回执必须分开报、各自注明口径——这是 P2 预算那次「`truncated` 与 `truncatedByBudget` 必须分开报」的同类教训：给错口径比不给更糟。
9. 预算联动：`chars` 按折叠后的行累计；`resolveSnapshotLimits` 不用动。

**测试**（`snapshot.test.ts` + tool-browser 相关）：

- 断言 `webpage_find` 能命中被折叠的实例、返回各自 ref、**且命中行带祖先上下文**；

- 同步更新现有 ref 顺序断言（折叠会改变打印行数，但不改变 rows 顺序）。

## 2. 跨 epoch 稳定元素定位：ref 失效后低成本恢复

**状态**：待做（设计已评审，结论如下）
**问题**：ref 绑定 epoch，页面任何变动后旧 ref 全部失效，恢复通道目前只有「重新全量 snapshot」（工具描述写死 `only recovery is a fresh snapshot`，见 `tool-browser/index.ts:1558/1712/1717`）。多轮对话场景反复快照撑爆上下文。
**当前机制事实**：`RefRegistry.publish()` 整表换血（refs.ts:73）；`invalidate()` 导航清空（refs.ts:91）；`resolve` 前置纪元校验（refs.ts:103）；provider.ts:792 已有 `DOM.resolveNode` 验活路径可复用。

**分阶段设计**：

- **P1 `webpage_revalidate`（精确恢复，零上下文成本）**
  - `RefRegistry` 保留最近 K 个纪元的表（环形封顶，K 建议 3；条目数封顶如 2000）；`resolve` 仍严格报 stale，不放水。
  - **文档身份校验（review 第二轮新增，关键）**：纪元推进时记录文档标识，revalidate **先比对旧纪元记录的文档标识与当前文档**——不一致则**直接拒绝精确恢复**（转 P2 指纹），不看 backendNodeId。原因：「同一 backendNodeId 要么同节点要么没有」**只在同一文档生命周期内成立**；导航后 backendNodeId 重新编号，可能撞上旧号并成功解析到**新文档里的另一个节点**，若其 role/name 恰好相同（新页面也有「下一页」按钮）就会**静默命中错误元素**——这是本设计最忌讳的失效形态。role/name 核对是第二道防线，不能当唯一防线。
  - **标识怎么拿（review 第三轮修订）**：用 **`Page.getFrameTree` 按需读取主 frame 的 `loaderId`**，在 `publish()` 时随纪元一起记下。**不要走事件订阅**——已核对：provider 目前只发 `Page.enable`、**没有订阅任何 Page 事件**（provider.ts 内 `connection.on(` 零命中），走 `Page.frameNavigated` 订阅要新建订阅管线（协议层 `on` 虽有，但会话生命周期/重连/解绑都要照顾），而按需读取只需一次命令、无状态、零生命周期负担。loaderId 每次导航都会变，足以当文档身份。
  - 通过文档校验后：旧表里的 `backendNodeId` → `DOM.resolveNode` → `describeNode` 核对 role/name → 一致则通过总纲的 `adopt()` 原语把**同一 ref 号装回当前纪元**。
  - 参数建议接受 **ref 数组**（多轮对话常一次要用多个旧 ref，逐个往返浪费）；单个 ref 是数组的特例。
  - 安全性质（在校验成立的前提下）：同一文档内同一 backendNodeId 要么解析到同一节点要么没有；「序号单调不重置」原则不动。
- **P2 指纹兜底（跨导航）**
  - `publish` 时存指纹 `{role, name, DOM 路径}`；导航后 backendNodeId 必死，用指纹 `Runtime.evaluate` 搜候选。
  - **匹配策略（review 第二轮明确）**：**role + name 为主判据**，DOM 路径只作**加权/排序**——SPA 下 class 与 nth-child 高度不稳定，把路径当硬条件会大量漏匹配。
  - 唯一命中 → 自动恢复；多命中 → 返回候选让模型挑，**绝不自动绑**。
- **P3 子树快照**：**已划入任务 5**（ref 子树是区域快照的形态之一），实施时从本任务移除。
- **排除**：增量失效（mutation 监听管线复杂、AX 树反正是整棵重取，先不做）。
- **配套**：`BROWSER_STALE_REF` 恢复提示文案改为「先 revalidate，失败再 snapshot」。
- **边界**：iframe 的 backendNodeId 按 frame 隔离，P1 先限定同 frame；恢复写回走 provider 串行路径。
- **测试**：恢复成功 / 节点已死 / role-name 不符 / **loaderId 不一致（新增，断言直接拒绝而非误绑）** 四条路径 + **反向验证**（故意改坏文档校验确认转红）。

## 3. 页面刷新稳定 + AI 问答回答完成信号

**状态**：待做（设计已评审，结论如下）
**问题**：
1. 刷新/settle 判定只看 URL 变化（`detectNavigation`，provider.ts:1520）+ `readyState complete`（`settleDocument`，provider.ts:1557）+ 标题非空。SPA 数据继续加载、骨架屏换正文、图片懒加载都不覆盖，模型只能反复 snapshot 探测。
2. AI 问答页（DeepSeek/ChatGPT/豆包/Kimi 等）回答是流式生成：没有 load 事件、没有 URL 变化、没有现成「生成完成」信号，模型要靠 snapshot 轮询文本长度——每次 10~40k 字符，多轮问答直接烧穿上下文（与任务 1/2 同一条上下文经济主线）。
**现有可复用资产**：`webpage_wait` 已有等时间/等文本/等元素消失三种语义且回执带 `satisfied`（tool-browser/index.ts）；`networkCollector` 已在收全量请求生命周期事件（P2 预算系统）——信号源现成。

**设计：quiescence 三信号组合判定**

**A. 页面稳定（`webpage_wait` 加 `until: 'stable'` 目标）**

1. **readyState complete**——已有，保留。
2. **DOM 静默**：MutationObserver 计数探针（每会话幂等安装，`window.__dsh_mut` 旗标防重装；导航后重装），轮询「自上次读取以来增量 = 0」连续两个安静窗口（如各 500ms）判稳。
3. **网络静默**：networkCollector 加 inflight 计数（requestWillBeSent +1，loadingFinished/loadingFailed −1），inflight == 0 持续一个窗口。

组合判定 + **deadline**，判稳规则（2026-09-18 review 明确化）：`readyState complete` 是前置，`stable = readyState && domQuiet && (networkQuiet || 网络忙已持续超过宽限期)`；超时不算失败，**回执如实报哪个信号没安静**（`satisfied: false, signals: {dom: 'busy', network: 'quiet', ...}`）——沿用「截断可解释」原则，绝不把慢页面谎报成稳定。宽限期（如 3s）管心跳/长轮询站点：网络信号只能加权，不一票否决。

**B. AI 问答「回答完成」（同一套信号的特例，零站点特判）**

信号优先级：

1. **流式请求关闭（最强、最通用）**：所有主流聊天页都用 SSE 或流式 fetch 吐字，生成结束这条请求才关闭。inflight 计数把「生成中/已完成」化归为「网络忙/静默」——不用读页面文本，不用写任何站点规则。**与折叠任务同一原则：不写站点黑名单**。
2. **回答容器文本停止增长**（次强）：MutationObserver 增量 + 定向读容器 textLength，连续 N 窗口不变。作为信号 1 的旁证（SSE 关了但页面还在渲染 markdown 时由它兜底）。
3. **停止按钮消失（仅佐证）**：role=button、名称含「停止/Stop」的元素消失。跨站语言/命名不稳，只做第三旁证，不单独定论。

**落点**：

- `browser-cdp/network.ts`：networkCollector 加 inflight 计数与「当前有无打开的流式请求」查询。
- `browser-cdp/provider.ts`：quiescence 组合判定 helper（新），`webpage_wait` 处理器接入 `until: 'stable'`。
- `tool-browser/index.ts`：`webpage_wait` 描述与回执 schema 加 `until` 参数与 `signals` 明细。

**范围边界（review 第二轮明确，防误伤）**：

- **本轮不动 `settleMutation` / 自动 settle**（click、press、navigate 后的既有等待逻辑保持原样）。只加**显式** `until: 'stable'` 目标——若顺手把 quiescence 接进自动 settle，每次 click 都会多等一个安静窗口（≥1s），把简单操作拖慢，属于回归。
- **`webpage_wait` 需要可配 deadline（已核对现有数值，2026-09-18 review 第二轮）**：现有三种模式是 `time_ms`（1~30000，封顶 `MAX_WAIT_TIME_MS = 30_000`）/ `text` / `ref`，且描述写死 **「Exactly one of time_ms / text / ref」**；text/ref 的等待窗口走 provider 配置 `waitTimeoutMs = 10_000`（provider.ts:97），超时报 `satisfied: false`。
  - **问题**：AI 回答生成常见 10~30s，10s 窗口会让模型在生成中途拿到 `satisfied: false`，误判「生成完了但没内容」——正是本任务要消灭的误判。
  - **改法**：① `until: 'stable'` 作为**第四种模式**，同步改「exactly one」的校验逻辑与错误文案（否则模型传 `until` 会被现有互斥校验拒掉）；② `until: 'stable'` 的窗口默认取大值（如 30s，与 `MAX_WAIT_TIME_MS` 对齐）并允许 `timeout_ms` 覆盖，硬上限不得超工具超时。

**坑与边界**：

- 心跳/长轮询站点 inflight 永不清零 → 稳定判定必须 deadline + 分信号报告，网络信号只能加权不能一票否决。
- SSE 请求在 Network 域的生命周期时序（streaming response 的 loadingFinished 何时发）**需真机实测**——大多数实现里 SSE 请求 pending 到连接关闭，正好是我们要的，但要防 HTTP/2 多路复用例外。
- MutationObserver 探针跑在页面 JS 上下文，`Runtime.evaluate` 是 CDP 特权通道不受页面 CSP 限制，无沙箱问题；但要处理探针安装时页面正在换文档（安装失败静默重试下次轮询）。
- **探针状态是可篡改的（review 第三轮补）**：`window.__dsh_mut` 是页面全局，而 `webpage_execute` 的白名单**允许 `Runtime.evaluate`**——页面脚本或用 execute 的模型都能读写它，从而伪造「DOM 静默」。按本项目「页面内容永远是数据不是代码」的哲学，处理方式两条：① 判定不得只依赖探针（`readyState` + 网络信号构成的多信号结构本身就是防线，单信号被污染不至于直接误判）；② 回执里不要暴露探针的全局名与计数器语义，避免被页面内容诱导去改它。若后续发现真被污染，再考虑换成 CDP 侧计数（如 `Runtime.addBinding`）。
- 上下文成本：一次 wait 回执 1~2 行，替代反复 snapshot 轮询；与任务 2 的 revalidate 互补（页面真变→revalidate/快照，页面在生成→wait）。

**测试**：

- fixture 页：setTimeout 分批改 DOM → stable 在安静窗口后判定；持续心跳 → deadline 超时且 signals 如实报 busy。
- **反向验证**：注释掉 DOM 静默判定，确认含动态内容的 fixture 会误判稳定（转红后恢复）。
- SSE 信号需真机实测用例（本地起一个 SSE 端点的 fixture 页）。

## 4. JS 执行器与按键执行器 bug（Space 键名 / contenteditable / userGesture）

**状态**：**代码层已完成（2026-09-18）**；剩 live/真机行为验证。
**更正（2026-09-18，重要）**：本条原写的「Bug 1：Space 条目缺 `text: ' '`」**是我的误读**——`text: ' '` 自 P1 提交 `56f5ad2` 起就在（`git show HEAD:...` 已核）。真凶见下，是**另一个**更贴近现象的问题。

### Bug 1（真凶）：`key: "Space"` 被判为不支持的键

`KNOWN_KEYS`（provider.ts）里只有单字符写法 `' '`，**没有 `'Space'`** —— 但**错误文案**与 **`webpage_press` 工具描述**都把 `Space` 当命名键宣传。模型照描述写 `key: "Space"` → `describeKey` 走「多字符且不在名单」分支 → 抛 `BROWSER_PROTOCOL_ERROR: unsupported key "Space"`。**宣传的名字必须真的能用**，这是「模拟不了按键，比如 space 键」的真正来源。
**修法**：抽出 `SPACE_KEY` 常量（`{ key:' ', code:'Space', virtualKeyCode:32, text:' ' }`），`' '` 与 `'Space'` 两个键名共用。

### Bug 2：fill 对 contenteditable 失效（AI 问答页「输入问题」断链的另一半）

原来的 `fill` 对非 input/textarea 一律 `element.textContent = value` —— 不触发 `beforeinput`，Lexical/ProseMirror/Slate 等富文本框架（AI 问答页输入框的主流实现）内部状态不更新、发送按钮不亮；且丢换行结构。
**修法（已实现）**：页面内函数改为三分支并返回走法（`'value'` / `'editable'` / `'text'`）；`contenteditable` 分支只做**聚焦 + 全选**（`selectNodeContents`），真正的写入由 provider 随后发 **`Input.insertText`** 完成——走浏览器原生输入管线，`beforeinput` 才会派发。**必须先全选**：`insertText` 是「在选区处插入」，否则新值会拼接到旧内容后面。

### Bug 3：webpage_execute「执行不了 JS」的三个形态

1. **缺 `userGesture: true`** → **已修**：`Runtime.evaluate` 现在强制 `returnByValue` + `awaitPromise` + `userGesture`。不带时 `clipboard.writeText` / `requestFullscreen` / `window.open` / 媒体自动播放一律被页面拒 `NotAllowedError: Transient user activation is required`——「执行不了」的最常见形态。
2. **`awaitPromise: true` 强制等待** → **已改文案**：工具描述补「长期不落定的 Promise（流、轮询循环）会一直阻塞到超时，只需快速答案时用 `Promise.race([...])` 包一层」。不引入异步回执。
3. **`isEmptyObject` 误杀合法 `{}`** → **已改文案，维持拒绝**：`document.body` 静默 `{}` 与合法空对象在序列化结果上无法区分（subtype 也不是 node），放行会让模型拿到垃圾 `{}` 当成功。新文案写明出路（`JSON.stringify({})` / 取具体字段），DOM 节点与空对象走**两条不同**的针对性文案。

### 配套（已实现）

- `Input.*` 前缀拒绝文案补引导：「模拟按键/输入/滚动请用 `webpage_press` / `webpage_fill` / `webpage_scroll`」——防模型以为按键能力不存在。
- `webpage_press` 描述补能力边界：只能产生**单个 ASCII 字符**，CJK 等组合文本无法走键事件 → 用 `webpage_fill`。
- `webpage_fill` 描述补：contenteditable 走原生输入管线（框架状态与发送按钮会更新）；`webpage_execute` 描述补 userGesture 与 Promise.race。

### 测试（已落地 6 条新断言）

- **参数层（单测，mock socket）**：`Space` 与 `' '` 两个键名都可用且 keyDown 带 `text: ' '`（**反向**：`Meta` 仍拒）；contenteditable 走 `Input.insertText` 且页面函数含 `selectNodeContents`（**反向**：普通 input 绝不调 insertText）；evaluate 带 `userGesture: true`；空对象仍拒绝且文案含 `JSON.stringify({})`；`Input.*` 拒绝文案含 `webpage_press`/`webpage_fill`。
- **反向验证已完成**：一次改坏三处（删别名 / 关掉 editable 分支 / userGesture 置 false）→ 三条断言**同时转红**（3 failed），恢复后 340 passed。
- **未做（需真机）**：真浏览器里 seletion+insertText 的实际写入、`navigator.clipboard.writeText` 不再 NotAllowedError、AI 问答页全链路（fill 问题 → 发送 → 等回答，衔接任务 3）。

## 5. 快照按区域返回：ref 子树 / 视口 / 几何矩形

**状态**：待做（设计已评审，结论如下）。**吸收并扩展任务 2 的 P3**（ref 子树快照）——实施时把 P3 从任务 2 划入本任务。
**问题**：长页/多屏页一次全量 snapshot 烧预算（10~40k 字符），模型明明只关心某个结果卡片、当前视口或某个区块。按需取区域是上下文经济主线的第四条通道（折叠省密度、revalidate 省快照、wait 省轮询、区域省范围）。

**CDP 支撑面（已核对）**：

- `Accessibility.getPartialAXTree`：按 `backendNodeId` 取子树 AX 树，**返回结构与 `getFullAXTree` 完全一致** → `buildOutline` 纯函数零改动复用。
- `DOMSnapshot.captureSnapshot`：一次调用拿全页布局树，每个布局节点带 `backendNodeId` + `boundingBox` → 与 AX 树按 backendNodeId join，本地做几何过滤，共 **2~3 个 CDP 调用**（viewport 形态还需 `Page.getLayoutMetrics` 拿视口尺寸），不需要逐元素 `DOM.getBoxModel`（那是 N 次往返）。
- 细节：captureSnapshot 的 `boundingBox` 是 **quad（四角）**，要取 min/max 转 AABB 再求交。

**`webpage_snapshot` 加 `region` 参数族**：

| 参数 | 语义 | 实现 |
|---|---|---|
| `ref` | 只出该元素子树的大纲 | `getPartialAXTree(backendNodeId)`，任务 2 P3 的落地 |
| `viewport: true` | 只出当前视口内可见元素 | full AX tree + captureSnapshot 布局盒与视口矩形求交 |
| `box: {x,y,width,height}` | 只出与几何矩形相交的元素 | 同上机制，矩形换成调用方给的 |

可见性判定：元素盒与区域**有交集即算**（部分可见的元素不该丢——模型正要滚向它）；`display:none`/透明节点 AX 树已滤。

**参数交互的两个约束（review 第二轮新增）**：

- `ref` 形态的锚点 ref **必须来自当前纪元**（stale ref 直接报 `BROWSER_STALE_REF`，与既有语义一致）；若模型手上只有旧 ref，先走任务 2 的 revalidate。
- 三种形态与 `max_lines` 可组合；`region` 与「按 ref 单元素截图」（`webpage_screenshot` 的 `ref`）是两套语义，不要复用同一字段名造成歧义。

**使用闭环（与任务 3 衔接）**：长文页的标准读法是 `webpage_scroll` → `webpage_wait until:'stable'`（等懒加载/渲染落地）→ `webpage_snapshot region:{viewport:true}` → 反复。区域快照是「读」，稳定判定是它的前置保证——两次阅读之间页面还在变的话，区域结果会自相矛盾。

**两个关键坑（不改就白做）**：

1. **区域快照不能沿用 `publish()` 整表换血**：否则全页快照的 ref 全部作废，模型取个区域就把之前攒的 ref 打光了——按需取区域的意义直接归零。用总纲的 **`adopt()` 原语做 additive publish**：区域快照的新 ref **追加**进当前纪元，序号继续单调递增。「同号不同元素」的不变量不受影响（新增的号来自新序列号，不碰旧映射）。这是对「每次 snapshot 推进纪元换表」既有不变量的**语义扩展**，必须写进 refs.ts 的模块注释。
2. **`webpage_find` 缓存语义**：区域快照**不得覆盖**全页缓存（否则 find 查不到区域外内容，模型被误导）。按总纲第 2 条：缓存条目带 `region` 标记，find 回执声明「当前缓存只含 X 区域」；同一会话的全页快照仍整体覆盖。

**回执如实**：`region` 范围回显 + 区域外元素计数（`outsideRegion: n`），防模型误以为看到全部——沿用「截断可解释」原则。**口径独立**：`outsideRegion`（区域外还有几个）与任务 1 的 `foldedRepeats`（折叠了几个）互不相干，必须分开报、各自注明口径（见任务 1 第 8 条）。

**与任务 1 叠加**：区域输出走同一套折叠逻辑（区域内重复按钮照样折）。

**测试**：

- ref 子树 / viewport / box 三形态 fixture：断言区域内元素在、区域外不在、`outsideRegion` 计数正确。
- additive 语义：全页快照取 ref → 区域快照 → **旧 ref 仍可用**；反向验证：若误用整表换血，断言转红。
- find 缓存：全页快照 → 区域快照 → find 仍能命中全页内容且回执带区域声明。
- （真机）长文页：viewport 快照 + 滚动 + viewport 快照，两次 ref 不互斥，总上下文远小于两次全量。
